# Mode 3 zkWrapper — 한 신원(salt)에 Google 계정 여럿 (설계, 2026-11-26)

- 상태: 사용자 승인(2026-11-26 — "1은 나(구현까지), 2·3은 권장대로"). 구현 결과는 §6.
- 배경(피드백 2026-11-26): "uid → salt 관계를 다시 정리. uid 여러 개를 한 salt 로 묶을 수 있는가? 풀 수 있는 문제는 맞는가?"
- 범위: zkWrapper 방식만. 회로·컨트랙트·증명 키는 바꾸지 않는다. 다른 방식(passkey-web·에이전트)은 손대지 않는다.

## 1. 지금의 관계 (코드 기준)

| 값 | 어디서 | 누가 쓰나 |
|---|---|---|
| salt(`s_u`) | 패스키(PRF) | 서비스 쪽 신원 전부: `auid = Poseidon(D, s_u)`, `PPID = Poseidon(s_u, arid, chainid)` — uid 는 2026-11-13 에 PPID 에서 빠졌다 |
| uid | Google `sub` 의 해시 | 발급 서버만: 본인 확인(Google 토큰), 개봉이 돌려주는 값, 계정 폐기 단위 |
| `C_u` | `Commit(uid, s_u, blind_u, attrs)` | 등록부 리프 `Poseidon(auid, Cf_u)`. zkWrapper 는 π_IdP 가 없어 `C_u` 안의 uid 값을 아무도 검사하지 않는다 |

묶음은 발급 서버가 만든다: 첫 발급 때 "uid 하나 = auid 하나" 로 고정하고(`auid_pinned`), 한 auid 는 한 계정만 쥔다(`auid_taken`).

## 2. 답

- **여러 uid 를 한 salt 로 묶을 수 있다.** 서비스가 보는 신원은 salt 뿐이므로 회로를 바꾸지 않는다. 발급 서버가 "이 uid 들은 같은 신원" 임을 기록하고, 어느 uid 로 와도 그 신원의 발급을 하면 된다 — 같은 PPID 가 나온다.
- **대가 1 — zkWrapper 는 그 Google 계정들이 같은 사람임을 안다.** 숨기려면 uid 마다 다른 auid(예: `Poseidon(D, s_u, uid)`)가 필요하고 회로가 바뀐다. 그러면 한 uid 의 계정을 폐기해도 다른 uid 로 같은 PPID 를 계속 쓸 수 있어 계정 폐기가 뚫린다. 하지 않는다.
- **대가 2 — 반대 방향(uid 하나에 salt 여럿)은 계속 막는다.** 허용하면 한 사람이 서비스마다 PPID 를 여럿 갖는다(중복 계정).
- **로그인의 두 요소는 유지한다.** 지금 로그인은 Google 계정 + 패스키 둘 다 있어야 한다. 연결이 한 요소만으로 되면 그 한 요소로 신원을 가져갈 수 있다 — 연결에는 지금 계정의 Google 확인, 패스키(salt), 더할 계정의 Google 확인 셋이 모두 필요하다(M3).

## 3. 결정

| # | 결정 | 이유·대가 |
|---|---|---|
| M1 | 신원 = 지금의 계정 레코드(`accounts[첫 uid]`). 연결한 계정은 그 레코드의 `logins: [{ uid, email, at }]` 에 둔다(첫 계정 말고 4개까지). 상태 파일 버전은 그대로(없으면 빈 목록). | 계정 표·등록부 슬롯·폐기·봉투가 모두 uid 열쇠로 돼 있다 — 열쇠를 바꾸지 않고 별칭만 더한다. |
| M2 | 래퍼 인증(`wrapperAuth`)이 토큰의 uid 를 **주인 계정**으로 바꾼다. 발급·세션 끝내기·계정 폐기·봉투가 모두 신원 단위로 동작한다. | 한 곳에서 바꾸면 경로마다 따로 고칠 것이 없다. |
| M3 | 연결(`POST /cia/wrapper/link`) 두 걸음. **begin**: 지금 계정의 토큰(요청 키₁) + `auid` + **연결 열쇠의 서명**(`link_sig` — 패스키 한 번, 아래 M3a) + 다음 요청 키₂ 의 해시(`next`)에 대한 서명. 서버는 `next → 주인` 을 10분 기억한다(메모리). **finish**: 요청 키₂ 에 묶인 **더할 계정의 토큰** + 서명. | 토큰을 브라우저 저장소에 두지 않는다(Google 을 두 번 다녀오는 사이에 남는 것은 꺼낼 수 없는 요청 키뿐이다). 재기동하면 begin 부터 다시 한다. |
| M3a | **연결 열쇠**(`lib/mode3_link_key.js`, 보안 검토 I-1): salt 에서 유도한 서명 키(secp256k1, `SHA-256("zkwrapper-link-key-v1\|" + salt)`). 브라우저는 발급 본문에 그 주소(`link_key`)를 싣고, 서버는 **등록(첫 발급) 때만** 계정에 고정한다. begin·떼기는 그 키로 요청 내용(begin: `next`, 떼기: 뗄 uid)과 서버 주소에 서명해야 한다(`link_salt_proof`). | `auid` 는 바뀌지 않는 값이고 브라우저의 등록 기록·서버에 그대로 있어, 한 번 읽히면 패스키 없이 되풀이해 낼 수 있다 — "패스키로 확인" 의 증거가 되지 못한다. 열쇠가 없는 계정(이 기능 전에 등록)은 연결을 쓰지 못한다(`link_key_missing`). |
| M4 | finish 거절: 더할 uid 가 이미 자기 계정을 갖고 있다·다른 신원에 붙어 있다(`link_has_account`), 이미 이 신원의 것이다(`link_exists`), 한도(`link_limit`), begin 이 없다·지났다(`link_not_started`). 계정을 합치지 않는다. | 합치면 두 PPID 집합 중 하나를 버려야 한다. |
| M5 | 떼기(`op: 'remove'`): 이 신원의 아무 계정 토큰 + `auid` + 뗄 uid 에 대한 서명. **첫 계정은 떼지 못한다**(`link_primary`). | 첫 uid 가 레코드의 열쇠다. 뗀 uid 는 다른 패스키로 새 신원을 만들 수 있다(Google 계정이 둘이면 원래 가능한 일이다). |
| M6 | 발급 기록(`auidSLog`) 항목에 **그 로그인에 쓴 uid**(`by` — 주인과 다를 때만)를 남긴다. 개봉은 그 uid 하나를 돌려준다(없으면 주인 uid). | 사용자 결정 3: 개봉 한 번에 드러나는 범위를 그 로그인의 계정으로 좁힌다. 뗀 뒤에도 기록은 남아 지난 로그인은 열린다. |
| M7 | 계정 폐기·관리자 폐기·삭제는 **신원 전체**다. 연결된 계정의 토큰으로 "내 계정 폐기" 를 해도 신원 전체가 폐기된다. | 사용자 결정 2. Google 계정 하나만 폐기하면 다른 계정으로 같은 PPID 를 계속 쓴다. |
| M8 | `C_u` 안의 uid 는 브라우저가 처음 등록한 값 그대로 둔다 — 어느 계정으로 로그인해도 `C_u` 가 바뀌지 않는다(바뀌면 열린 세션이 모두 폐기된다). 발급 응답에 이 신원의 uid 목록(`logins`)을 실어 브라우저가 "내 계정인지" 를 판단한다. | 값은 검사되지 않는다(§1). 브라우저마다 다른 uid 가 들어갈 수 있다. |
| M9 | 화면: `/user` 에 **"로그인 계정"** 카드(목록·"Google 계정 더하기"·"떼기"). 관리자 계정 표에 연결된 계정 수와 이메일. | |

## 4. 바뀌는 곳

- `lib/mode3_wrapper_auth.js`: `linkDigest({ op, auid?, next?, uid? }, aud)`.
- `cia.js`: `linkOwner`·`ownerOf`, `wrapperAuth`(주인으로 바꿈 + `loginUid`), `linkWrapper`(begin·finish·remove), 발급 기록의 `by`, 개봉의 uid, 발급 응답·계정 표의 `logins`.
- `mode3/user/core/user_core.js`: `wrapperLinkBegin`·`wrapperLinkFinish`·`wrapperLinkRemove`·`wrapperLogins`, "내 계정인지" 판단, 발급 응답의 `logins` 저장.
- `mode3/user/popup.js`·`idp_return.js`·`ui.js`·`index.html`·`mode3/common/strings.js`: 카드와 Google 귀로 셋.
- `mode3/cia_admin.html`: 계정 표.

## 5. 한계

- 봉투 경로(`/cia/wrapper/envelope`)와 발급은 지금처럼 `auid` 만 본다 — 브라우저 저장소의 `auid` 와 그 사람의 Google 로그인을 함께 쥔 사람은 백업을 지우거나 한도를 채울 수 있다(2026-11-24 I-1 때 받아들인 수준 그대로, 이번에 바꾸지 않았다). 연결·떼기만 연결 열쇠로 막는다.
- 연결한 Google 계정 하나의 토큰만으로(패스키 없이) 세션 끝내기·신원 전체의 계정 폐기를 할 수 있다(M7, 기존 결정 A2 — 기기를 잃었을 때 쓰는 기능). 연결한 계정 수만큼 그 길이 늘어난다.

- zkWrapper 는 연결된 Google 계정들이 같은 사람임을 안다(§2 대가 1).
- 패스키 분실 복구(salt 봉투)는 **첫 계정으로만** 된다 — 봉투와 대조값이 첫 uid 에 묶여 있다. 연결한 계정으로 새 기기에서 복구하려 하면 `recover_auid_mismatch` 로 멈춘다(백업 카드는 2026-11-25 에 화면에서 뺐다).
- begin 의 기억은 메모리다 — 서버가 재기동하면 연결을 처음부터 다시 한다.
- 실제 Google 로는 리허설하지 않았다(대역 Google 로 격리 테스트).

## 6. 테스트

- 서버(`tests/test_cia_wrapper.mjs`): begin·finish 로 연결, 연결한 계정의 발급이 같은 계정·같은 슬롯·`logins` 응답, 발급 기록의 `by` 와 개봉이 돌려주는 uid, 거절(auid 틀림·begin 없음·자기 계정 있는 uid·같은 계정 다시·한도·첫 계정 떼기·서명 목적 바꿔 쓰기), 떼기 뒤 그 계정의 발급 거절(`auid_taken`), 계정 폐기가 연결된 계정의 발급도 막는다.
- 브라우저(`tests/test_mode3_user_wrapper_browser.mjs`): `/user` 에서 더하기(Google 두 번·패스키 한 번) → 다른 계정으로 zkONE 로그인 → 같은 PPID, 떼기.

## 7. 보안 검토(2026-11-26, 독립 검토 1회)와 반영

| # | 지적 | 반영 |
|---|---|---|
| I-1 | begin 의 "패스키" 증거가 고정값 `auid` 라, Google 계정 하나 + 읽어 낸 `auid` 로 연결이 됐다. | 연결 열쇠(M3a) — begin·떼기에 salt 에서 유도한 키의 서명을 요구한다. |
| I-2 | 개봉이 로그인 uid 만 남겨, 관리자가 그 uid 로 폐기하면 404 이거나(연결된 uid) 뗀 뒤 새로 만든 다른 신원을 폐기했다. | 개봉 기록에 신원의 계정 uid(`identity`)를 따로 남기고 관리자 표에 보인다. 서비스에 주는 응답에는 없다. |
| I-3 | 떼기·신원 변화가 대기 중인 begin 을 취소하지 않았다. | 대기분에 begin 한 계정·그때의 auid 를 적고, finish 가 다시 본다. 떼면 그 계정의 대기분을 지운다. |
| M-1 | 발급과 finish 의 경합으로 한 uid 가 자기 계정이면서 다른 신원의 연결 계정이 될 수 있었다. | `registerAccount` 의 동기 구간에서 연결된 uid 의 등록을 거절한다. |
| M-2 | 발급 중에 떼어진 계정으로 세션이 하나 더 나갔다. | 발급의 두 폐기 검사 옆에서 "아직 이 신원의 계정인가" 를 함께 본다(`login_removed`). |
| M-3 | 브라우저의 낡은 목록 때문에 "내 계정 폐기" 가 이미 떼어져 다른 신원이 된 계정을 폐기할 수 있었다. | 브라우저가 폐기하려는 신원(`owner`)을 싣고 서버가 토큰의 신원과 대조한다. |
| M-4 | begin 이 같은 `next` 의 대기분을 덮어썼고, 브라우저가 받은 목록을 검사 없이 저장했다. | 같은 `next` 는 `link_pending` 으로 거절, 브라우저는 자기 uid 가 없는 목록을 저장하지 않는다. |
