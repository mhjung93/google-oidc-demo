## 1. 배경

지갑은 `/submitTransaction` 캐시 미스마다 폐기 트리를 **처음부터 다시 쌓는다.** 실측:

| 리프 수 n | insert | build 3회 | 합계 |
|---:|---:|---:|---:|
| 1,000 | 15 ms | 280 ms | 295 ms |
| 8,000 | 712 ms | 2,175 ms | 2,888 ms |
| 32,000 | 15,958 ms | 8,794 ms | **24,752 ms** |

`build()`는 리프당 0.274 ms로 선형이고, `insert()`는 리프마다 배열 전체를 정렬해 초선형이다.
증명 생성(799.61 ms)과 맞먹는 지점이 **n ≈ 2,650**, 1억 사용자·1일 1회 로그인 기준
**세션 폐기율 0.064%** 다. 메모이제이션은 손익분기를 0.128%로 2배 밀 뿐이고, 정렬 제거는
0.136%로 거의 무의미하다 — 배열 삽입의 O(n) 이동이 남기 때문이다.

**점근 복잡도를 바꾸지 않으면 1억 규모 주장이 성립하지 않는다.** 이 문서가 그 방법이다.

## 2. 현재 구현이 O(n)인 이유

`lib/imt.js`는 리프의 `next`를 **물리적 인접성**에서 유도한다:

```js
const values = [0n];                       // 정렬된 배열
nextOf(i)   = values[i + 1];               // 다음 배열 원소
leafHash(i) = H(values[i], nextOf(i));
insert(v)   → values.push(v); values.sort();
```

정렬된 배열 위치가 곧 리프 위치이므로 **중간에 삽입하면 그 뒤 모든 리프의 인덱스가 밀린다.**
그래서 전체 재구성이 필요하다. 설계의 한계가 아니라 구현의 선택이다.

## 3. 정석 IMT

`next`를 리프에 **명시적으로 저장**하고 물리적 위치는 삽입 순서대로 **append**한다.
정렬 순서는 연결 리스트로만 표현되고, 물리 위치와 분리된다.

```
leaf[i] = Poseidon(value_i, nextIndex_i, nextValue_i)
```

- 물리 인덱스 0 = anchor. 초기값 `(0, 0, 0)` — 값 0, 다음 없음(sentinel).
- `nextValue == 0` 은 "이 리프가 가장 큰 값"이라는 sentinel. 현재와 동일.
- 깊이 20 고정 → 물리 슬롯 1,048,576개. 안 쓰는 슬롯은 빈 값으로 취급하고, 레벨별 빈
  서브트리 해시(`zeros[0] = 빈 리프`, `zeros[k] = H(zeros[k-1], zeros[k-1])`)를 미리 계산해
  비어 있는 가지에 쓴다. 이게 없으면 매번 2^20개를 해싱해야 해 고정 용량이 성립하지 않는다.
- **빈 리프는 리터럴 `0`이어야 한다. `Poseidon(0, 0, 0)`으로 두면 안 된다.**
  후자로 두면 모든 빈 슬롯이 anchor `(0, 0, 0)`과 같은 모양이 되어, 아무 빈 슬롯이나 low
  리프로 제시해 `t > 0`인 **모든 값**의 비멤버십을 통과시킬 수 있다. 회로 테스트로 고정해 뒀다.

### 3.1 삽입 — O(log n)

값 `v`를 넣을 때:

1. `v`보다 작은 값 중 가장 큰 것을 가진 리프 `L`(인덱스 `i`)을 찾는다. **회로 밖 연산이다.**
2. 다음 빈 인덱스 `n`에 새 리프를 쓴다: `(v, L.nextIndex, L.nextValue)`
3. `L`을 갱신한다: `(L.value, n, v)`

바뀌는 리프는 둘(`i`, `n`)뿐이고, 각각 경로 하나씩만 다시 계산하면 된다. **O(log n).**

**root는 삽입 순서에 의존한다.** 물리 배치가 삽입 순서로 정해지므로 `[5, 3]`과 `[3, 5]`는
같은 집합이지만 **다른 root**를 만든다(비멤버십 의미는 동일하다). 따라서 IdP와 지갑이 같은
root를 얻으려면 **값 집합이 아니라 삽입 순서까지 같아야 한다.**

이것은 3.4절의 `seq` 변경 로그가 충족한다 — 지갑이 로그를 순서대로 적용하면 같은 배치가
된다. 다만 **전체 조회는 값 집합이 아니라 리프 배열을 물리 순서로 돌려줘야 한다.**
값만 주고 지갑이 알아서 쌓게 하면 다른 root가 나온다.

`rebaseline()`은 예외다 — 정렬된 순서로 쌓으므로 결과가 입력 순서와 무관하다.

### 3.2 제거는 지원하지 않는다

**언링크(앞 리프의 next를 건너뛰게 고치는 것)는 건전하지 않다.**

언링크된 리프는 여전히 Merkle 멤버이므로 low 리프로 제시할 수 있다. 리프 `j = (v, →, w)`가
리스트에서 빠진 뒤 구간 `(v, w)` 안에 새 값이 삽입되면, `j`를 써서 **그 새 값에 대한 거짓
비멤버십 증명**을 만들 수 있다. 낡은 리프가 낡은 구간을 계속 증언하기 때문이다.

리프를 0으로 지우는 것은 더 나쁘다 — `(0, 0, 0)`은 anchor와 같은 모양이라 `t > 0`인 **모든**
값에 대해 비멤버십을 통과시킨다.

따라서 **정석 IMT는 append-only다.** 이것이 Aztec의 nullifier tree가 제거를 지원하지 않는
이유이고, 우리도 같은 제약을 받는다.

### 3.3 재기준화로 회수한다

제거가 없으므로 트리 크기는 "현재 폐기 집합"이 아니라 **"역대 삽입 횟수"** 다.
회수는 **살아있는 집합만으로 트리를 새로 쌓는 재기준화**로만 가능하다.

**트리거.** 슬롯 소진이 기준이다. 깊이 20 = 1,048,576 슬롯. 사용률이 임계치(예: 80%)를
넘으면 경고하고, 그보다 높은 선(예: 95%)에서는 삽입을 거부하며 재기준화를 요구한다.
운영자가 수동으로 앞당길 수도 있어야 한다. 스트레스 조건(1억 사용자·세션 폐기율 1% →
시간당 41,700건)에서 80% 도달까지 약 20시간이고, 현실적 폐기율에서는 훨씬 길다.

**절차.** 기존 2단계 게시(prepare → pushRoot → commit)를 그대로 쓴다. 재기준화는
prepare 단계에서 "살아있는 값만으로 쌓은 새 트리"를 후보로 계산할 뿐이고, commit 전까지
기존 epoch가 계속 서빙된다. push가 확정된 뒤에만 IdP가 전진한다는 성질이 그대로 유지된다.

**epoch.** 재기준화 commit 시 epoch 번호를 올린다. 지갑은 자기 epoch와 다르면 증분이
아니라 전체를 다시 받아야 한다는 것을 이걸로 안다. 변경 로그(3.4절)도 이때 초기화된다.

**무엇이 재기준화 고유의 비용인가.** 흔히 "재기준화 순간 모든 지갑의 캐시가 죽는다"고
생각하기 쉬운데, **그건 재기준화 고유의 문제가 아니다.** 증명은 root에 묶여 있으므로
평범한 폐기 게시도 root를 바꾸는 순간 전 지갑의 캐시를 무효화한다.

재기준화에만 있는 비용은 **전체 재다운로드와 전체 재구성**이다. 증분 조회로 따라잡을 수
없고, 모든 지갑이 동시에 O(n) 전송·계산을 한다. 그래서 재기준화는 드물어야 하고,
가능하면 활동이 적은 시간대에 수행해야 한다.

재기준화 전 root로 만든 증명은 재기준화 후 무효여야 한다. `isCurrentRoot`가 최신 root
하나만 인정하므로 **이미 그렇게 동작한다** — grace를 제거해 둔 것이 여기서 맞아떨어진다.

### 3.4 변경 로그와 증분 조회

지갑이 자기 트리를 이어서 갱신하려면 "무엇이 바뀌었는지"를 받아야 한다.

**커서는 리프 인덱스가 아니라 시퀀스 번호여야 한다.** 삽입 한 번은 리프를 **둘** 바꾸는데,
새 리프는 마지막 인덱스 `n`에 쓰이지만 갱신되는 low 리프의 인덱스 `i`는 **`n`보다 훨씬
작을 수 있다.** 따라서 "인덱스 k 이후를 달라"는 요청으로는 이미 받은 구간에서 일어난
갱신을 놓친다. 리프 900을 추가하면서 리프 5가 바뀌는 일이 정상적으로 일어난다.

**구조.** IdP가 단조 증가하는 `seq`와 변경 로그를 유지한다. 리프 쓰기 하나가 로그 항목
하나다(삽입 1건 = 항목 2건).

```
로그 항목 = { seq, index, leaf }
조회      = GET /idp/revocation_state?since=<seq>
응답      = { epoch, seq, root, mutations: [...] }   // seq 오름차순
```

지갑은 `(epoch, lastSeq)`와 자기 리프 배열을 들고 있다가, 받은 변경을 seq 순서대로 적용하고
영향받은 경로만 다시 계산한다.

**전체 조회도 유지한다.** 첫 접속, epoch 불일치(재기준화 발생), 그리고 아래 절단 상황에서
필요하다.

**로그 절단.** 로그는 epoch 안에서 삽입 2배로 자란다(최악 약 200만 항목). 무한히 들고 있을
수 없으므로 상한을 두고 오래된 항목부터 버린다. 요청한 `since`가 남아있는 가장 오래된
항목보다 이전이면 증분으로 따라잡을 수 없으므로, **전체 조회를 하라고 명확히 응답한다.**
조용히 부분 결과를 주면 지갑의 트리가 root와 어긋나 모든 증명이 실패한다.

## 4. 회로 변경

리프 해시가 `Poseidon(2)` → `Poseidon(3)`으로 바뀌고 입력 신호 `lowNextIndex`가 하나 는다.
그 외 Merkle 경로 검증, 252비트 정규화·범위 검사, `LessThan` 비교, sentinel 처리는 **전부 그대로다.**

실측(컴파일해 확인):

| | 비멤버십 1개 | `pi_pk_i` 전체 | 현재 대비 |
|---|---:|---:|---:|
| 현재 | 6,627 | 19,049 | — |
| **정석 IMT** | **6,648** | **19,091** | **+0.22%** |
| (참고) 델타 분할 C@20+D@10 | — | 27,443 | +44.1% |

`nextIndex`에 범위 검사는 **불필요하다.** 비멤버십의 건전성은 "그 값들을 담은 리프가 트리
안에 있다"는 Merkle 경로가 보장하고, `nextIndex`가 틀리면 리프 해시가 달라져 경로 검증에서
걸린다. 증명에 쓰이지 않는 부수 필드다.

## 5. 건전성 — 폐기된 키가 통과할 수 없는 이유

`v`가 집합에 있으면, 연결 리스트가 정렬돼 있으므로 `L.value < v < L.nextValue`를 만족하는
리프 `L`이 **존재하지 않는다.** `v` 바로 앞 리프의 `nextValue`는 정확히 `v`이고 `v < v`는
거짓이기 때문이다. 회로가 강한 부등식을 쓰므로 `t == L.value`와 `t == L.nextValue` 모두 거부된다.

전제는 **연결 리스트가 정렬 불변식을 지킨다**는 것이고, 이는 IdP가 유지한다 — 지금과 같은
신뢰 가정이다. 3.2절이 지적한 대로 **언링크를 허용하면 이 불변식이 깨진다.**

anchor 리프 `(0, 0, 0)`은 최솟값 미만 target의 low 리프 역할을 하므로 절대 제거·변경되면
안 된다(현재와 동일).

## 6. 구성요소별 변경

### 6.1 `lib/imt.js` — 재작성

- 저장: `leaves[i] = { value, nextIndex, nextValue }` 배열 + 레벨별 해시 캐시
- `insert(v)`: low 리프 탐색 → 두 리프 갱신 → 두 경로 갱신. O(log n)
- `remove()`: **제거한다.** 지원하지 않는 연산이다
- `rebaseline(liveValues)`: 살아있는 값 집합으로 새 트리를 쌓아 반환
- `getNonMembershipWitness(target)`: `lowNextIndex`를 witness에 포함
- 레벨 캐시를 유지해 `getRoot()`가 매번 전체를 재계산하지 않게 한다
- **대량 구축 경로를 따로 둔다.** 레벨 캐시가 물질화되기 전에는 삽입 1건이 O(n)이라,
  빈 트리에 32,000건을 증분으로 넣으면 63초가 걸린다. 같은 작업을 대량 구축 경로로 하면
  3.4초다. **첫 동기화와 재기준화는 반드시 이 경로를 타야 한다.**

### 6.2 IdP (`custom_idp.js`)

- 상태 스키마 갱신: 정렬된 값 배열 → 리프 배열(`value`/`nextIndex`/`nextValue`)
  (구현 결과 상태 파일 버전은 **v4**다 — v3는 계정 층에서 이미 쓰였다)
- 변경 로그와 `since=<seq>` 증분 조회 (3.4절). 전체 조회는 유지
- epoch 번호를 상태에 포함하고 재기준화 commit 시 증가
- 재기준화를 게시 경로(prepare/commit)에 흡수 (3.3절). 만료 판정은 여기서만 쓴다
- `/idp/publish/commit`의 만료 리프 제거 로직 제거
- **predecessor 탐색용 인메모리 인덱스.** 삽입할 때 "값보다 작은 것 중 최대"를 찾아야 하는데,
  리프 배열은 물리 순서라 정렬돼 있지 않다. 정렬된 값 인덱스를 따로 두고 이진 탐색한다.
  이건 트리 밖 자료구조라 해시 계산이 없고, 삽입 시 메모리 이동만 든다 — 병목이 아니다
- **슬롯 사용률 노출.** 관리자 응답과 게시 응답에 사용/전체를 포함하고, 임계치에서 경고,
  소진 임박 시 삽입을 거부하며 재기준화를 안내한다

### 6.3 지갑 (`wallet_agent.js`)

- 트리와 `(epoch, lastSeq)`를 **요청 간에 캐시**한다. 지금은 캐시 미스마다 새로 만든다
- `since=lastSeq`로 변경분만 받아 적용. **epoch가 다르거나 "너무 오래됨" 응답을 받으면**
  전체를 다시 받는다
- witness에 `lowNextIndex` 추가

### 6.4 회로·배포

- `circuits/lib/imt_nonmembership.circom`: 리프 해시 3-입력, `lowNextIndex` 입력 추가
- `circuits/pi_pk_i.circom`: witness 필드 추가에 따른 배선
- **`zk:compile`·`zk:key` 재실행 필요** → `PiPkIVerifier` 재배포 → factory 재배포 →
  CREATE2 지갑 주소 변경. 명시적 승인이 필요한 항목이다

## 7. 기대 효과

| | 현재 | 정석 IMT |
|---|---|---|
| 지갑의 트랜잭션당 비용 | **O(n) 전체 재구성** | O(log n) 증분 |
| 무거운 재구성 빈도 | 캐시 미스마다 | 재기준화마다(수십 시간) |
| 회로 제약 | 19,049 | 19,091 (+0.22%) |
| root 개수 | 1 | 1 (변경 없음) |
| 새 공격면 | — | 없음 |

2절의 손익분기(세션 폐기율 0.064%)가 소멸한다.

**실측 (2026-09-02, `scripts/bench_imt_v2.mjs`, node v22.20.0).** 폐기 1건이 더 게시됐을 때
지갑이 트랜잭션마다 치르는 비용(insert + root + witness, ms 평균):

| n | v1(제거된 경로) | **v2** | 배율 |
|---:|---:|---:|---:|
| 1,000 | 179.3 | **1.984** | 90x |
| 8,000 | 1,428.9 | **2.024** | 706x |
| 32,000 | 5,754.5 | **1.973** | **2,917x** |

n을 32배 늘려도 v2는 1.984 → 1.973 ms로 **평평하다(0.99x)**. 같은 구간에서 v1은 32.1배로
커진다. 콜드 구성 비용(재기준화·첫 동기화에서만 치른다)은 n=32,000에서 19,007 ms →
3,373 ms로, 6.1절이 요구한 대량 구축 경로가 실제로 동작함을 보인다.

## 8. 검증 계획

1. `lib/imt.js` 단위: 삽입 후 root가 전체 재구성 결과와 **일치**(증분 갱신의 정확성)
2. **같은 순서**로 증분 삽입한 트리와 전체 구축한 트리의 root 일치.
   (삽입 순서가 다르면 root도 달라지는 것이 정상이다 — 3.1절. 그것도 함께 단언해
   "집합만 같으면 된다"는 오해를 막는다)
3. 폐기된 값에 대해 witness를 얻을 수 없음(현재 테스트 유지)
4. **회로 반례**: 언링크된 낡은 리프를 low 리프로 제시하는 시나리오가 실제로 위험함을
   문서화용으로 재현(제거를 지원하지 않는 근거)
5. 재기준화 후 옛 root 증명이 온체인에서 거부되는지
6. 성능 회귀: n = 1,000 / 8,000 / 32,000에서 트랜잭션당 비용이 O(log n)으로 떨어지는지 실측
7. 전 구간 E2E(`tests/test_mode2_e2e_onchain.js`) 통과

## 9. 남은 위험

- **`nextIndex`가 회로에서 검증되지 않는다.** 4절대로 건전성에는 무관하지만, 지갑이
  잘못된 `nextIndex`를 넣으면 리프 해시가 어긋나 증명이 실패한다. 진단 메시지가 필요하다
- **재기준화가 새로운 운영 작업이다.** 슬롯 소진을 감시하지 않으면 삽입이 실패한다.
  잔여 슬롯을 노출하고 임계치 경고가 필요하다
- **재기준화 순간 모든 지갑이 전체 재다운로드·재구성을 한다.** 동시 요청이 IdP·미러에 몰린다.
  (캐시 무효화 자체는 재기준화 고유 문제가 아니다 — 평범한 폐기 게시도 root를 바꾸면
  전 지갑의 증명 캐시를 무효화한다. 3.3절 참조)
- **변경 로그가 메모리를 쓴다.** epoch 안에서 삽입 2배로 자라며, 절단하면 뒤처진 지갑이
  전체 조회로 떨어진다. 상한을 어디에 둘지는 실측으로 정해야 한다
- zkey 재생성으로 기존 증명·키가 무효화된다. 되돌릴 수 없다
- 이 문서는 depth 20 고정을 전제한다. 재기준화가 회수를 담당하므로 깊이를 늘릴 필요는
  당분간 없지만, 슬롯 소진 주기가 짧아지면 재검토 대상이다
