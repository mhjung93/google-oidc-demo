# Mode 3 — 추적 방식 셋의 비교, 그리고 zkLogin 과의 비교 (정리, 2026-11-26)

- 배경(피드백 2026-11-26): "trace tag version, PPID smart account version, no tag version 과 다 비교하여 장단점 정리", "비교할 거면 zkLogin 처럼 web3 protocol 과 비교".
- 대상 방식: zkWrapper(Google 계정 + 패스키, 발급에 π_IdP 없음)를 기준으로 쓴다. 옛 trace tag 방식은 zkIdP(π_IdP 있음) 때의 설계다 — 그 차이는 표에 적었다.
- 수치의 출처를 칸마다 밝힌다. **"추정" 이라 적은 값은 재지 않은 것이다.**

### 장단점

**A. trace tag 방식**
- 장점: 개봉이 암호로 강제된다(두 조각이 모여야 한다). 발급자가 기록을 남기지 않아도 된다. 로그인만 한 사용자도 같은 방식으로 열린다.
- 단점: 로그인·거래마다 회로와 가스 비용이 든다. 서비스마다 키 조각을 영구 보관해야 하고 하나만 잃어도 과거를 못 연다. 발급자와 서비스가 담합하면 그 서비스 사용자 전부가 열린다. 사용자는 개봉을 알 수 없다. zkWrapper 에는 그대로 못 쓴다.

**B. 태그 없음**
- 장점: 회로·거래가 가장 가볍다. 키 조각이 없다. 구현이 가장 단순하다(지금 돌아간다).
- 단점: zkWrapper 가 혼자 연다 — "조건부 익명성" 이 절차에만 기댄다. zkWrapper 가 체인의 거래를 자기 기록과 맞춰 "누가 어느 서비스를 쓰는지" 를 알 수 있다. 기록이 차거나 지워지면 열 수 없다. 사용자는 개봉을 알 수 없다.

**C. PPID 계정 방식**
- 장점: 로그인·거래의 비용은 B 와 같고 추적 기록은 PPID 마다 한 번이다. 어느 한 당사자도 혼자 열지 못한다(감사자 위원회 + zkWrapper). 개봉이 체인의 요청을 거쳐 **사용자가 안다**. 발급 기록을 없앨 수 있어 B 의 "발급자가 서비스 이용을 안다" 를 줄일 길이 생긴다. 조각 하나를 잃어도 된다.
- 단점: 감사자 위원회라는 새 당사자와 키 관리가 필요하다(누가 맡는가는 정책 문제로 남는다). 서비스마다 첫 로그인에 증명 한 번과 거래 한 번이 든다. 알림은 감사자 과반이 정직할 때만 보장된다. 개봉 요청 이벤트가 공개라 "이 PPID 가 조사받는다" 가 모두에게 보인다. 개봉 뒤에는 zkWrapper 가 그 신원을 계속 알아본다. 새 회로·컨트랙트·감사자 프로세스가 필요하다(구현 안 됨).

**정리**: 비용만 보면 B, 개봉의 강제만 보면 A·C, 사용자에게 알림까지 요구하면 C 뿐이다. A 는 zkWrapper 구조(π_IdP 없음)와 맞지 않아 되살리려면 발급 구조부터 바꿔야 한다.
C 는 A 의 2-of-2 를 "발급자·서비스 밖의 감사자 2-of-3" 으로 옮기고 태그를 거래에서 계정으로 옮긴 것이다 — 2026-09-16 스펙이 "범위 밖" 으로 남겼던 항목(§8 한계 3)에 해당한다.

## 2부. zkLogin 과의 비교

zkLogin(Sui)과 zk-Delegation(zkWrapper 방식)은 둘 다 "Google 로그인을 블록체인 계정의 권한으로 바꾼다". 푸는 문제의 범위가 다르다.

> zkLogin 칸의 출처: 수치는 논문 v8 초안에 정리해 둔 값(arXiv 2401.11735 §5·Table 3 메모 — `docs/paper/zkd/v8_comparison_draft.md`, CCS'24 판과의 대조는 아직 안 했다)이고,
> 구조 설명은 공개 문서 기준이다. **이 정리를 쓰면서 원문을 다시 확인하지 않았다** — 발표·논문에 쓰기 전에 원문 대조가 필요하다.

| | zkLogin | zk-Delegation (zkWrapper 방식) |
|---|---|---|
| 목표 | OIDC 로그인으로 체인 계정을 쓴다(지갑 키 없이) | 같은 것 + 서비스마다 다른 가명·발급자에게 서비스 숨김·폐기·조건부 개봉 |
| 계정 주소 | 발급자·클라이언트 ID(`aud`)·`sub`·salt 에서 유도 — **클라이언트(지갑·앱)마다 하나** | `PPID = Poseidon(salt, arid, chainid)` — **서비스마다 하나**, 스마트 계정(EVM) |
| 증명이 보이는 것 | "이 JWT 는 발급자의 RSA 서명이 맞고, nonce 가 이 임시 키를 가리키며, 주소가 이 JWT·salt 에서 나온다" — JWT 검증을 회로 안에서 한다 | "발급자(zkWrapper)가 서명한 자격증명이 있고, 등록부에 있으며 폐기되지 않았고, PPID 가 그 salt 의 것이다" — Google 토큰 검증은 zkWrapper 가 회로 밖에서 한다 |
| 회로 크기·증명 시간 | 약 100만 R1CS, rapidsnark 로 2.1 s(16 vCPU 서버), 증명 획득 2.78 s ² | 30,866 제약, 브라우저·snarkjs 로 약 1 s(중앙값 973.7 ms ¹) |
| 증명을 만드는 곳 | 보통 증명 서비스(서버) — 그 서버는 JWT 와 salt 를 본다. 직접 만들 수도 있다 | 사용자 브라우저(비밀이 브라우저 밖으로 나가지 않는다) |
| salt | salt 서비스가 JWT 를 받고 내주거나 사용자가 보관 | 패스키에서 유도(저장하지 않는다). 서버는 모른다 |
| 표준 Google 그대로 되는가 | **된다** — 발급자를 바꾸지 않는다 | Google 은 그대로지만 **중간 발급자(zkWrapper)가 필요하다** |
| Google 이 아는 것 | 누가(`sub`) 어느 클라이언트(`aud`)에 로그인하는지 | 누가 zkWrapper 에 로그인하는지 — 어느 서비스인지는 모른다 |
| 중간 당사자가 아는 것 | salt 서비스·증명 서비스: JWT(사용자 식별), 주소 | zkWrapper: Google 계정(`sub`·이메일). 로그인 때는 어느 서비스인지 모른다(가명 `arid_s`). 체인에 거래를 내면 발급 기록으로 이을 수 있다(1부 B) |
| 서비스·앱이 아는 것 | 주소. 한 지갑으로 여러 앱을 쓰면 같은 주소가 보인다 | 그 서비스 전용 PPID 와 증명. 다른 서비스의 PPID 와 이어지지 않는다 |
| 체인에서 보이는 것 | 발급자(`iss`)와 주소, 증명 | `arid`(서비스), PPID, 세션 가명(`auid_s`), 증명 |
| 세션 | 임시 키 + 만료 epoch. 만료 전 폐기 없음 | 세션키 + 만료 블록. **세션·계정을 만료 전에 폐기**(폐기 목록 root 가 증명의 공개 입력) |
| 조건부 개봉(문제가 생겼을 때 신원 확인) | 없다 | 있다(1부 — 지금은 B, 설계는 C) |
| 속성 조건(나이·국가 등) | 없다 | 있다 — 값은 숨기고 조건만 증명(자기 신고 속성) |
| 검증하는 곳 | 체인의 프로토콜이 직접(검증 비용이 낮다 — 서명 하나당 약 2 ms ²) | EVM 스마트 계정이 Groth16 검증(가스 — 옛 회로 V10 에서 execute 455,947 gas, **지금 회로로는 다시 재지 않았다**) |
| 신뢰해야 하는 것 | 발급자의 키(JWK 를 체인이 받아 둔다), salt 서비스(쓰면), 증명 서비스(쓰면) | zkWrapper(발급·등록부·폐기 목록 게시 — 게시가 멈추면 로그인이 멈춘다), 서비스의 릴레이(거래 전달) |
| 사용자가 준비할 것 | 없다(Google 계정) | 패스키 하나 |

² 논문 v8 초안의 메모(위 출처 주의).

### 읽는 법

- **zkLogin 이 나은 곳**: 발급자를 바꾸지 않는다(중간 당사자 없이 표준 Google 로 된다). 체인이 직접 검증해 거래 비용이 낮다. 사용자가 준비할 것이 없다.
- **zk-Delegation 이 나은 곳**: 서비스마다 다른 주소라 서비스끼리 맞대도 같은 사람임을 모른다. Google 이 어느 서비스인지 모른다. 증명이 작아 브라우저에서 만든다(JWT·salt 를 증명 서버에 주지 않는다). 폐기·조건부 개봉·속성 조건이 있다.
- **치르는 값**: 중간 발급자(zkWrapper)를 믿어야 하고 그것이 Google 계정을 안다. 패스키가 필요하다. EVM 에서 검증 가스를 낸다.
- **같은 축으로 재지 않은 것**: 증명 시간은 하드웨어·증명기가 다르다(16 vCPU 서버의 rapidsnark 대 데스크톱 브라우저의 snarkjs). 회로 크기 차이(약 100만 대 3만)는 "JWT 의 RSA 검증을 회로 안에서 하느냐" 에서 온다 — zk-Delegation 은 그 검증을 zkWrapper 에게 맡긴 대가로 작다.
