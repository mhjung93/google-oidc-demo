## 1. 한 줄

PPID 마다 **한 번**, `Enc_{pk_aud}(auid)` 를 체인의 등록부 컨트랙트에 남긴다(작은 증명 π_trace 로 올바름을 보인다). 개봉은 누군가 그 컨트랙트에 **개봉 요청 거래**를 내야만 시작되고,
그 거래의 이벤트를 사용자 화면이 받아 알린다. 감사자 키는 셋으로 나눠 둘이 모여야 열린다 — 정직한 감사자는 체인의 요청을 본 뒤에만 자기 조각을 쓴다.

## 2. 먼저 짚을 사실

1. **"읽으면 알림" 은 그대로는 불가능하다.** 체인에 올린 값은 누구나 흔적 없이 읽는다. 복호는 체인 밖에서 일어난다. 알릴 수 있는 것은 "복호 절차가 시작됐다" 이고,
   그것이 보장되려면 복호가 **반드시** 체인의 요청을 거쳐야 한다 — 그래서 키를 나눈다(§5). 키가 하나면 알림은 그 감사자의 약속일 뿐이다.
2. **zkWrapper 에서는 `Enc(uid)` 를 검증할 수 없다.** uid 는 `C_u = Commit(uid, s_u, blind_u, attrs)` 안에만 있고, zkWrapper 는 π_IdP 가 없어 그 값을 보지 않는다(점이 유효한지만 본다).
   사용자가 아무 uid 나 넣어 암호화해도 회로가 잡지 못한다. 반면 `auid = Poseidon(D, s_u)` 와 `PPID = Poseidon(s_u, arid, chainid)` 는 같은 salt 에서 나온다 — 회로 하나로 묶인다.
3. **그래서 `auid` 를 암호화한다**(결정 ①). 개봉은 두 단계가 된다: 감사자들이 복호 → `auid`, zkWrapper 가 `auid →` Google 계정. 어느 한쪽도 혼자 열지 못한다.
   `Enc(uid)` 로 하려면 발급 때 uid 를 검증하는 증명(π_IdP)을 zkWrapper 에 되살려야 한다(기각 — §8).

## 3. 당사자와 키

| 당사자 | 갖는 것 | 하는 일 |
|---|---|---|
| 감사자 A₁·A₂·A₃ | Baby Jubjub 위 임계 키의 조각 `x_i`(Shamir 2-of-3). 공개키 `pk_aud = x·B8` 는 등록부 컨트랙트에 고정 | 체인의 `OpenRequested` 를 본 뒤에만 부분 복호 `D_i = x_i·c1` 과 그 올바름의 증명(DLEQ)을 낸다 |
| zkWrapper | 계정 표(`auid ↔` Google 계정들) | 부분 복호를 모아 `auid` 를 얻고(조합자) 계정을 찾는다. 감사자 조각은 갖지 않는다 |
| 서비스 | 자기 `arid`, 서비스 키 | 자기 PPID 에 대해서만 개봉을 요청한다 |
| 사용자 브라우저 | salt(패스키) | 첫 로그인 때 π_trace 를 만들어 기록을 남긴다. 자기 PPID 의 `OpenRequested` 를 지켜본다 |

- 키 생성: 데모는 한 번의 딜러(조각을 만들어 나눠 주고 버린다). 실제 운영은 분산 키 생성(DKG) — 범위 밖.
- 감사자가 누구인가는 정책이다(예: 규제 기관·서비스 연합·제3의 감사 법인). zkWrapper 와 서비스는 조각을 갖지 않는 것이 요점이다(지금의 "zkWrapper 혼자 연다" 를 없앤다).

## 4. 기록 남기기

### 4.1 암호문 (옛 TraceTag 와 같은 모양, 평문만 다르다)

```
c1 = ρ·B8                      ρ ∈ [1, 2^250)
K  = ρ·pk_aud
c2 = auid + Poseidon(K.x, K.y)
기록 = (PPID, arid, c1, c2)
```

### 4.2 회로 π_trace (새 회로, PPID 마다 한 번)

```
비공개  s_u, ρ
공개    PPID, arid, chainid, pk_aud(x, y), c1(x, y), c2
제약    PPID = Poseidon(s_u, arid, chainid)
        auid = Poseidon(DOMAIN_MODE3_AUID, s_u)
        ρ ≠ 0,  c1 = ρ·B8,  K = ρ·pk_aud,  c2 = auid + Poseidon(K.x, K.y)
```

- 등록부 멤버십·폐기는 여기서 보지 않는다. PPID 가 salt 를 정하므로(다른 salt 로 같은 PPID 를 만들 수 없다) "이 PPID 의 주인의 auid" 는 회로가 보증하고, 그 salt 가 등록된 신원인지는 로그인·거래의 π_RP 가 본다.
- 크기: 옛 `TraceTag`(`circuits/lib/mode3_trace_tag.circom` — 스칼라 곱 둘 + Poseidon)에 Poseidon 둘을 더한 정도. **재지 않았다** — 옛 태그가 π_cred 에 더하던 몫(수천 제약)과 비슷할 것으로 본다(§9 에서 잰다).
- `pk_aud` 는 공개 입력이고 컨트랙트가 자기 값과 대조한다(대조하지 않으면 사용자가 자기 키로 암호화한다 — 옛 `pk_trace` 와 같은 이유).

### 4.3 컨트랙트 `TraceRegistry` (응용 체인마다 하나)

```
register(ppid, arid, c1, c2, proof)      π_trace 검증, 이미 있으면 거절, 저장, emit TraceRegistered(ppid, arid)
has(ppid) → bool
requestOpen(ppid, reasonHash) → id       msg.sender 가 그 arid 의 서비스(또는 정책이 허용한 요청자)인지 확인, emit OpenRequested(id, ppid indexed, requester, reasonHash)
noteShare(id, auditorIndex, shareHash)   감사자가 부분 복호를 냈다는 표시(조각 자체는 체인에 올리지 않는다), emit ShareSubmitted(id, auditorIndex)
```

- **언제 남기나: 그 서비스의 첫 로그인 때.** 서비스는 로그인 검증에 `has(PPID)` 를 더하고, 없으면 브라우저가 π_trace 를 만들어 서비스의 릴레이가 `register` 를 보낸다(계정 배포를 대신 보내는 것과 같은 길).
  `Mode3WalletFactory.deploy` 도 `has(PPID)` 를 요구한다. 계정 배포 때만 남기면 거래 없이 로그인만 하는 사용자는 추적 기록이 없다.
- 같은 증명을 남이 다시 내도 같은 기록이 남을 뿐이다(증명이 PPID·암호문에 묶여 있다).
- 로그인·거래의 π_RP 와 `Mode3Wallet.execute` 는 바꾸지 않는다 — 태그는 거래에 실리지 않는다.

## 5. 개봉과 알림

```
1. 서비스      TraceRegistry.requestOpen(PPID, H(사유))                 → 이벤트 OpenRequested(id, PPID, 요청자, H(사유))
2. 사용자 화면  응용 체인의 OpenRequested 를 주기적으로 읽어 자기 PPID 와 견준다  → "zkONE 계정에 개봉 요청이 있었습니다(시각·요청자)"
3. 감사자 Aᵢ    이벤트를 보고 사유를 심사(체인 밖 정책) → D_i = x_i·c1 + DLEQ 증명을 조합자(zkWrapper)에게, noteShare(id, i, H(D_i))
4. zkWrapper   조각 둘을 검증·조합: K = λ_a·D_a + λ_b·D_b,  auid = c2 − Poseidon(K.x, K.y)  → 계정 표에서 그 신원의 Google 계정 → 요청자에게(정책대로)
```

- **알림의 보장**: 감사자 셋 중 둘 이상이 "체인의 요청 없이는 조각을 쓰지 않는다" 를 지키면, 알림 없는 개봉은 없다. 둘이 체인 밖에서 담합하면 알림 없이 `auid` 를 얻는다(그래도 Google 계정까지 가려면 zkWrapper 의 표가 필요하다).
- **사용자 화면이 지켜보는 방법**: 브라우저는 체인을 직접 읽는다(zkWrapper 를 거치지 않는다). PPID 로 걸러 달라고 노드에 묻지 않고 **이벤트 전체를 받아 브라우저에서 거른다** — 노드가 "이 IP 가 이 PPID 를 지켜본다" 를 알지 못하게.
- **이의 기간(선택)**: 감사자가 요청 뒤 N 블록을 기다렸다가 조각을 내게 하면, 사용자가 알림을 받고 이의를 낼 시간이 생긴다. 정책이라 이 문서는 값만 열어 둔다.
- 드러나는 범위: 한 번의 개봉은 그 PPID(그 서비스의 그 계정) 하나의 `auid` 다. 같은 사람의 다른 서비스 PPID 는 암호문이 따로라(ρ 가 다르다) 따로 요청해야 한다 — 다만 zkWrapper 가 `auid` 를 알게 된 뒤에는 §6 의 한계 3 이 적용된다.

## 6. 보장과 한계

1. **zkWrapper 혼자 열지 못한다.** 지금(태그 없음)은 발급 기록(`auid_s → uid`)으로 zkWrapper 가 체인의 거래를 혼자 이을 수 있다. 이 설계에서는 그 기록을 없앨 수 있다(§7).
2. **서비스 혼자, 감사자 하나 혼자 열지 못한다.** 감사자 둘 + zkWrapper 가 모여야 Google 계정까지 간다.
3. **개봉 뒤에는 zkWrapper 가 그 신원을 안다.** `auid` 는 신원마다 하나라, zkWrapper 는 그 사용자의 이후 발급도 알아본다(발급 요청에 `auid` 가 있다). 개봉은 되돌릴 수 없다.
4. **요청 이벤트는 모두에게 보인다.** "이 PPID 가 조사받는다" 가 공개된다. 숨기려면 이벤트에 `H(PPID, nonce)` 만 싣고 사용자가 맞춰 보게 할 수 있지만 요청자가 nonce 를 사용자에게 줄 길이 없다 — 하지 않는다.
5. **감사자 둘의 담합은 알림을 우회한다.** 임계값을 올리면(3-of-5 등) 줄지만 없어지지 않는다.
6. **조각 둘을 잃으면 과거 기록은 영원히 열리지 않는다**(하나는 잃어도 된다 — 2-of-2 태그보다 낫다).
7. **첫 로그인이 느려지고 거래가 하나 든다**: π_trace 한 번(브라우저)과 `register` 거래 한 번(서비스 릴레이가 낸다 — 누가 가스를 내는지는 서비스 정책).
8. **조합자가 zkWrapper 라는 점**: 감사자는 조각만 내고 `auid` 를 보지 않는다. 대신 zkWrapper 가 조각을 받고도 결과를 안 줄 수 있다(가용성) — 감사자 둘이 직접 조합하면 `auid` 까지는 얻는다.

## 7. 함께 바꿀 수 있는 것 (이 설계가 여는 선택)

- **발급 기록(`auidSLog`)을 없앤다.** 개봉이 그 기록에 기대지 않으므로, zkWrapper 는 "어느 가명을 누구에게 냈는지" 를 남기지 않아도 된다(2026-11-19 T6 을 되돌린다). 계정당 5,000개 상한·`auid_log_full` 도 사라진다.
- **π_RP 의 공개 입력에서 `auid_s` 를 뺄 수 있다.** 지금은 개봉의 열쇠라 공개다. 빼면 zkWrapper 가 자기가 서명한 가명을 체인에서 찾아 "이 사람이 이 서비스를 쓴다" 를 알아내는 길이 닫힌다(2026-11-19 스펙 §3 의 대가). 회로 재빌드가 필요하고, 서비스의 ID 토큰 대조(sub = auid_s)와 엮여 있어 따로 설계해야 한다 — 열린 항목.

## 8. 기각한 안

- **`Enc(uid)`**: zkWrapper 에 π_IdP(발급마다 약 0.3 s, 회로·키 배포)를 되살려야 uid 를 묶을 수 있다. 얻는 것은 "감사자만으로 Google 계정이 나온다" 인데, 그것은 zkWrapper 없이 열린다는 뜻이라 오히려 한 당사자(감사자 위원회)에게 권한이 모인다.
- **거래마다 태그(옛 방식)**: 비교 문서 참고 — 거래마다 회로·가스 비용이 들고 알림을 걸 곳이 없다.
- **감사자 하나**: 알림이 강제되지 않는다(§2-1).
- **조각을 체인에 올려 컨트랙트가 조합**: Baby Jubjub 연산을 EVM 에서 하면 비싸고, 조합 결과(`auid`)가 공개된다.

## 9. 구현한다면 (범위와 순서 — 승인 필요)

1. 회로 `circuits/pi_trace.circom` + 빌드(zkey·vkey·wasm·`TraceVerifier.sol`). **회로 컴파일·키 생성은 사용자 승인 뒤에만**(CLAUDE.md). 제약 수·증명 시간·`register` 가스를 잰다.
2. 컨트랙트 `TraceRegistry.sol`, `Mode3WalletFactory.deploy` 의 `has(PPID)` 검사, 배포 스크립트. 기존 배포는 무효 — 데모 재배포.
3. 브라우저: 첫 로그인의 π_trace·`register`(서비스 릴레이 경로), `/user` 의 개봉 알림 카드(이벤트 읽기·거르기).
4. 서비스: 로그인 검증의 `has(PPID)`, 개봉 요청 화면이 `requestOpen` 거래를 낸다.
5. 감사자: 데모용 프로세스 하나가 조각 셋을 따로 들고(파일 셋, 0600) 이벤트를 본 뒤에만 부분 복호 — "한 프로세스가 셋을 흉내 낸다" 를 화면·문서에 밝힌다.
6. zkWrapper: 조합·계정 찾기, `auidSLog` 제거(§7 — 따로 결정).
7. 테스트: 회로 증인(올바른 암호문·틀린 auid·틀린 pk_aud·ρ=0), 컨트랙트(중복 등록·남의 arid 요청), 임계 복호(둘이면 열리고 하나면 안 열림·틀린 조각의 DLEQ 거절), 브라우저(첫 로그인 등록·알림).

- 서비스(`mode3_rp.js`): 로그인의 `has(PPID)` 검사 — 없으면 **로그인 요청에 실려 온 기록**(`trace`)을 π_RP 확인 뒤 릴레이어가 올린다(`registerTrace`; 기록도 없고 실려 오지도 않으면 `trace_required`). 릴레이(`/api/mode3/relay`)도 같은 검사를 한다. `POST /api/mode3/trace/open`(관리자 — 자기 서비스 계정만, 사유 필수 — 체인의 개봉 요청).
- zkWrapper(`cia.js`): 설정의 `trace.registry`·`trace.pk`(감사자 키 — 이 서버가 자기 노드에서 읽어 고정), 관리자 `GET /cia/admin/trace/requests`·`POST /cia/admin/trace/:id/open`(체인에 표시를 남긴 감사자 둘의 부분 복호를 확인·조합 → 계정).
- 브라우저: 로그인 중 `buildTrace`(기록이 없으면 설정의 감사자 키로 π_trace 를 만들어 로그인 응답에 싣는다), `/user` 의 "개봉 알림" 카드(체인의 요청을 읽어 자기 PPID 로 거른다, 10초마다), 서비스 관리자·zkWrapper 관리자 화면의 버튼·목록.
- 체인 콘솔(`scripts/mode3_console.mjs`): `traceRecord`·`traceRequest`·`traceRequests` — 버튼 없이 기록을 읽고 개봉 요청 거래를 낸다. 탐색기 자동 검증 대상에 `TraceRegistry`·`TraceVerifier`. "로그인 전체 플로우" 에 추적 기록 단계.
- 분리 데모(`scripts/demo_split_start.sh`): zkwrapper 방식이면 등록부를 올리고 감사자를 띄운다(`TRACE=0` 으로 끈다, 산출물이 없으면 건너뛴다).

**설계와 다른 것**
1. **계정 배포(`Mode3WalletFactory.deploy`)는 기록을 요구하지 않는다.** 기록을 강제하는 곳은 서비스의 로그인 검사뿐이다(§4.3 은 팩토리도 요구한다고 적었다). 팩토리·지갑 컨트랙트를 바꾸면 주소 계산·참조 코드 대조·기존 테스트가 모두 바뀌어 이번에는 손대지 않았다 — 서비스를 거치지 않고 팩토리를 직접 부르면 기록 없는 계정이 생길 수 있다.
2. **개봉 요청(`requestOpen`)은 아무나 낼 수 있다.** 서비스에는 체인 위의 신원이 없어 컨트랙트가 가르지 않는다 — 요청자 주소와 사유의 해시가 이벤트에 남고, 받아들일지는 감사자의 몫이다. 데모의 감사자는 **요청을 보면 바로 응답한다**(`MODE3_AUDITOR_AUTO=0` 이면 사람이 승인).
3. **감사자는 한 프로세스다.** 조각 파일 셋을 한 디렉터리(`.local/auditors`)에 두고 한 프로세스가 셋을 흉내 낸다 — "둘이 담합하면 알림 없이 연다" 를 데모가 막아 주지는 않는다. 기본은 1·2번만 응답한다(셋 중 둘이면 열린다는 것을 보이려고).
4. **발급 기록(`auidSLog`)은 그대로 있다.** 지금의 개봉(서비스가 증명을 내고 zkWrapper 가 기록에서 찾는 길)도 그대로 동작한다 — §7 의 "기록을 없앤다" 는 하지 않았다. 두 길이 함께 있는 동안에는 "zkWrapper 혼자 열지 못한다" 가 성립하지 않는다.
5. 이의 기간(§5)은 없다.

6. **알림의 범위는 이 브라우저로 로그인한 서비스다.** 지켜보는 PPID 는 체인에서 기록을 확인하고 적어 둔 것과 지금 세션의 것이다 — 새 브라우저에서 신원을 되찾으면, 그 브라우저로 다시 로그인하기 전의 서비스에 온 요청은 보이지 않는다.
7. **체인에 "이 PPID 의 기록이 있나" 를 묻는 조회가 서비스마다 한두 번 나간다.** 그 조회를 받는 노드는 그 IP 와 PPID 를 이을 수 있다(§5 가 알림 조회에서 피하려던 것). 확인한 뒤에는 묻지 않는다.

**독립 검토(2026-11-26, Opus — Critical 0·Important 4·Minor 8)와 반영**: 회로·임계 복호·컨트랙트의 결속에서는 깨지는 곳이 나오지 않았다(남의 PPID 로 등록·주인의 auid 가 아닌 암호문·틀린 auid 로 조합 모두 막힘). 고친 것:
- I-1 기록 등록을 따로 열린 엔드포인트에서 **로그인 안**으로 옮겼다 — π_trace 는 등록된 사용자인지 보지 않으므로, 열려 있으면 무작위 `s_u` 로 만든 증명마다 릴레이어의 가스가 나갔다.
- I-2 브라우저는 **zkWrapper 설정에 고정된 감사자 키**로만 잠근다 — 자기 RPC 가 준 키로 잠그면 그 노드가 제 키를 내밀어 `auid` 를 읽을 수 있었다.
- I-3 감사자 HTTP 는 **토큰**(조합자와 나눠 갖는다)과 Host 검사를 거친다 — 부분 복호 둘과 공개키만 있으면 누구나 조합할 수 있으므로, 같은 PC 의 다른 프로세스나 브라우저가 연 페이지가 읽거나 승인을 누르지 못하게 했다.
- I-4·M-6 **전제로 적는다**: 감사자는 자기 노드가 보여 주는 체인을 믿는다 — 노드가 요청·기록을 꾸미면 알림 없는 부분 복호가 나가고, 재편성되면 조각은 나갔는데 알림은 사라진다. 운영이라면 감사자마다 자기 노드를 쓰고 확정을 기다린다(`MODE3_AUDITOR_CONFIRMATIONS`, 데모 기본 0). 데모는 노드의 개발 계정으로 거래를 내므로, 노드의 RPC 에 닿는 누구나 감사자·서비스의 주소로 거래를 낼 수 있다.
- M-1 릴레이도 기록을 요구한다. M-2 요청 목록은 최근 200건만 읽고 화면 갱신을 막지 않는다. M-3 부분 복호의 증명을 요청(체인·등록부·번호)에 묶고, 조합자는 체인에 표시를 남긴 감사자의 조각만 쓰며 맞는 쌍을 모두 시도한다. M-4 개봉 요청은 사유 필수·자기 서비스의 계정만. M-5 키 파일이 일부만 있으면 배포가 멈추고(`MODE3_AUDITOR_REDEAL=yes` 일 때만 새로), 감사자는 조각이 공개 기록과 짝인지 확인한다. M-7·M-8 은 위 6·7.
- 고치지 않은 것: 요청을 아무나 낼 수 있어 요청마다 감사자가 표시 거래를 둘 낸다(요청 스팸의 비용). `shareHash` 는 체인에 남기만 하고 조합자가 대조하지 않는다(부분 복호의 증명은 매번 새 난수라 감사자가 다시 뜨면 값이 달라진다).

**가스**(2026-11-26, 임시 hardhat 체인, 일회용 측정 스크립트 — 저장소에 없다): `register` 383,903~383,915(n=5 — Groth16 검증 + 저장 5칸), `requestOpen` 121,853~138,953(n=5 — 첫 요청이 가장 크다), `noteShare` 39,458~39,470(n=10). 계정마다 한 번 드는 것은 `register` 뿐이고, 나머지는 개봉할 때만 든다(요청 1 + 표시 2).
