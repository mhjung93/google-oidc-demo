## 2부. 계정 자기 폐기 (평가 4-가)

상태: **구현됨**(`c076682`) — 버튼은 홈이 아니라 `/user` 의 "보관 상태" 카드에 있다(§1.2a A1).

### 2.1 지금

- 서버는 **이미 된다**: `cia.js:2290` `/cia/account/self_revoke` 의 `WRAPPER` 분기가 1회용 요청 키에 묶인 Google 토큰과 `revokeDigest({ scope: 'account' })` 에 대한 서명을 받아 계정을 폐기한다
  (`lib/mode3_wrapper_auth.js:58`, 토큰 1회 소비). 처리는 관리자 계정 폐기와 같은 `revokeAccount` 다.
- 화면만 없다: `ui.js:94-95` 가 zkWrapper 에서 "계정 자기 폐기" 버튼(비밀번호를 묻는 옛 버튼)을 숨기고 "계정 폐기는 zkWrapper 관리자에게 요청합니다" 를 둔다(11-21 최종 검토 I-1 의 임시 조치).
- 같은 구조의 클라이언트가 이미 있다: 세션 끝내기 `wrapperRevokeSession`(`mode3/user/core/user_core.js:1180` 부근, `29850b1`) — 홈이 Google 을 다녀온 뒤 `wrapperBegin` 의 요청 키로 서명해 `/cia/revoke` 를 부른다. 패스키를 쓰지 않는다.

## 3부. 패스키 분실 복구 (평가 4-나)

상태: **구현됨**(브랜치 `feat/mode3-v11`, `b91b75b`..`46eb28c` + 최종 검토 수정). 실제 동작과 §3.2~3.6 의 차이는 **§3.7**.

### 3.1 문제

- salt 는 패스키 하나의 PRF 에서 나온다(`s_u = SHA-256(도메인 ‖ PRF) >> 6`). 그 패스키를 잃으면(동기화되지 않는 보안 키, 동기화를 끈 기기, 기기 분실) salt 가 사라진다.
- 지금 남은 길은 관리자 삭제뿐이다(zkWrapper 스펙 §8.4). 삭제 뒤 새 패스키로 등록하면 **auid 와 PPID 가 바뀐다 → 서비스별 계정 주소(지갑 컨트랙트)가 바뀐다 → 옛 주소의 자산은 옛 PPID 의 증명으로만 움직이므로 꺼낼 수 없다.**
  zkONE 이 거래소라는 시연 설정에서는 가장 큰 약점이다.
- 사용자는 이 사실을 미리 알 수 없다(`auid_pinned` 안내는 "처음 쓴 패스키로 로그인하라" 뿐이다).

### 3.2 고른 방향: "salt 봉투" (제안)

**salt 는 그대로 두고, 같은 salt 를 다른 열쇠로 잠근 사본(봉투)을 미리 만들어 둔다.**

```
지금:     패스키₁ ─PRF→ s_u                     (유일한 길)
바꾼 뒤:   패스키₁ ─PRF→ s_u                     (그대로 — 지금 사용자도 PPID 가 바뀌지 않는다)
          패스키₂ ─PRF→ K₂ ─복호→ 봉투₂ → s_u   (백업 패스키)
          복구 코드 ─────→ K_c ─복호→ 봉투_c → s_u (종이에 적어 두는 코드)
```

- 봉투 = `AES-GCM(K, s_u, AAD = "zkd-env-v1" ‖ uid ‖ 봉투 id)`.
  - 백업 패스키의 열쇠: `K₂ = HKDF(PRF₂, "zkd-env-key-v1")`. PRF 입력은 지금과 같은 `zkd-s_u-v1` 을 쓴다(패스키₂ 로 바로 만든 salt 를 쓰지 않으므로 충돌하지 않는다).
  - 복구 코드의 열쇠: 128비트 이상의 무작위 코드에서 HKDF. 사람이 고르는 비밀번호가 아니다.
- **봉투는 zkWrapper 서버에 Google 계정(uid)별로 둔다.** 서버는 암호문만 가진다. 열쇠(PRF·코드)는 서버로 가지 않는다.
- **무결성은 auid 로 확인한다.** 브라우저는 봉투를 연 뒤 `Poseidon(T_AUID2, s_u)` 가 계정에 고정된 auid 와 같은지 본다. 서버가 봉투를 바꿔치기하면 열리지 않거나 auid 가 맞지 않는다.
  서버가 봉투를 숨기는 것(서비스 거부)은 막지 못한다.
- 지금 사용자도 그대로 쓴다. 패스키₁ 의 salt 를 바꾸지 않으므로 PPID·주소가 바뀌지 않는다. 백업은 나중에 더하면 된다.

### 3.3 흐름

**백업 만들기(평상시, 홈의 "백업 추가")**
1. Google 확인(1회용 요청 키) → 패스키₁ → s_u.
2. (백업 패스키) 새 패스키₂ 를 만들고 PRF₂ 를 얻는다. 또는 (복구 코드) 코드를 만들어 화면에 한 번 보인다. 사용자가 적었는지 확인한다(다시 입력 받기).
3. 봉투를 만들어 `POST /cia/wrapper/envelope { id_token, pk_e, sig, envelope: { id, kind: 'passkey'|'code', credentialId?, ct } }`. 서명 본문은 `envelopeDigest({ op: 'add', id, H(ct) }, aud)` 다.
4. 서버: 결속 확인 → 계정이 등록돼 있고 폐기되지 않았는가 → 계정당 봉투 수 제한(예: 5) → 저장.

**복구(새 기기, 패스키₁ 없음)**
1. 서비스에서 "zkWrapper 로 로그인" → Google → 이 기기의 패스키(없으면 "이미 있는 패스키 쓰기") → 발급 요청 → 서버가 `auid_pinned` 로 거절한다.
2. 거절 응답에 **봉투 목록**(id·kind·credentialId·ct)을 함께 준다. 이 요청은 이미 Google 토큰과 요청 키 서명으로 결속돼 있다.
3. 승인 창: "이 Google 계정에는 백업이 있습니다 — 백업 패스키로 복구 / 복구 코드로 복구". 백업 패스키는 `allowCredentials` 를 봉투의 credentialId 로 좁혀 부른다.
4. 봉투를 연다 → auid 대조 → 이 기기의 새 패스키₃ 로 봉투₃ 를 만든다.
5. 다시 로그인한다. 앞의 토큰은 이미 쓰였으므로 Google 을 한 번 더 다녀온다. 이번 발급 요청에 봉투₃ 추가를 함께 싣고 서명 본문이 덮는다. 이후 이 기기에서는 패스키₃ 로 된다.
   - **주의**: 패스키₃ 의 PRF 로 바로 만든 salt 는 s_u 와 다르다. 그래서 이 기기의 salt 는 늘 봉투₃ 를 거쳐 나온다. 지갑은 연결된 패스키가 "직접(패스키₁)" 인지 "봉투 경유" 인지를 기억한다.

**잃은 패스키 막기**
- 서버는 패스키를 보지 않으므로 잃은 패스키₁ 자체를 막을 수는 없다. 잃은 패스키₁ 로 로그인하려면 Google 계정도 있어야 한다 — 두 요소 가운데 하나만 잃은 상태다.
- 봉투로 만든 백업(패스키₂, 코드)은 지울 수 있다: `envelopeDigest({ op: 'remove', id })`.
- 완전히 끊으려면 salt 를 바꿔야 하고, 그러면 PPID 가 바뀐다. 이것은 지금처럼 관리자 삭제로 남긴다.

### 3.4 고르지 않은 것

| 안 | 고르지 않은 이유 |
|---|---|
| zkWrapper 가 s_u 를 보관(Google 로그인만으로 복구) | zkWrapper 는 승인한 모든 서비스의 arid 를 안다. s_u 까지 알면 `PPID = H(s_u, arid, chainid)` 를 서비스마다 계산해 사용자를 모든 서비스에서 추적한다. 설계 목표(zkWrapper 는 어느 서비스인지 모른다)가 무너진다. |
| 복구 코드에 s_u 를 평문으로 담기 | 코드를 주운 사람이 Google 계정 없이도 모든 서비스의 PPID 를 계산해 사용자를 추적할 수 있다. 봉투 방식이면 코드만으로는 아무것도 못 한다(봉투는 Google 결속 뒤에만 받는다). |
| 컨트랙트 쪽 복구(옛 주소의 자산을 새 PPID 로 옮기기) | 지갑 컨트랙트와 회로의 변경이 필요하다. 누가 옮김을 승인하는지(서비스·zkWrapper)라는 새 신뢰도 생긴다. 이 스펙의 범위 밖이다. |
| 동기화 패스키만 권장하고 끝내기 | 비용이 0 이라 **함께 한다**(패스키 만들기 화면 안내). 다만 동기화 계정(Google 비밀번호 관리자 등)을 잃거나 보안 키를 쓰는 사람에게는 답이 되지 않는다. |

### 3.5 보안·프라이버시 메모

- zkWrapper 가 새로 아는 것: 계정별 백업 수와 종류, 백업 패스키의 credentialId(패스키마다 무작위 값이다). s_u·PRF·코드는 모른다.
- 공격자가 Google 계정과 백업 패스키₂(또는 코드)를 함께 가지면 복구할 수 있다. 이것은 패스키₁ 과 같은 수준이다(백업은 같은 문을 여는 열쇠가 하나 더 생기는 것이다). 그래서 확인 창에 "백업은 안전한 곳에" 를 적는다.
- 봉투 목록은 `auid_pinned` 를 받을 수 있는 사람(Google 토큰 + 요청 키)에게만 간다. 받아도 열쇠 없이는 쓸 수 없다.
- 계정을 관리자가 삭제하면 봉투도 지운다. 폐기만이면 남긴다(§6 Q6).

### 3.6 바꾸는 곳 (예상)

- `lib/mode3_wrapper_auth.js`: `envelopeDigest({ op, … }, aud)`, 발급 본문 digest 에 선택 칸 `envelope`.

| E3 | **auid 대신 대조값**: 409 `auid_pinned` 는 `auidCheck = SHA-256 16진("zkd-auid-check-v1|" + uid + "|" + auid)` 와 봉투(id·kind·credentialId·ct)만 준다 — auid 는 싣지 않는다. 브라우저는 연 salt 로 같은 값을 계산해 맞을 때만 발급을 보낸다(다르면 `recover_auid_mismatch`). 대조값·암호문은 코어 메모리에만 두고 화면 응답·로그에는 싣지 않는다. | §3.3-2·§3.2 "auid 로 확인" — Google 계정만 가진 사람에게 auid 를 주지 않으려고(I1). |
| E4 | **같은 토큰으로 다시 발급**: `auid_pinned` 는 토큰을 쓰기 전에 거절되므로, 복구는 409 를 받은 같은 Google 토큰·같은 요청 키로 발급을 다시 청한다(새 본문을 요청 키의 서명이 덮는다). Google 을 두 번 다녀오지 않는다. 요청 키 수명(10분, Google 왕복 포함) 안에 끝나야 한다. | §3.3-5 의 두 번째 Google 왕복을 없앴다. |
| E5 | **서명하는 글**: 봉투 추가 `zkwrapper|envelope|aud|add|auid|id|kind|credentialId(또는 -)|ct`, 삭제 `zkwrapper|envelope|aud|remove|auid|id`, 복구 발급 = 지금의 발급 글 끝에 `|envelope|id|kind|credentialId|ct`. **`ct` 를 해시하지 않고 그대로 넣는다**(브라우저 WebCrypto 에 동기 SHA-256 이 없다 — ct 는 b64url ≤ 256자라 구분자가 없다). 봉투가 없는 발급의 글은 바이트까지 예전과 같다. | §3.3-3 의 `H(ct)` 를 ct 그대로로. auid 칸은 E9. |
| E6 | **상태 파일 버전은 14 그대로** — `accounts[uid].envelopes` 는 없어도 되는 칸이다(없으면 빈 목록). 기동 때 모양이 틀린 항목은 버리고 notes 에 남긴다. 관리자 삭제 때 계정과 함께 사라지고, 계정 폐기 때는 남는다(§6 Q6). | §3.6 "상태 파일 버전이 바뀐다" 를 하지 않았다. |
| E7 | **봉투 종류와 한도**: 백업 = `passkey`(백업 패스키)·`code`(복구 코드), 계정당 5개(`envelope_limit`). 복구한 기기의 봉투 = **`device`**, 따로 10개 — 발급으로만 더하고, 같은 credentialId 면 바꿔 넣고, 차면 가장 오래된 `device` 를 밀어낸다. `device` 는 백업을 바꾸거나 밀어내지 않는다(같은 id·credentialId 의 백업이 있으면 더하지 않는다). 백업 한도가 찬 것이 복구를 막지 않는다. 목록만 읽는 서버 경로는 없다 — `/user` 의 백업 목록은 이 브라우저가 받은 더하기·지우기·복구 응답으로만 바뀐다. | §3.3-4 "계정당 봉투 수 제한(예: 5)" 을 종류별로 나눴다. §3.6 의 "목록" 은 두지 않았다. |
| E8 | **이 기기의 사본**: 복구한 기기는 자기 패스키(PRF)로 잠근 `device` 봉투를 IndexedDB 에 두고(kv `passkey = { credentialId, via: 'envelope', envelope: { id, kind, ct, uid } }`), 복구 발급이 받아들여지면 서버에도 같은 봉투를 둔다(저장소가 지워져도 그 패스키로 다시 복구). 발급이 받아들여지지 않은 복구(10분 간격·네트워크 등) 뒤에는 사본만 있고 서버에는 그 기기 봉투가 없을 수 있다 — 다음 로그인은 사본으로 되지만, 그 상태에서 저장소가 지워지면 백업으로 다시 복구해야 한다(그때 이 브라우저의 목록 메타에는 서버에 없는 `device` 항목이 남을 수 있다 — 화면은 백업만 보인다). 다음 로그인은 패스키 한 번으로 사본을 연다. 사본은 **대조가 맞은 바로 뒤, 발급을 보내기 전에** 쓴다(최종 검토 I-2) — 발급 뒤 증명 중에 창이 닫혀도(서비스 창은 300초에 닫는다) 이 기기가 막히지 않는다. 첫 시도에 고른 패스키가 바로 백업 패스키면 다시 묻지 않고, 새 봉투도 만들지 않고 그 백업 봉투를 사본으로 쓴다. 서버에서 그 기기의 봉투를 지워도 사본으로는 계속 된다. | §3.3-4 "새 패스키₃ 로 봉투₃" 를 구체화했다. |
| E9 | **백업 추가·삭제에 salt 증명**(최종 검토 I-1, 2026-11-24 사용자 결정): 추가·삭제 요청은 계정의 `auid` 를 싣고 서명한다. 서버는 토큰을 쓰기 전에 계정에 고정된 auid 와 맞춰 보고, 다르면 409 `envelope_auid_mismatch`(없으면 400 `envelope_bad`)로 거절한다 — 토큰은 남는다. 응답에 auid 는 없다. 그래서 **지우기도 지금 패스키를 한 번 묻는다.** | §3.3 "잃은 패스키 막기" 의 삭제는 Google 결속만이었다 — Google 계정만 가진 사람이 409 로 봉투 id 를 알아 백업을 모두 지우거나 한도를 쓸모없는 봉투로 채울 수 있었고, 사용자는 그것을 볼 수 없었다. |
| E10 | **패스키는 클릭 한 번에 한 번**(사용자 동작이 있어야 WebAuthn 을 여는 브라우저 대비): 백업 패스키 더하기는 돌아온 화면에서 두 번 누른다 — ① 지금 패스키로 확인 ② 백업 패스키 만들기(만들기는 `excludeCredentials` 에 지금 패스키·이 브라우저가 아는 봉투의 credential 을 넣어 같은 인증기에 백업이 생기지 않게 한다). 복구 코드는 돌아온 화면에서 만들어 한 번 보이고 다시 입력받은 뒤 "확인하고 저장"(지금 패스키 한 번). 지우기는 돌아온 화면의 "지금 패스키로 확인하고 지우기". 복구 한 번에 패스키를 묻는 횟수: 이 기기에 패스키가 있으면 1 + 백업 패스키 1, 새로 만들면 만들기 1 + 확인 1 + 백업 패스키 1(복구 코드면 백업 몫 0). | §3.3 흐름에 클릭 단계를 정했다. |

**알려진 한계**
- 서버가 정직하다는 전제의 검사다. 악의적인 서버는 봉투를 숨기거나(백업이 없다고 하거나) 지울 수 있고, **옛 봉투와 옛 대조값을 함께** 주면 브라우저는 가리지 못한다(대조값도 서버가 준다).
- 복구는 사용자 자격증명(C_u) 교체다 — 그 계정의 앞 교체 뒤 10분(`CIA_CRED_CHANGE_MIN_MS`) 안이면 `cred_change_too_soon` 으로 막힌다. 화면은 "서비스에서 처음부터" 로 안내한다. 간격은 남긴다(등록부를 갈아 끼우는 서비스 거부를 막는다).
- 서비스 창은 승인 창을 300초 기다린다(`mode3/rp.html` `POPUP_TIMEOUT_MS`) — 요청 키 수명(10분)보다 짧다. 복구 코드는 미리 꺼내 둔다(시연 대본).
- `/user` 의 백업 목록과 한도 미리 알림은 이 브라우저가 받은 응답 기준이다 — 다른 기기에서 더한 백업은 이 브라우저가 다음에 더하거나 지울 때 나타난다(서버가 다시 거른다). 백업 패스키를 만들 때의 `excludeCredentials` 도 그 목록 기준이다.
- 복구한 기기에는 속성 도구 기록이 없어 다음 발급의 C_u 가 빈 속성이다 — 조건을 거는 서비스를 쓰려면 그 기기에서 속성을 다시 넣는다.
- 이 기기의 사본이 망가지면(저장소 손상) 로그인이 `envelope_open_failed` 로 멈춘다 — 빠져나오는 길은 `/user` "보관 상태" 의 "모두 지우기" → "패스키 연결 끊기" 뒤 다시 로그인(복구 화면).
- 백업 패스키를 만든 뒤 서버가 거절하면(한도·중복) 인증기에 쓰이지 않는 패스키가 남을 수 있다(화면이 알린다).
- 사본은 대조가 맞은 뒤 발급 전에 쓰므로, 발급이 받아들여지지 않은 복구 뒤에도 이 기기의 패스키는 그 계정에 묶인다 — 이 브라우저에서 다른 Google 계정을 쓰려면 `/user` "보관 상태" 의 "모두 지우기" → "패스키 연결 끊기" 를 먼저 한다(아니면 `wrapper_account_mismatch`).
- 실제 Google·실제 보안 키(GPM)로는 아직 리허설하지 않았다 — 대역 Google·가짜 인증기로 격리 테스트만 했다.

## 4. 순서 (제안)

1. 1부(홈·용어) — 화면만 바뀌고 서버가 바뀌지 않는다. 옆 세션의 홈 작업이 커밋된 뒤에 한다.
2. 2부(계정 자기 폐기) — 클라이언트만 바뀐다. 1부와 같은 파일(`ui.js`·`strings.js`)이라 이어서 한다.
3. 3부(봉투 복구) — 서버·상태 파일이 바뀐다. 구현 계획을 따로 쓰고 Opus 독립 검토를 받는다(암호 설계 포함).

## 5. 검증 (개요)

- zkWrapper 브라우저 테스트(`tests/test_mode3_user_wrapper_browser.mjs`)를 먼저 돌린다(가장 작은 범위). 이어서 strings 단위 테스트, 3부는 서버 단위·체인 그룹.
- 다른 모드가 바뀌지 않았는지: passkey-web·스냅 브라우저 테스트 한 번(그룹 `browser`).
- 사람 확인: 새 Chrome 프로필로 `https://wallet.zkd.test:5100/` 을 열어 미등록 홈 → zkONE 로그인 → 등록 홈. 3부는 실제 GPM 패스키 + 보안 키(또는 두 번째 프로필)로 백업 → 복구.
