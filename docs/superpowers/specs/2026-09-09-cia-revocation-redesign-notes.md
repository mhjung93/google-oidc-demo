# CIA 기반 폐기 재설계 — 진행 중 메모

**상태: 설계 대화 진행 중. 확정된 설계가 아니다.**
2026-09-09 대화에서 정해진 것, 확인한 사실, 아직 열린 질문을 적어 둔다.
현행 구현(v3 이중 트리 + V4 전이 검증 레지스트리)은 아직 그대로 돌고 있고, 이 문서는
그것을 **대체할** 방향을 잡는 중이다.

---

## 1. 확정된 것

- **IdP → CIA**(Credential Issuing Authority)로 개념 전환.
- CIA는 **`(uid, pk)`** 를 보관한다 — 사용자별 장기 공개키 등록부.
- **장기 신원키는 CIA가 발급한다.** 사용자가 스스로 만들지 않는다. CIA는 `sk`를 기억하지 않는다.
  - uid당 **하나**, 장기.
  - **BAAR와 다르다** (아래 §3 참고). 의도적 변경이므로 논문에 그렇게 적어야 한다.
- **세션 키쌍은 사용자가 만든다.** (지금 `wallet_agent.js`가 하는 대로. 이번 논의에서는 뒤로 미룸.)
- **발급 시 사용자가 제출하는 것은 ZKP다.** JWT 아님.
  - 공개: `(C, arid)`
  - 숨김: `(salt, a)`
  - 관계: `C = salt·B + Σ aᵢ·Gᵢ` (`B`, `Gᵢ`는 공개 파라미터)
- CIA가 증명을 검증하고 통과하면 **`credential id = H(uid, arid, C)`** 를 구성한다.
  이 값이 머클 트리의 리프다.
- credential은 **세션별**로 발급된다. 목적은 **세션키의 정당성 보증**.
- **`C`는 show 시점에 숨겨야 한다.** (근거는 §2)

---

## 2. 논의에서 확립된 근거

### 2.1 `C`를 숨겨야 하는 이유

두 가지이고 두 번째가 결정적이다.

- **`C`가 고정값이면 영구 식별자다.** `salt`·`a`가 사용자 고정이면 `C`도 고정이라, 모든 show가
  서로 연결된다(같은 verifier든 다른 RP든). 교차-RP 언링커빌리티가 통째로 사라진다.
- **세션마다 `C`를 새로 만들어도 남는다.** CIA는 발급 시점에 `(uid, C)`를 본다. show 시점에
  `C`를 보는 쪽은 CIA 기록과 대조해 **uid를 복원**할 수 있다. `C`는 **발급 장면과 사용 장면을
  잇는 손잡이**다.

**숨겨서 지키는 것은 언링커빌리티지 속성 기밀성이 아니다** — 속성은 Pedersen이 이미 hiding이다.

### 2.2 `arid`도 같이 숨겨야 한다

CIA의 발급 시점 관측은 **`(uid, C, arid)`** 셋이다. 이 중 **어느 하나라도** show 시점에
드러나면 CIA가 연결할 수 있다. 따라서 `arid`도 show에서 숨겨야 한다.

### 2.3 샤드 인덱스를 공개하면 CIA에 대한 누출이 된다

`id = H(uid, arid, C)`는 CIA가 계산할 수 있다(셋 다 안다 — 폐기하려면 그래야 한다).
샤딩하고 **샤드 인덱스를 온체인에 공개하면** 그 인덱스도 CIA가 계산할 수 있으므로,
CIA는 트랜잭션마다 후보를 좁힌다(4,096 샤드면 약 12비트).

어제 고친 것이 "RP 간 누출"이었는데 같은 구조가 **"CIA에 대한 누출"** 로 재등장한다.

### 2.4 그런데 이번엔 샤딩이 필요 없을 수 있다

계정 층이 없어지고 트리에 **만료되지 않은 폐기 세션 credential만** 담기면:

- 폐기율 0.01%/일 × 1억 = 하루 10,000건
- credential 수명 1시간 → 상주 폐기 리프 **약 417개**
- 100배로 잡아도 41,700 → 깊이 17이면 담긴다

깊이 20 단일 트리를 **회로 안에서** 전부 검증해도 약 5,800 제약으로, 지금의 깊이 8 + 깊이 10
두 개와 비슷하거나 싸다. 그러면 **공개할 인덱스가 없어 누출도 없고**, 상위 트리·컨트랙트
접기·리셋 보조정리·전이 증명이 전부 불필요해진다.

> 오늘까지의 복잡함은 **전부 샤딩에서 나왔고**, 샤딩은 "트리가 크다"는 전제에서 나왔다.
> 계정 층을 빼면 그 전제가 무너진다.

### 2.5 멤버십 vs 비멤버십 — 갱신율이 10,000배 갈린다

샤드 4,096 기준, 캐시된 증명이 사는 시간:

| | 내 샤드 갱신 빈도 | 캐시 수명 |
|---|--:|--:|
| 비멤버십 (폐기 0.01%/일 = 블록당 1.4) | 2,900블록에 1회 | 약 10시간 |
| 멤버십 (발급 = 블록당 13,900) | 블록당 3.4회 | 1블록 미만 |

샤딩으로는 못 구한다 — 같은 수명을 얻으려면 샤드를 10,000배 늘려야 한다.
멤버십은 **트랜잭션마다 재증명**(약 500 ms + CIA 왕복)을 받아들일 때만 성립하고,
그러면 **CIA가 모든 트랜잭션의 가용성 의존**이 된다.

### 2.6 유효성과 미폐기는 별개 장치다

- **발급된 것이 맞다** → 서명(또는 누적기 멤버십)
- **폐기되지 않았다** → 폐기 목록 비멤버십

지금 구현이 이미 이렇다: `pi_pk_i` 회로가 IdP의 EdDSA-Poseidon 서명을 회로 안에서 검증하고,
**동시에** 폐기 트리 비멤버십을 증명한다. 유효 목록 트리는 처음부터 없었다.

### 2.7 "CIA가 C에 서명했다"만으로는 부족하다

같은 증명 안에 함께 묶여야 하는 것:

- **세션키 `pk_i` 바인딩** — 없으면 "세션키 정당성 보증"이라는 목적 자체가 성립 안 함
- **비폐기** — 서명은 "발급됐다"만 말한다
- **`id` ↔ `C` 결속** — 비멤버십에 쓰는 `id`가 서명된 그 `C`에서 나왔음을 보여야 한다.
  아니면 폐기된 사용자가 다른 `id`로 통과한다
- **비밀 지식** — 없으면 `(σ, C)`를 엿본 사람도 증명할 수 있다
- **문맥 결속** — nonce·chain_id·컨트랙트 주소(지금 `payloadHash`가 하는 일)

## 3. BAAR 원문에서 확인한 사실

출처: `documents/BAAR_PLOSONE_e0343696.pdf` (PLOS One, 2026-03-31)

### 3.1 credential 구성 (§3.5)

**Request (사용자)**
- 장기 키쌍 `(d, e = d·G)` 샘플링 — **사용자가 만든다**
- **임시 키쌍 `(d_u, e_u)`** 별도 생성
- `C = r·H + Σ mᵢ·Gᵢ`, `r ← Zq`
- 속성·블라인딩 지식의 ZKPoK `π`
- 전송: `Request = (e_u, C, π, Sign_{d_u}(C))`

**Generation (CIA)**
- `π`와 `e_u` 아래 서명 검증
- `Acc'root = Merkle.Insert(C, Accroot)` — **커밋을 누적기에 삽입**
- 갱신된 root 온체인 게시, 멤버십 witness `w` 반환

**Validation (사용자)** — `σ = Schnorr.Sign(d_u, π' ‖ w)`, verifier에게 `(C, e_u, m_S, π', w, σ)` 전송

**Verification (verifier)** — ① `VerifySchnorr(e_u, σ)` ② `Verify(π', m_S, C)` ③ `Merkle.Verify(w, C, Acc_root)`

**Revocation** — `Acc'' = Merkle.Remove(C, Acc)`

### 3.2 핵심: **BAAR에는 CIA 서명이 없다**

발급이란 **`C`를 누적기에 넣는 것**이고, 유효성은 **누적기 멤버십**이다.
`σ`는 사용자의 임시키 Schnorr 서명이지 CIA 서명이 아니다.
(§3.3의 `Issue (par, a, e) → σ`를 CIA 서명으로 읽으면 오독이다 — 대화 중 한 번 그렇게 잘못 읽었다.)

### 3.3 BAAR의 문제점 (우리 설계에 영향 있는 것)

1. **`C`가 verifier에게 평문으로 간다.** credential마다 고정이므로 모든 show가 연결된다 —
   논문이 내세운 "unlinkable"과 충돌한다. §2.1의 구멍이 BAAR에 그대로 있다.
2. **논문 내부 불일치**
   - 리프가 `C`인가(§3.5 검사 ③) `x = H("tag"‖C)`인가(Protocol 3)
   - `RCL`에 **추가**해서 폐기(§3.3) vs 누적기에서 **제거**해서 폐기(§3.5, Protocol 3)
     → 화이트리스트인지 블랙리스트인지가 뒤섞여 있다
   - `KeyGen`이 Fig 1에서는 **CIA 상자 안**인데 §3.3 본문은 "**Each user samples** a private key d"
     (가장 앞뒤 맞는 해석: Fig 1의 것은 CIA 자신의 발급자 키. 상자 안 넷이 전부 체인에 쓰는
     연산이고, §3.2도 "CIA initializes the system by generating keys"라 한다.
     한편 `Verify(par, e, Θ)`가 사용자별 `e`로 검증하므로 사용자 키도 따로 있어야 한다.)
3. **witness 갱신 부담을 다루지 않는다** — "users coordinate with the CIA to refresh their
   Merkle witnesses" 한 줄. 삽입·제거 어느 쪽이든 root가 바뀌면 전원의 witness가 무효다.
4. **만료가 없다** — credential은 폐기 전까지 영원히 살아 누적기가 총 발급량으로 자란다.

### 3.4 BAAR의 다른 성질

- **pairing-free**가 첫 번째 기여다. secp256k1 위 Schnorr ZKPoK를 쓴다.
  → **PS 서명(페어링 기반)을 쓰면 그 기여와 배치된다.** (저장소에는 PairCT 시절 PS가 이미 있다.)
- **검증이 오프체인**이다. "ZKPs and signature verification are performed off-chain,
  whereas the blockchain is used **solely to maintain the revocation state**."
  Fig 1도 Validation/Verification을 Verifier 쪽 체인 밖에 그린다.
  → 지금 PairCT 구현은 정반대로 `PPIDWallet.execute()`가 **온체인 Groth16 검증**을 한다(335,862 gas).

## 4. 아직 열린 질문

1. **credential의 유효성을 무엇이 보장하는가** ← 지금 여기서 멈춰 있다
   - (BAAR 그대로) 누적기 멤버십 — CIA 서명 없음. 갱신율 = 발급율, witness 갱신 상시.
   - CIA 서명 + 폐기 비멤버십 — 트리가 작아지고(상주 수백) 캐시가 산다.
   - 둘 다 — 중복으로 보인다.
2. **증명 검증을 온체인에서 하는가 오프체인에서 하는가** (세 번 물었으나 아직 미결)
   - 오프체인(BAAR): 가스 거의 0, 오늘의 온체인 기계 전부 불필요.
     대신 **"폐기된 세션은 `execute()`가 revert한다"는 PairCT의 강제력이 사라진다.**
   - 온체인(지금): 지갑이 스스로 폐기를 강제. 대신 그 기계를 유지.
   - 둘 다: RP는 로그인 때 오프체인, 체인은 트랜잭션 때.
3. **만료 처리** — 폐기 리프를 언제 어떻게 빼는가. 서명 안에 만료를 넣어야 하는가.
   (넣지 않으면 폐기 트리가 계속 자라고, 지금의 만료 축 샤딩 회수 장치가 사라진다.)
4. **`C`가 세션마다 새로운가** — `salt`를 발급마다 새로 뽑는가.
5. **CIA가 sk를 본다는 점**을 어떻게 다루는가 — 분산 키생성? 사용자 기여 혼합? 신뢰 가정 명시?
6. **PS(페어링) vs Schnorr(pairing-free)** — BAAR 일관성 vs 저장소 기존 자산.
