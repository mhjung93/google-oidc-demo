# Mode 3 — 서비스 보관 계정을 실제 체인 주소로 (설계 초안)

- 작성: 2026-11-25. 상태: **승인(2026-11-25, Q1~Q3 권장대로)·구현, 라이브 미반영**. 사용자 결정(② HD 유도) — 같은 날 앞서 정한 "키를 새로 맡지 않는다(화면만 정리)" 를 뒤집는다.
- 목적: Google 등 소셜 로그인 사용자도 체인에 자기 주소가 있고, 보내면 `from` 이 그 주소다. zk 로그인(내 PPID 계정)과의 차이는 "주소가 있나" 가 아니라 **"키를 누가 쥐나"** 로 보인다.

## 1. 지금 (확인한 것)
- 쿠키 채널 구매는 장부 숫자(`custodyEth`)만 올리고 체인 거래가 없다. 보내기는 릴레이어(zkONE = 0번, zkTWO = 1번)가 자기 돈으로 보낸다(`mode3_rp.js` `ledgerOp`).
- 릴레이어 서명은 hardhat 노드가 한다(`provider.getSigner(i)`). 서비스 프로세스에는 지금까지 개인 키가 없었다 — **이 변경으로 처음 생긴다.**
- `mode3_rp_custody_seed.json` 은 **.gitignore 에 걸리지 않는다**(저장소는 공개). `.bak-…` 은 걸린다. `SYNC=1` 은 정해진 목록만 보내므로 시드는 오가지 않는다.
- provider 는 응답 캐시가 꺼져 있다(`cacheTimeout: -1`) — 보낸 직후의 잔고·nonce 가 낡지 않는다. 서비스는 탐색기 주소를 모른다(지갑 쪽만 `MODE3_EXPLORER_URL`).
- 구매는 "KRW 확인 → 송금 → KRW 차감" 사이에 잠금이 없다(서명 채널). 동시에 두 번이면 KRW 보다 많이 보낼 수 있다. 쿠키 채널 보내기는 "먼저 깎기" 가 그 역할을 했는데 이번에 없어진다.

## 2. 설계

### 2.1 시드와 주소 — 새 파일 `lib/mode3_rp_custody.js`
- 시드: 무작위 32바이트, 서비스마다 하나. 파일 이름은 계정 파일에서 정한다(`…accounts.json` → `…custody_seed.json`; `MODE3_RP_CUSTODY_SEED_FILE` 로 바꿀 수 있다) — 한 폴더의 여러 서비스(`new_rp.sh`)가 시드를 나눠 쓰지 않는다.
- 첫 기동에 만든다: 0600, 이미 있으면 덮지 않는 쓰기(`wx`) + fsync. 있는 파일의 권한이 0600 보다 넓거나 모양이 틀리면 기동을 막는다. **오류 문구에 파일 내용을 싣지 않는다**(파서 오류를 그대로 내지 않고 고정 문구).
- 시드를 잃고 조용히 새로 만들면 남의 키가 된 주소의 돈을 잃는다: 계정 파일에 시드의 **지문**(전용 경로의 주소 — 공개값)을 적어 두고, 지문이 있는데 시드가 없거나 다르면 기동을 막는다. 지문이 없으면(처음) 만든다.
- 경로: `SHA-256("zkd-rp-custody-v1|" + 계정 id)` 앞 16바이트를 31비트 넷으로 나눈 **강화 경로 네 단**. 요청하신 한 단(0..2³¹−1)은 두 계정이 같은 주소(같은 키)를 받을 수 있다 — 계정 1만 개면 약 2%. 네 단(124비트)이면 사실상 없다. 강화 경로는 한 계정의 키가 새도 다른 계정으로 번지지 않게 한다.
- 키는 저장하지 않고 보낼 때마다 유도한다. 시드·개인 키는 응답·로그·화면·`rp_info`·health 에 나가지 않는다.

### 2.2 장부 동작 (`ledgerOp`)
- **계정별 잠금**: 입금·구매·보내기를 계정마다 한 줄로 세운다(두 채널 모두) — KRW 초과 구매와 nonce 충돌을 막는다.
- **구매**: 채널에 관계없이 릴레이어가 `target`(서명 = PPID 계정, 쿠키 = 보관 주소)으로 송금하고 `relayedTxs` 에 `kind:'buy'` 로 적는다. KRW 는 먼저 빼고, **나가지 않았거나(해시 없음) 체인에서 되돌려졌을 때만** 돌려준다. 냈는데 확인하지 못하면 새 사유 `buy_unconfirmed`(KRW 는 차감된 채). 노드가 거래를 받고도 오류로 답하면 나갔는지 알 수 없다 — 나가지 않은 것으로 본다(한계).
- **보내기**(쿠키만): 보관 키로 서명. `gasLimit` 은 받는 쪽이 일반 주소면 정확히 21000, 컨트랙트면 추정값(추정이 21001 을 주는 노드에서 "최대" 를 그대로 보내면 가스 부족이 된다 — 구현 중 발견). 수수료 값(`maxFeePerGas` 등)을 명시해 **검사한 값과 보낸 값이 같다**.
  - 잔고 < 금액 → `insufficient_custody`. 금액 ≤ 잔고 < 금액 + 가스 → 새 사유 `insufficient_gas`(보낼 수 있는 최대를 함께).
  - 거래를 내지 못함 → `withdraw_failed`. 냈는데 확인을 못 함 → 새 사유 `withdraw_unconfirmed`(해시를 함께 — 다시 누르면 두 번 나갈 수 있다고 알린다).
  - `relayedTxs` 의 `kind:'custody_withdraw'` 는 그대로, `account` 에 보관 주소.
- **보기**(`ledgerView`): `ETH_CUSTODY` = 보관 주소의 체인 잔고(못 읽으면 `-`), `custodyAddress`, `custodyWei`, `custodyMaxWei`(= 잔고 − 21000 × 지금 수수료, 음수면 0). 소셜 수단(google·naver·zkoidc)이 있거나 잔고가 있는 계정에만 낸다 — zk 만 쓰는 사람에게 쓸 일 없는 주소를 보이지 않는다.
- **계정 하나에 Google·zk 가 함께 연결된 경우 두 주소를 따로 둔다**(보관 주소와 PPID 계정 — 합치거나 옮기지 않는다).

### 2.3 계정 파일 (`lib/mode3_rp_accounts.js`)
`custody`·`addCustody` 를 없애고, 열 때 `custodyEth` 칸을 지운다(옛 `attr` 칸과 같은 방식). `custodyKey`(지문) 칸을 더한다. version 은 2 그대로.

### 2.4 화면 (`rp.html`·`strings.js`)
- "내 계정 번호" 줄 옆에 0x 주소 · 복사 · 탐색기 링크(주소 형식·`http(s)` 주소일 때만). 탐색기 주소는 `rp_info.explorerUrl` — 시작 스크립트가 두 서비스에도 `MODE3_EXPLORER_URL` 을 준다.
- 안내: "주소는 내 것이지만 **키는 서비스가 보관합니다** — 서비스가 대신 서명해 보냅니다." 다음 줄: "zkWrapper 로 로그인하면 내 세션키와 증명이 있어야만 나가는 계정(PPID)을 받습니다."
- 보내기 칸에 "보낼 수 있는 최대 … ETH (가스 제외)". `ko`·`en`·`ko_wr`·`en_wr`, 새 사유 셋. 옛 "서비스가 맡아 두고"·"거래소 보관" 문구와 "키를 새로 맡지 않는다" 주석을 고친다.

### 2.5 운영
- `.gitignore` 에 `mode3_rp*_custody_seed*.json*` — **시드를 만드는 코드보다 먼저 커밋한다.**
- `demo_split_start.sh` 리셋 백업 목록에 `mode3_rp_custody_seed.json`·`mode3_rp_*_custody_seed.json`. 계정 파일과 **함께** 옮겨야 한다(지문이 맞지 않으면 기동이 막힌다). `demo_web_reset.sh` 는 지금도 계정 파일을 옮기지 않으므로 그대로 둔다(둘 다 남아 짝이 맞는다).

## 3. 한계 (docs/MODE3_DEMO.md 에도 적는다)
- **시드 파일 하나가 그 서비스 보관 계정 전부의 키다.** 서버가 털리면 전부 잃는다. 서비스는 사용자 동의 없이 돈을 옮길 수 있다 — 일반 OIDC 쪽의 의도된 대비다.
- 백업된 옛 시드(`.bak-…`)가 VM 에 쌓인다. 체인이 새로 시작해 가치는 없지만 키라는 점은 같다.
- 서비스마다 시드가 달라 **체인 주소만으로는** 두 서비스의 같은 사람을 잇지 못한다. 그래도 두 서비스는 같은 Google `sub` 를 받으므로 기록을 맞추면 주소까지 이어진다.
- 체인은 누가 보냈는지(주소)와 금액을 공개한다. 장부 방식에서는 릴레이어 뒤에 가려져 있었다.
- 가스는 잔고에서 나가므로 "최대" 로 보내도 수수료 여유분이 조금 남는다. 잔고 전부를 비우는 기능은 없다.

## 4. 검증
- 새 단위 테스트 `tests/test_mode3_rp_custody.mjs`(`run_tests.sh` unit): 0600·덮지 않음·재기동 뒤 같은 주소·계정마다 다른 주소·서비스마다 다른 주소·시드 유실/교체/망가짐/넓은 권한이면 기동 거부(오류 문구에 내용 없음)·유도 고정값(KAT, 테스트 전용 시드).
- `test_mode3_rp_accounts.mjs`(custody 제거·옛 칸 삭제·지문), `test_rp_social_logins.mjs`: 구매 뒤 보관 주소의 **체인 잔고**, 보내기의 `from` = 보관 주소, 받는 쪽 증가, 가스만큼 더 줄어듦, 초과·가스 부족·0·주소 오류, 동시 구매 둘 중 하나만 통과, 동시 보내기 둘의 nonce, 재기동 뒤 같은 주소·잔고, zkONE·zkTWO 주소가 다름.
- 시드·개인 키가 새지 않음: `rp_info`·health·`/api/rp/me`·장부 응답·`/api/mode3/txs`·서비스 로그에 없음(테스트가 만든 시드로 대조).
- 브라우저: `test_mode3_user_wrapper_browser.mjs`(주소·복사·링크·안내·최대·이어 로그인 때 주소가 지워짐). `test_mode3_wallet_snap_oidc_browser.mjs` 는 다른 방식의 테스트라 **고치지도 돌리지도 않았다**(2026-11-25 사용자 결정) — 보관 잔액을 장부 숫자로 기대하면 깨질 수 있다. 서명 채널 구매는 `test_mode3_user_core_wrapper.mjs` 가 본다.
- 라이브: zkONE Google 로그인 → 입금·구매 → 보내기 → Blockscout 의 `from`. 재기동·SYNC 는 먼저 묻는다.

## 5. 하지 않는 것
시드 암호화·HSM, 잔고 전부 비우기, 보관 ↔ PPID 사이 이체, 키 내보내기, 서비스끼리 주소 공유.

## 6. 정한 것 (2026-11-25)
- **Q1.** 서버 동작은 모든 방식, 주소·복사·링크·최대 표시는 zkWrapper 만. **Q2.** 강화 경로 네 단. **Q3.** 지문이 맞지 않으면 기동을 막는다.
