# Mode 3 zkWrapper — 보관 사본: 같은 패스키면 속성까지 되찾는다 (설계·구현, 2026-11-26)

- 상태: **구현됨**(2026-11-26). 결과는 §6.
- 배경(피드백 2026-11-26): "패스키를 통해서 복원한다면, 사용자 속성까지 전부 복원할 수 있도록 해야 한다. 가장 간단한 방법으로는 cloud 에 저장해놨다가 패스키 인증되면 다 복사해오던가",
  "휴대폰 인증도 될 수 있게 해야 함".
- 범위: zkWrapper 방식만. 회로·컨트랙트는 바꾸지 않는다.

## 1. 지금까지

같은 패스키(같은 salt)로 다른 브라우저·기기에서 로그인하면 계정 주소(PPID)는 같다. 그러나 **속성**과 **사용자 자격증명의 재료**(`blind_u`)는 그 브라우저에만 있었다.

- 새 브라우저의 첫 로그인은 빈 속성의 새 `C_u` 를 받았다 → 조건을 거는 서비스(zkTWO)에 못 들어갔다(Google 로 가기도 전에 "속성이 없습니다" 로 멈췄다).
- 새 `C_u` 는 교체라서, 다른 기기에서 열려 있던 세션이 모두 폐기됐다.
- 이미 등록된 두 기기 중 한쪽이 속성을 바꾸면 다른 쪽은 `registry_mismatch` 로 로그인이 막혔다.

휴대폰의 패스키로 노트북에서 로그인하는 경우(QR)가 바로 이 "같은 패스키, 새 브라우저" 다.

## 2. 결정

| # | 결정 | 이유·대가 |
|---|---|---|
| V1 | 브라우저는 발급 요청마다 **보관 사본**(`vault`)을 싣는다: `{ v:1, uid(C_u 안의 값), profile, attrs[6], blind_u }` 를 salt 에서 유도한 키(AES-256-GCM, `SHA-256("zkwrapper-vault-v1\|" + salt)`)로 잠근 것. 암호문은 계정의 `auid` 에 묶인다. | 속성이 바뀌는 것은 발급 때다 — 사본이 늘 등록된 `C_u` 와 같은 내용이 된다. 따로 올리는 왕복이 없다. |
| V2 | 서버는 발급이 받아들여지면 그 암호문을 계정에 둔다(덮어쓴다). **열지 못한다** — 속성 값은 서버가 모른다는 원칙(D15) 그대로. 발급 요청의 서명이 사본까지 덮는다. | |
| V3 | 내려주기 `POST /cia/wrapper/vault { id_token, pk_e, sig, auid }`: 요청 키에 묶인 Google 토큰 + 서명 + 계정의 `auid`. **토큰을 쓰지 않는다** — 같은 토큰으로 이어서 발급한다. 상태를 바꾸지 않는다. | 암호문은 salt 없이는 쓸모가 없다. `auid` 가 다르면(다른 패스키) 주지 않는다. |
| V4 | **새 브라우저**(이 브라우저에 등록도 속성 기록도 없다): Google 확인·패스키 뒤, 발급 전에 사본을 받아 연다. 열리면 속성·프로필·`blind_u`·`C_u` 를 그 값으로 등록하고 로그인한다 — `C_u` 가 같아 교체가 아니다. 사본이 등록부보다 낡았으면 속성만 쓰고 새 `C_u` 를 받는다. | 다른 기기의 세션이 남는다. 조건을 거는 서비스에 바로 들어간다. |
| V5 | **이미 등록된 브라우저**가 `registry_mismatch` 를 만나면: 사본의 `C_u` 가 등록부의 내 슬롯 리프와 **같을 때만** 그 값으로 맞추고 한 번 더 로그인한다. 같지 않으면 지금처럼 멈춘다. | 사본은 salt 의 키로만 만들 수 있다 — 서버가 꾸며 낼 수 없으므로 "내 다른 기기가 바꿨다" 는 증거가 된다. 서버의 바꿔치기는 여전히 `registry_mismatch` 로 드러난다. |
| V6 | 등록이 없는 브라우저는 "속성이 없습니다" 로 **Google 전에 멈추지 않는다** — 사본은 패스키 뒤에야 받는다. 받고도 비어 있으면 로그인이 `attrs_unset` 으로 멈춘다. | 처음 쓰는 사람이 조건을 거는 서비스부터 가면 Google·패스키를 거친 뒤에 안내를 본다(전에는 그 전에 봤다). |
| V7 | 되찾았으면 이 브라우저의 속성 기록(`/user` "내 속성" 카드가 읽는다)도 그 값으로 맞춘다. 서비스로 가는 응답에는 싣지 않는다. | 기록이 다르면 다음 로그인이 속성을 다시 바꿔 기기끼리 번갈아 교체한다. |
| V8 | 싣지 않는 것: 세션키·세션·거래 기록·증명 기록. 세션은 브라우저마다 따로 만든다. | 세션키를 서버에 두면(암호문이라도) 폐기·만료의 의미가 흐려진다. |

## 3. 바뀐 곳

- `lib/mode3_profile_vault.js`(새 파일): `sealVault`·`openVault`·`isVaultCt`·`vaultDigest`.
- `lib/mode3_wrapper_auth.js`: `issueDigest` 가 `vault` 를 덮는다(없으면 글은 예전과 같다).
- `cia.js`: 발급 본문의 `vault`(모양 검사 → 받아들인 발급에서 `acct.vault`), `POST /cia/wrapper/vault`.
- `mode3/user/core/user_core.js`: 발급에 사본 싣기, `restoreFromVault`, `wrapperLogin` 의 복원(V4)·맞추기(V5), `wrapperAttrsReady`(V6).
- `mode3/user/popup.js`: 속성 기록 맞추기(V7).

## 4. 보안 메모

- 서버·Google 계정만 가진 사람은 사본을 받아도 열지 못한다(키는 salt 에서만 나온다). 열 수 있는 사람은 패스키를 가진 사람이다.
- 서버가 사본을 숨기거나 옛것을 주면: 새 브라우저는 빈(또는 옛) 속성으로 새 `C_u` 를 받는다 — 지금까지의 동작으로 돌아갈 뿐이다. 옛 사본으로 바꿔 끼워도 다른 사람의 사본은 열리지 않는다(`auid` 에 묶였다).
- 사본에는 속성 값이 들어 있다. salt 가 새면(패스키 탈취) 속성도 열린다 — 그때는 계정 전체가 넘어간 것이다.
- 내려주기는 토큰을 쓰지 않으므로 토큰 수명 동안 되풀이해 받을 수 있다. 받는 것은 같은 암호문이다.

## 5. 한계

- **세션·거래 기록·증명 기록은 되찾지 않는다**(V8) — 새 브라우저의 `/user` 는 그 브라우저에서 한 로그인만 보인다.
- 한 번도 로그인(발급)하지 않고 `/user` 에서 속성만 저장한 상태는 사본에 없다 — 사본은 발급 때 올라간다.
- 두 기기가 서로 다른 속성으로 번갈아 저장하면 마지막 발급이 이긴다.
- 패스키가 다른 새 기기(패스키 분실)는 이 사본을 열지 못한다 — 그 길은 salt 봉투(백업)이고, 봉투로 salt 를 되찾은 기기는 같은 salt 라 이 사본을 연다(그 조합은 테스트하지 않았다).
- **휴대폰 패스키(QR·블루투스)는 실제 기기로 확인하지 않았다.** 코드로는 "같은 패스키의 새 브라우저" 와 같은 길이고, 그 길을 가짜 인증기로 테스트했다.
