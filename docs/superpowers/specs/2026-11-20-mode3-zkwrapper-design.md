# Mode 3 — zkWrapper: 별도 IdP 없이 Google 토큰을 세션 토큰으로 (설계 초안)

2026-11-20. 상태: **방향 확정(사용자 "추천대로 해줘") — §8 의 여섯 가지는 추천안으로 정했다. §3·§5 는 독립 검토(Opus)를 받아 §10 의 조건을 반영했다.** 대상 모드: `passkey-web`.

## 0. 사용자 결정(2026-11-20)

사용자 메모(원문):

> 홈페이지 만들어서 zk-Delegation을 쓰려면 어떻게 할지를 플로우로 안내
> 별도 IdP를 만들지 말고, zkWrapper 역할만 하도록 브라우저에서 지원
> RP가 등록하는 시퀀스도 그대로 있어야 함
> pi_idp는 필요없는 것으로 하여 그냥 토큰 발급받고, 래퍼가 session token으로 가공하면서 pi_rp 만들어주기

이어서 정한 것:

- 5100 을 사용자가 접속하는 **별도 서버**로 두고, 4100(zkIdP)의 역할은 없앤다. OIDC 토큰을 받아 세션 토큰으로 가공하는 일(OIDC wrapper)을 5100 이 맡는다.
- 래퍼는 **서명 키를 가진 서버**다(브라우저 코드만으로 Google 서명을 회로 안에서 검증하는 zkLogin 식이 아니다) — 등록부·폐기·개봉이 그대로 남는다.
- **π_RP 는 브라우저에서 만든다** — salt 와 서비스 식별자는 서버로 가지 않는다.
- 받아들인 조건 둘: ① 브라우저는 체인을 **5100 서버를 거치지 않고** 읽는다(§5). ② "5100 이 내려주는 코드는 정직하다" 는 가정이 하나 는다(§5).

## 1. 주체와 역할

| 주체 | 지금 | 바꾼 뒤 |
|---|---|---|
| Google | 일반 OIDC 비교용, 가입 때 이메일 확인(11-20) | **신원 확인 전담.** 계정 = Google 계정(`uid = H(google\|sub)`) |
| zkWrapper(5100) | 사용자 PC 의 정적 페이지 서버(`mode3_user_static.js`) | 홈페이지 + 브라우저 앱(패스키·증명) + **발급 서버**(Google 토큰 검증 → 세션 토큰 서명, 등록부·폐기 게시, 서비스 등록·승인, 개봉) |
| zkIdP(4100, `cia.js`) | 계정·비밀번호·로그인 화면·인증 창, 발급, 게시, 개봉, 서비스 승인 | **없음** |
| 서비스(3100·3101) | zkIdP 공개키와 체인으로 π 검증 | 그대로 — 믿는 공개키·주소가 zkWrapper 것으로 바뀐다 |
| 체인 | 등록부·폐기 목록(캐노니컬) + 거울 | 그대로 — 게시자가 zkWrapper 다 |

## 2. 흐름

### 2.1 서비스 등록(그대로 — 자리만 5100)

1. 운영자가 zkWrapper 홈페이지의 "서비스 등록" 에서 운영자 계정을 만들고 서비스(이름·주소·공개키)를 낸다.
2. zkWrapper 관리자가 승인한다 → 서비스 인증서(arid 포함)가 나온다.
3. 서비스 서버가 인증서를 받아 활성화되고, 팩토리 컨트랙트를 배포한다.

지금 `cia.js` 의 `/cia/register_rp`·`/cia/rp/*`·`/cia/rps`·관리자 승인이 이 일이다 — 주소만 옮긴다.

### 2.2 로그인(처음이든 아니든 같은 길)

1. 서비스 → 브라우저: "zk 로그인" 을 누르면 zkWrapper 창이 뜨고 서비스 인증서와 1회용 난수(r_s·r_rp)를 받는다.
2. 브라우저: 서비스 인증서를 확인한다(zkWrapper 가 승인한 서비스인가).
3. 브라우저: **1회용 요청 키 쌍**(pk_e)을 만든다 — 꺼낼 수 없는 키로, 이 창이 Google 을 다녀오는 동안만 브라우저에 둔다(salt 가 아니다).
4. 브라우저 → Google: 인가 요청. `nonce = "issue:" + H(pk_e)` — 토큰을 이 요청 키에 묶는다. 늘 계정 선택 화면을 거친다(`prompt=select_account` — 화면 없이 지나가는 `prompt=none` 은 쓰지 않는다, §10 C2).
5. Google → 브라우저: ID 토큰(`iss`·`sub`·`aud` = zkWrapper 의 클라이언트 ID). Google 은 어느 서비스인지 모른다.
6. 브라우저: 패스키 → salt(늘 같은 값, 저장하지 않음) → 임시 세션 키(pk_i), 커밋먼트(C_u·C_s), 가명(auid_s·arid_s).
7. 브라우저 → zkWrapper 서버: `{ id_token, pk_e, auid, auid_s, arid_s, C_u, C_s, max_height, chainid, … }` 와 **요청 키의 서명**. π_IdP 는 없다.
8. zkWrapper 서버: 토큰 검증(서명·iss·aud·exp) → `nonce` 가 `H(pk_e)` 인지, 본문 서명이 pk_e 의 것인지 대조 → `uid = H(google|sub)` → 계정이 처음이면 `auid` 를 그 계정에 **고정**하고 등록부에 올려 게시, 아니면 고정된 `auid` 와 같은지 대조 → 세션 토큰(= `(auid_s, arid_s, Cf_u, Cf_s, chainid, allowAgent)` 에 대한 서명)을 돌려주고 `(uid, auid_s)` 를 발급 기록에 남긴다.
9. 브라우저: (처음이면 게시를 기다린 뒤) **π_RP** 를 만든다.
10. 브라우저 → 서비스: PPID·π_RP·서명. 서비스는 증명과 체인의 최신 root·자기 arid 를 확인한다.

패스키는 로그인마다 **한 번**(6)이다. 토큰을 요청 본문이 아니라 요청 키에 묶는 까닭: 본문(가명·커밋먼트)은 salt 가 있어야 만들 수 있는데, Google 을 다녀오면 창이 새로 떠 salt 가 사라진다 —
본문에 묶으면 패스키를 Google 앞뒤로 두 번 묻게 된다. 요청 키로 묶으면 가로챈 토큰은 그 키 없이는 쓰지 못하고, 패스키는 돌아온 뒤 한 번만 묻는다.

### 2.3 그 밖

- **거래**: 그대로(브라우저가 증명·서명, 서비스가 중계). zkWrapper 는 관여하지 않는다.
- **세션 폐기**: 브라우저가 zkWrapper 서버에 폐기를 요청한다 — 본인 확인은 Google 토큰(폐기용 nonce)이다. 지금은 π_IdP 로 한다.
- **계정 폐기**: 본인이 Google 토큰으로, 또는 관리자가.
- **개봉**: 서비스가 그 PPID 의 최신 로그인 증명을 zkWrapper 에 내고, 관리자가 승인하면 발급 기록에서 uid(= Google 계정)를 찾는다 — 11-19 의 "trace tag 없는 개봉" 그대로.

## 3. π_IdP 를 빼도 되는가

π_IdP(`circuits/pi_idp.circom`)가 발급 때 zkIdP 에 증명하던 것과, 빼고 난 뒤 무엇이 그 일을 하는가:

| π_IdP 가 하던 일 | 뺀 뒤 |
|---|---|
| 본인 확인("이 계정 auid 의 s_u 를 안다") | Google ID 토큰 |
| 증명을 이 요청에 묶기(`tag = H(s_u, ctx)`) | 토큰의 `nonce = H(pk_e)` + 요청 본문에 대한 pk_e 의 서명(§2.2) |
| `auid = H(s_u)` | π_RP 가 다시 증명한다(②) — 등록부 리프가 `H(auid, Cf_u)` 라, 틀린 auid 로 등록하면 그 사용자의 π_RP 가 만들어지지 않는다 |
| `auid_s`·`C_s` 가 같은 `r_rp` 로 정형 | π_RP 가 다시 증명한다(②·⑤·⑦) — 틀리게 내면 쓸 수 없는 토큰을 받을 뿐이다 |
| `C_u` 가 그 `uid` 를 담는다 | 잃는다. 다만 11-13 부터 PPID 에 uid 가 없어(`PPID = H(s_u, arid, chainid)`) 서비스 쪽 성질에는 쓰이지 않는다 |

그래서 **π_RP 회로(`pi_cred`)는 그대로 두고**(재빌드 없음) 발급 요청에서 π_IdP 만 뺄 수 있다 — 독립 검토의 결론도 "조건부 예" 다(회로 본문의 제약으로 확인: `pi_cred.circom` 95·105·108·111·173·180행).
다만 위 표는 "받은 토큰을 쓸 수 있는가" 만 본 것이다. **발급 한 번에는 부수효과가 있다** — 발급 기록 추가, C_u 교체(옛 것 은퇴), 등록부 게시. π_IdP 는 "Google 토큰은 있지만 salt 는 없는 쪽" 이
이 부수효과를 일으키지 못하게도 막고 있었다. 그래서 서버에 아래 대조가 꼭 들어간다(전부 서버 쪽 — 회로 변경 없음):

- **계정당 auid 는 하나로 고정한다**(첫 발급 때). 등록부 리프는 요청의 auid 가 아니라 고정된 값으로 만든다 — "Google 계정 하나 = salt 하나 = 서비스마다 PPID 하나".
- **auid_s 는 전체에서 한 번만**: 다른 계정의 발급 기록에 이미 있는 auid_s 로 온 요청은 거절한다. 안 그러면 남의 auid_s 를 주워 자기 계정의 기록에 심어 개봉이 엉뚱한 계정을 가리키게 할 수 있다(§10 C1).
  auid_s 는 서비스보다 래퍼에 먼저 가므로 정직한 요청자가 늘 먼저다. 개봉은 일치가 둘 이상이면 답하지 않고 그렇게 표시한다.
- **"한 auid 는 한 계정"(R11)은 그대로 둔다**(초안의 "푼다" 를 뒤집는다 — auid 는 첫 발급 전에는 어디에도 나가지 않아 선점이 어렵고, 풀면 두 계정에 같은 리프를 넣어 계정 폐기를 피하는 길이 생긴다).
  더해서 **한 번이라도 본 Cf_u 는 다른 계정에서 받지 않는다**(§10 I2).
- **토큰은 한 번만 쓴다**(nonce 1회 소비), **C_u 교체는 계정당 빈도를 제한한다** — 토큰 하나로 등록부를 계속 갈아 끼워 다른 사용자의 로그인을 실패시키지 못하게(§10 I1).
- **래퍼 전용 Google 클라이언트 ID** 와 **지갑 오리진으로만 넘기는 중계**: 서비스가 같은 클라이언트 ID 를 쓰면, 악의적인 서비스가 자기 요청 키의 nonce 로 피해자의 토큰을 받아 피해자 계정에 자기 패스키를 고정할 수 있다(§10 C2).
  서비스의 Google 로그인(일반 OIDC 비교용)은 다른 클라이언트 ID 를 쓴다. 같은 값이면 zkWrapper 는 뜨지 않는다.
- **폐기도 같은 결속**: 세션 폐기·계정 폐기의 토큰도 `nonce = H(pk_e)` 이고, 목적·대상(scope·Cf_s)을 담은 본문에 pk_e 로 서명한다(§10 I3). 서명 본문에는 늘 목적과 서버 주소가 들어간다.
- C_u·C_s 의 부분군 점 검사는 지금 `checkIdpAuth` 안에 있다 — 발급 경로로 옮겨 남긴다.
- **패스키를 잃었을 때**: auid 를 바꾸면 PPID 가 바뀐다 — 관리자가 계정을 지우는 길만 둔다(§8). 계정을 지우면 그 계정의 발급 기록도 사라져 지난 로그인의 개봉이 안 된다(지금 구조와 같다).

## 5. 서비스 식별자가 zkWrapper 서버에 새지 않게

프로토콜 메시지로는 새지 않는다 — 서버가 받는 것은 로그인마다 바뀌는 `arid_s` 뿐이다. 페이지와 발급이 한 서버가 되면서 생기는 옆길:

| 길 | 조치 |
|---|---|
| **체인 읽기**: 지금 브라우저는 체인을 5100 의 `/rpc/app`·`/rpc/rev` 로 읽는다. 그 가운데 서비스별 호출이 있다 — 팩토리의 `computeAddress(PPID)`, 계정 주소의 코드·nonce 조회(거래 준비) | 계정 주소는 브라우저에서 계산하고(CREATE2), 나머지 읽기는 **zkWrapper 가 아닌 RPC**(공개 노드)로 보낸다. 데모에서는 체인 노드의 주소를 브라우저에 직접 준다 |
| **Referer**: 서비스가 창을 열 때 주소가 실려 갈 수 있다 | 서비스 페이지의 `referrer: same-origin`(지금 `mode3/rp.html` 에 있다)을 **연동 필수 항목**으로 안내한다 |
| **내려주는 코드**: salt·서비스 식별자를 다루는 스크립트를 zkWrapper 가 낸다 | 구조로 막지 못한다 — 가정으로 적는다. 번들을 공개하고 해시를 고정해 검증할 수 있게 한다 |
| **서비스 페이지가 래퍼를 직접 부르는 요청**: 지금 서비스 페이지는 지갑 서버의 설정·상태(`/wallet/config`·`/mode3/health`)를 브라우저에서 부른다 — `Origin` 헤더에 서비스가 실린다 | 래퍼 방식에서는 서비스 페이지가 zkWrapper 를 직접 부르지 않는다(필요한 값은 승인 창의 메시지로 받는다) |
| **시간**: 발급 직후 어느 서비스에 세션이 생기는가 | 지금 구조와 같은 한계다 |
| **온체인 거래**: 체인에 PPID 와 서비스 컨트랙트가 남는다 | 지금 스펙(11-19 trace-without-tag §3)에 적힌 대가 그대로다 |

## 6. 홈페이지(5100 의 첫 화면)

- **사용자용**: ① 패스키 만들기 ② 서비스에서 "zk 로그인" ③ Google 계정 고르기 — 세 단계 안내와 "전체 플로우 한 장"(`/common/flow.html`) 링크. 아래에 지금의 zk 클라이언트 화면(연결된 서비스·증명·보관 상태).
- **서비스 운영자용**: ① 등록 ② 승인 ③ 연동(로그인 버튼·검증 엔드포인트·`referrer` 설정) 안내와 등록 화면.
- **관리자**: 승인·계정 표·폐기·개봉(지금 zkIdP 관리자 화면).

## 7. 논문·발표에 미치는 것

- 주체가 넷(사용자·IdP·RP·체인)에서 **Google(IdP)·zkWrapper·RP·체인**으로 읽힌다 — "IdP 는 RP 를 모른다" 는 Google 에 대해서는 구조로(aud 가 zkWrapper), zkWrapper 에 대해서는 `arid_s` 와 §5 의 조건으로 성립한다.
- π_IdP 가 프로토콜에서 빠진다 — 증명은 π_RP 하나다. 발급의 본인 확인은 OIDC 토큰이다.
- 가정이 는다: zkWrapper 가 내려주는 코드의 정직성(§5).
- 데모 시나리오의 "zkIdP 로 가입·로그인" 장면이 "Google 계정으로 zk 로그인" 이 된다.

## 8. 정한 것(2026-11-20 — 사용자 "추천대로 해줘", 아래는 내가 낸 추천안)

1. **범위**: passkey-web 분리 데모만 새 구조로 옮긴다. 스냅·에이전트·web 모드는 지금 동작 그대로 둔다.
   발급 엔진(상태·트리·게시·서비스 등록·개봉)은 `cia.js` 의 것을 **복사하지 않고 그대로 쓴다** — 래퍼 방식은 `cia.js` 에 깃발(`CIA_WRAPPER=1`) 뒤로만 더하고, 깃발이 꺼져 있으면 지금과 같다.
   zkWrapper 서버의 진입점은 새 파일(`mode3_zkwrapper.js`)이다: 래퍼 깃발을 켜고, 지금 `mode3_user_static.js` 가 내던 페이지·번들·회로 파일을 같은 프로세스에서 낸다.
   (처음 추천은 "cia.js 는 건드리지 않는다" 였다 — 2,200줄을 복사해 두 벌로 두는 것보다 깃발 뒤에 더하는 쪽이 고칠 곳이 한 군데라 바꿨다. 기존 모드는 체인 그룹 테스트가 지킨다.)
2. **5100 을 어디에 띄우나**: 먼저 **발표 PC**(지금 자리 — `https://wallet.zkd.test:5100` 이 `127.0.0.1` 을 가리킨다)에서 띄운다. Google 은 `*.zkd.test` 로 돌아오지 못하고 `https://127.0.0.1:5100/google-relay` 로만
   돌아오는데, 같은 서버가 그 중계 화면도 내므로 추가 설정이 없다. 별도 VM 으로 옮기는 것은 그다음 단계다 — `wallet.zkd.test` 를 그 VM 으로 돌리는 `/etc/hosts` 변경과 인증서 배치(사용자 작업),
   발표 PC 에 Google 귀환용 중계 화면만 내는 작은 서버가 필요하다. 공개 도메인을 쓰는 실제 배치에서는 중계가 필요 없다. (패스키의 RP ID 는 어느 쪽이든 `wallet.zkd.test` 그대로다.)
3. **로그인마다 Google**: 그렇다(§2.2). 로그인마다 Google 계정 선택 화면이 한 번 뜬다. Google 은 로그인 시각·횟수를 알고, 어느 서비스인지는 모른다.
4. **패스키 분실**: 사용자가 스스로 바꾸는 길은 두지 않는다. 관리자가 계정을 지우면(지금의 계정 삭제) 다음 로그인이 새 패스키로 다시 등록한다 — PPID 가 바뀐다.
5. **속성**: 기본값(1990·KR)으로 시작하고, 바꿀 때만 속성 도구를 쓴다(11-20 패스키 가입과 같다). zkIdP 프로필의 "이름(속성 커밋먼트)" 칸은 계정 화면과 함께 없어진다.
6. **이름**: 화면의 "zkIdP" 를 "zkWrapper" 로 바꾼다(passkey-web 화면 — 다른 모드의 문구는 그대로).

## 9. 검증 계획(개요)

- 발급: 토큰 nonce 가 요청과 다르면 거절, 다른 계정의 고정 auid 와 다르면 거절, 정상 발급 뒤 π_RP 가 서비스에서 통과.
- π_IdP 없이도 막히는 것: 틀린 auid 로 등록 → π_RP 생성 불가, 남의 `C_s`·`auid_s` 로 발급 → 쓸 수 없는 토큰.
- 체인 읽기가 5100 서버를 지나지 않는다(브라우저 테스트에서 `/rpc/*` 요청 0건).
- 서비스 등록·승인, 폐기, 개봉의 기존 테스트를 새 서버에 대고 돌린다.
- 독립 검토(Opus): §3 의 "π_IdP 를 빼도 되는가" 와 §5.

## 10. 독립 검토 결과(2026-11-20, Opus — 읽기만)

결론: **조건부 예** — π_RP 회로를 바꾸지 않고 π_IdP 를 뺄 수 있다. 회로를 바꿔야 하는 발견은 없고, 아래는 모두 서버 대조·배치 조건이다(§3 에 반영).

| | 발견 | 대응 |
|---|---|---|
| C1 | 남의 auid_s 를 자기 계정의 발급 기록에 심어 개봉이 엉뚱한 계정을 가리키게 한다(개봉은 첫 일치를 돌려준다) | auid_s 전역 유일, 개봉은 모호하면 답하지 않는다 |
| C2 | 서비스와 래퍼가 같은 Google 클라이언트 ID 를 쓰면, 악의적인 서비스가 자기 nonce 로 피해자의 토큰을 받는다 — 미등록 피해자의 계정에 자기 패스키를 고정, 등록된 피해자의 자격증명 은퇴·폐기 | 래퍼 전용 클라이언트 ID(같으면 기동 거부), 지갑 오리진으로만 넘기는 중계, `prompt=none` 금지 |
| I1 | 토큰 하나로 C_u 를 계속 갈아 끼워 등록부를 흔든다 — 다른 사용자의 로그인이 실패 | nonce 1회 소비, C_u 교체 빈도 제한 |
| I2 | R11 을 풀면 두 계정에 같은 리프를 넣어 계정 폐기를 피한다 | R11 유지 + 본 적 있는 Cf_u 는 다른 계정에서 거절 |

이 데모에는 그런 서비스가 없지만, 새 구조로 옮길 때 전용 클라이언트 ID 를 필수로 한다.
