# Mode 3 — 로그인 전체 플로우 카드 · 휴대폰 패스키(QR) (설계, 2026-11-19)

- 상태: **구현됨(2026-11-19, `c0e59fa`).** 결과는 §5, 리뷰 뒤 바꾼 것은 §6.
- 사용자 결정(2026-11-19 예고 작업 둘과 이어진 답): ① "각 동작의 의미를 보여주는 전체 플로우" = **zk 클라이언트 페이지의 카드, 실제 값 포함**, 범위는 **로그인만**.
  ② "Google 휴대폰으로 패스키 관리하는 모습" = **휴대폰으로 인증하기(QR)** — PC 화면의 QR 을 휴대폰으로 찍고 휴대폰에서 확인한다.
- 범위: passkey-web(`https://wallet.zkd.test:5100`). 다른 모드의 동작은 바꾸지 않는다(코어의 기록은 모드와 무관하게 남지만 화면·테스트는 passkey-web 만).
- 비범위: 회로·컨트랙트·zkIdP·서비스. 서비스가 증명을 검증하는 데 걸린 시간(zk 클라이언트는 모른다 — 서비스의 "알려 준 것" 칸이 그 자리다).

## 1. 로그인 전체 플로우

| # | 결정 | 이유 |
|---|---|---|
| F1 | 코어가 **성공한 로그인 한 번**의 단계별 기록을 kv `loginFlow` 에 남긴다(가장 최근 것 하나). `core.loginFlow()` 가 읽는다. | 화면이 "방금 한 로그인" 을 실제 값으로 그린다. 실패한 로그인은 남기지 않는다(중간에 끊긴 기록이 성공한 것처럼 보이지 않게). |
| F2 | 기록은 `{ at, arid, origin, serviceName, totalMs, steps: [{ key, ms, ... }], values }`. **공개값뿐이다** — salt·blind·세션 개인키·난수 n 의 값은 넣지 않는다. | 증명 기록(`proofs`)과 같은 규칙. |
| F3 | 단계(순서대로): `check_service`(서비스 인증서·컨트랙트 확인) · `passkey`(패스키로 s_u — 사람이 누르는 시간 포함, 보관분을 썼으면 `held: true`) · `sync`(체인 읽기) · `random`(난수 n) · `session_key`(임시 키 쌍) · `commit`(C_u·C_s) · `pseudonym`(auid_s·arid_s·요청 바인딩) · `prove_idp`(π_IdP) · `issue`(zkIdP 왕복) · `publish_wait`(등록부 게시 대기 — 기다렸을 때만) · `prove_session`(π_session, 캐시면 `cacheHit`) · `sign`(세션키 서명). | 사용자가 물은 세부(zkp 생성·임시 키 쌍·가명·난수)를 그대로 단계로 둔다. |
| F4 | 시간은 `performance.now()`(없으면 주입된 `now`)로 잰다 — 밀리초 아래까지. | 가명·난수는 0.1ms 안팎이라 `Date.now` 로는 0 이다. |
| F5 | `lib/mode3_wallet.js` 의 `buildIssueRequest` 에 **선택 인자 `onStep(key, ms)`** 를 더한다(안 주면 지금과 같다). | 커밋먼트·가명·π_IdP 가 이 함수 안에서 이어져 밖에서는 나눠 잴 수 없다. |
| F6 | 화면: "로그인 전체 플로우" 카드(`#flowCard`). 세 주체(서비스 · zk 클라이언트 · zkIdP)의 줄 위에 단계를 순서대로 놓고(주고받는 단계는 화살표, 혼자 하는 계산은 상자), 단계마다 **무엇을·왜**(의미)와 실제 값·걸린 시간을 편다. 로그인 전에는 의미만 보인다. 앞뒤에 시간 없는 두 단계(서비스의 로그인 요청 · 서비스로 증명 전달과 검증)를 그린다. | "각 동작의 의미". 그림은 `mode3/common/flow_figure.js` 의 `renderSequence`. |

## 2. 휴대폰 패스키(QR)

| # | 결정 | 이유·한계 |
|---|---|---|
| P1 | 패스키 설정 카드에 **"패스키를 둘 곳"**(이 기기 · 휴대폰) 선택을 둔다. 휴대폰이면 WebAuthn 요청에 `hints: ['hybrid']` 를 실어 Chrome 이 바로 QR 을 띄운다. | 힌트가 없어도 Chrome 창에서 "다른 기기" 를 직접 고를 수 있다 — 힌트는 시연의 손을 줄인다. |
| P2 | 연결할 때 인증기가 알려 준 **공개 정보**(`authenticatorAttachment`·`transports`·동기화 표시 BE/BS)와 고른 곳을 kv `passkey` 에 함께 둔다. 이후의 확인(`get`)은 저장한 `transports`·힌트를 그대로 싣는다. | 다음 로그인부터 Chrome 이 곧장 휴대폰으로 간다. 비밀은 없다. |
| P3 | zk 클라이언트의 패스키 줄에 **어디에 있는 패스키인지**(이 기기 / 다른 기기(휴대폰), 동기화 여부)를 보인다. | "휴대폰으로 패스키를 관리하는 모습" 을 화면에서도 읽히게. |
| P4 | 시연 순서와 준비물을 `docs/MODE3_DEMO_SCRIPT.md` 에 적는다. | 아래 한계. |

**한계·미검증**: 이 PC 에는 블루투스 어댑터가 없다 — QR 연동(하이브리드)은 **USB 블루투스 동글**이 있어야 한다(PC·휴대폰 둘 다 블루투스·인터넷 켬). 실제 휴대폰에서 PRF 가 나오는지,
만들 때 휴대폰을 두 번(만들기 + 확인 계산) 묻는지는 확인하지 못했다 — 자동 테스트는 WebAuthn 스텁으로 옵션과 저장·표시만 본다. 정책 key 에서는 로그인마다 패스키를 새로 확인하므로 로그인마다 휴대폰을 쓴다.

## 5. 구현 결과(2026-11-19)

- 통과: 패스키 모듈 10(새 4), 웹 코어 passkey 31(새 5 — 구현 전에 5건 실패를 확인), passkey-web 브라우저 33(새 3)·증명 로그인 17, 단위 40/40, 지갑 lib 19, 정적 서버 17, 분리 스크립트 19.
- 순서도 모양은 가짜 값으로 그려 넓은 화면(세 줄)·좁은 화면(접힌 목록) 스크린샷으로 확인했다.
- 실행 중인 분리 데모: 지갑 페이지는 호스트 PC 의 정적 서버가 작업 트리(`mode3/user/`·`mode3/common/`·`dist`)를 그대로 내므로 **재배포 없이 새로 고침으로 보인다**(VM 쪽 변경 없음).
- 정한 것: 게시 대기(`publish_wait`)는 새 C_u 가 아니어도 거울 중계가 늦으면 잠깐 기록된다(코어의 기존 대기 조건 그대로). 같은 단계를 두 번 돌면(발급 재시도) 시간을 더한다.
  패스키 단계의 시간은 같은 승인 창(withSalt 범위) 안에서 패스키를 물은 시간이다 — 로그인 함수에 들어오기 전에 물었어도 그 로그인의 것으로 센다.
- **미검증**: 실제 휴대폰·블루투스(QR 연동, PRF, 만들 때 두 번 묻는지). 실제 Chrome 에서 `hints` 가 QR 을 바로 띄우는지. 스냅·에이전트·web 모드의 화면(사용자 지시로 passkey-web 만 테스트).

## 6. 리뷰(2026-11-19, Opus — Critical 0·Important 2·Minor 17) 뒤 바꾼 것

- 기록에 비밀이 새지 않는 것(salt·blind·세션 개인키·PRF 출력 — 값으로도 파생값으로도), XSS 없음(전부 `textContent`), `ops.login` 을 감싼 것이 반환값·오류 전파를 바꾸지 않는 것은 확인됐다.
- **I-1 첫 로그인의 패스키 시간**: 승인 창은 등록과 로그인을 한 범위에서 잇는다 — 패스키는 등록하면서 물었고 그 시간은 `totalMs`(로그인 함수 시작부터) 밖이다. 요약이 "전체 3초 (… 패스키 8초)" 처럼
  부분이 전체보다 크게 나왔다. 코어가 그 경우 passkey 단계에 `before: true` 를 달고, 화면은 "로그인 전에(등록하면서) 확인했습니다 — 전체 시간에는 넣지 않습니다" 로 적으며 전체 대비 막대와 합계에서 뺀다.
- **I-2 단계 설명 넷이 프로토콜과 달랐다**: 난수 n("가로채 다시 보내도 받아들여지지 않게" → 요청을 묶는 값이 겹치지 않게 — 재전송을 막는 것은 `code` 정책의 1회용 코드다), salt("저장하지 않는다" → 어디에도 보내지 않는다,
  이 브라우저에 길어야 10분 암호화 보관), 봉투("zkIdP 는 안을 보지 못한 채" → uid 와 만료 높이는 본다), 게시 대기("새 C_u 일 때만" → 등록부의 반영이 늦을 때도).
- "값은 모두 공개값" 을 "비밀(salt)은 나오지 않는다 — 값마다 누가 아는지는 다르다(uid 는 zkIdP 만, r_rp 는 서비스만)" 로(M-17). F2 의 "난수 n" 은 비밀이 아니다(발급 본문에 평문으로 간다) — 기록에 넣지 않는 것은 그대로다.
- **같이 한 화면 수정**(셀프 리뷰의 남은 생각): 카드를 "보낸 트랜잭션" 위(세션 카드 바로 아래)로 올렸다. 발급 단계는 "zkIdP 에 보낸 것 →"(uid·가명·봉투·만료 높이·π_IdP)과 "← zkIdP 가 돌려준 것"(자격증명·ID 토큰)으로 나눠 적는다
  (`renderSequence` 의 `groups`). 승인 창에 진행 단계를 보이는 것은 하지 않았다 — 로그인 전체가 2~3초라 단계가 읽히기 전에 지나가고, 로그인 경로에 알림 구멍을 더 내야 한다.
- **고치지 않은 것**: `flowRec`·`scopeDerive` 가 모듈 변수라 로그인이 겹치면 섞인다(M-1 — 승인 창이 요청을 하나만 받아 지금은 닿지 않는다), 재지 않는 구간의 "기타" 표시(M-2), 난수 n 을 그림에서 체인 읽기 뒤에 둔 것(M-3),
  C_u·C_s 이름표에 Cf 값(M-5), 데모 변조 토글(`fake_sig` 등)을 건 로그인도 성공으로 기록(M-6), 휴대폰 패스키의 실제 기기 관련(M-9 고른 곳을 인증기 응답이 아니라 선택에서 정한다·M-10 USB 보안 키도 "휴대폰" 으로 표시·
  M-11 "이미 있는 패스키 쓰기" 는 transports 를 저장하지 못한다·M-12 PRF 미지원 안내) — 실제 휴대폰으로 확인한 뒤 함께 손본다.
