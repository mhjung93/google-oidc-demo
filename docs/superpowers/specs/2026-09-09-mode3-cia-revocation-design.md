# Mode 3 — CIA 기반 credential 발급과 폐기 설계

**상태: 설계 확정. 구현 전.**
작성 2026-09-09. 2026-09-09 설계 대화에서 정해진 내용을 옮긴다.

Mode 2(IdP + PS/EdDSA + Groth16 SSO)와 **공존하는 새 흐름**이다. Mode 2 코드·데모·상태
파일은 건드리지 않는다. 진행 중 메모는 `2026-09-09-cia-revocation-redesign-notes.md`이고
이 문서가 그것을 대체한다.

---

## 1. 무엇이 달라지는가

| | Mode 2 (현행) | Mode 3 (이 문서) |
|---|---|---|
| 발급자 | IdP | **CIA** (Credential Issuing Authority) |
| 장기 키 | 사용자 생성 | **CIA가 발급**, `sk_u`를 기억하지 않음 |
| 발급 입력 | JWT / 인가 토큰 | **커밋 `C` + `π_issue`** |
| 유효성 근거 | IdP EdDSA 서명 | **CIA EdDSA 서명** (동일 방식) |
| 폐기 자료구조 | v3 이중 트리(세션층 4,096 샤드 + 계정층 4,096 샤드) | **단일 IMT, 샤딩 없음** |
| 폐기 리프 | 세션 층 / 계정 층 두 종류 | **`H(C)` 한 종류** |
| 폐기 레지스트리 | `RevocationRegistryV4` (전이 검증으로 root 유도) | **CIA 서명 root + 리프 calldata** |
| 체인 구성 | 단일 체인 | **폐기 체인 1개 + 소비 체인 N개** |
| 검증 위치 | 온체인만 | **오프체인(RP 로그인) + 온체인(트랜잭션)** |

핵심 단순화는 **샤딩 제거**다. Mode 2의 복잡함(상위 트리, 컨트랙트 접기, 세션 리셋 보조정리,
전이 증명 회로 2개)은 전부 "트리가 크다"는 전제에서 나왔다. 폐기 리프가 **폐기가 일어날 때만**
생기도록 바꾸면 그 전제가 무너진다.

## 2. 위협 모형과 가정

### 2.1 CIA

**honest-but-curious.** 프로토콜을 정직하게 따르되, 본 것에서 최대한 추론한다.

- 폐기 목록을 정직하게 관리한다. 상대마다 다른 목록을 보여주지 않는다.
- 없는 사람을 폐기하거나 폐기된 사람을 숨기지 않는다.
- **그러나 알게 된 정보는 전부 학습한다.** 따라서 CIA에게 주는 정보를 최소화한다.

**신뢰와 가용성은 별개 축이다.** CIA를 신뢰하더라도 CIA가 죽지 않는다는 보장은 없다.
그래서 **조회는 항상 체인에서** 하고, CIA는 발급 경로에만 필요하다. CIA가 멈추면
새 로그인만 막히고 진행 중인 세션은 계속 동작해야 한다.

### 2.2 범위 밖

- **CIA-RP 담합** — 위협 모형에 넣지 않는다.
- CIA의 능동적 부정(위조 root 게시, 목록 조작).
- 사용자 자신의 credential 자발적 양도(계정 공유). 양도자만 손해를 보고 제3자 피해가 없다.

### 2.3 CIA에게 숨기는 것

| 값 | CIA가 아는가 | 이유 |
|---|---|---|
| `uid` | ○ | 등록부의 주체 |
| `pk_u` | ○ | 등록부 |
| `C` | ○ | 서명해야 하므로 |
| `H(C)` | ○ | `C`를 아니까. **폐기하려면 필요하다** |
| `max_height` | ○ | CIA가 정하는 정책값 |
| `arid` | **✕** | 알면 사용자의 RP 접속 이력 전체를 갖게 된다 |
| `s_u` | **✕** | 알면 `PPID`를 계산해 온체인 활동을 추적할 수 있다 |
| `pk_i`, `blind` | ✕ | `C` 안에 은닉 |

### 2.4 명시적 가정

**동시 로그인 없음.** 사용자가 서로 다른 RP 두 곳에 **같은 블록(12초) 안에** 로그인하지
않는다고 가정한다. 이 가정 위에서 `max_height`를 양자화 없이 공개한다(§7.3).

깨지는 경우: **지갑이 여러 RP 세션을 자동으로 한꺼번에 갱신하는 구현.** 사람은 그러지 않지만
프로그램은 그럴 수 있으므로, 지갑은 세션 발급을 몰아서 하지 않아야 한다.

## 4. credential

### 4.1 구성

```
C          = Commit(uid, arid, s_u, blind, pk_i)          ← Poseidon 커밋. blind 가 은닉을 담당 (§11 실측으로 확정)
credential = (C, max_height, σ_CIA)
             σ_CIA = EdDSA-Poseidon.Sign(sk_CIA, H(C ‖ max_height))
폐기 리프    = H(C)                                       ← Poseidon
PPID       = H(uid, arid, s_u)
```

`max_height`는 **`C` 밖에서 나란히 서명된다.** `C` 안에 숨기면 사용자가 임의로 크게 써넣어도
CIA가 확인할 수 없어 만료가 무력화된다. 반대로 `pk_i`는 `C` **안**에 있어야 한다 —
CIA가 `pk_i`를 보면 체인에 공개된 `pk_i`와 대조해 "이 사용자가 저 RP에 로그인했다"를 알아낸다.
두 값이 정반대 방향을 요구하므로 한 해시에 묶으면 안 된다.

**Mode 2 명명과의 대응.** 구현 시 혼동을 막기 위해 적어 둔다.

| Mode 3 | Mode 2 (`circuits/pi_ppid.circom`) | 뜻 |
|---|---|---|
| `arid` | `rid` (public) | RP 식별자 |
| `s_u` | `salt` (private) | 사용자 비밀. `PPID` 유도에 쓰인다 |
| `blind` | — (Mode 3 신규) | 커밋 블라인딩 |

**`PPID`의 구조는 Mode 2와 동일하다** — `Poseidon(uid, arid, s_u)`는 Mode 2의
`Poseidon(uid, rid, salt)`와 같은 것이다. §10의 6번 정정은 대화 중 제안했던 중간 설계
(`H(uid, arid)`)에 대한 것이며, **Mode 2 구현에는 그 결함이 없다.**

### 4.2 각 항이 하는 일

| 항 | 역할 | 빼면 생기는 일 |
|---|---|---|
| `uid` | 계정 식별. `PPID` 유도 | 지갑 주소를 만들 수 없다 |
| `arid` | RP 스코프 바인딩 | 세션키 하나가 털리면 **모든 RP**가 뚫린다 |
| `s_u` | `PPID`에 CIA가 모르는 비밀을 넣는다 | CIA가 `H(uid, arid)`를 열거해 모든 지갑 주소를 계산한다 |
| `blind` | 커밋 은닉 | CIA가 공개된 `(arid, pk_i)`와 자기가 아는 `uid`로 `C`를 재계산해 대조한다 |
| `pk_i` | 이 π가 이 서명자의 것임을 묶는다 | 남의 π를 주워 자기 키로 서명하면 **완전 사칭**이 된다 |

### 4.3 리프를 `C`로부터 **유도**하는 이유

리프가 `C` 안의 속성이면 사용자가 그 값을 고르므로, 아무 난수나 넣고 "내 건 트리에 없다"고
주장할 수 있다. 막으려면 발급 시 정합성 ZKP가 필요하다.

`H(C)`로 두면 **회로가 비공개 입력 `C`에서 직접 계산**하므로 다른 리프를 들이밀 방법이 없다.
발급 ZKP가 통째로 불필요해진다.

그리고 CIA는 서명하면서 `C`를 보므로 `H(C)`를 계산할 수 있다 — **속성을 하나도 모른 채로
정확히 그 credential만 죽일 수 있다.** `arid`를 모르는 채 폐기가 가능한 것이 이 구조의 핵심이다.

## 5. 증명 π

```
공개 입력   PPID, arid, pk_i, max_height, revRoot, pk_CIA_x, pk_CIA_y   ← 이 순서. 단계 (a)·(b)가 의존
비공개 입력 uid, s_u, blind, σ_CIA(S, R8x, R8y), 비멤버십 witness
             (C 는 입력이 아니라 회로가 계산하는 신호다 — 증명자가 C 를 고를 수 없다)

증명 내용
  ① EdDSA-Poseidon.Verify(pk_CIA, H(C ‖ max_height), σ_CIA) = 1
  ② C = Commit(uid, arid, s_u, blind, pk_i)                    ← 개봉. pk_i·arid는 공개 입력과 일치
  ③ PPID = H(uid, arid, s_u)
  ④ H(C) ∉ IMT(revRoot)                                       ← 비멤버십
```

**검증자의 의무: `pk_CIA_x`, `pk_CIA_y`는 공개 입력이므로 회로는 '어떤 키에 대해 서명이 유효하다'만
증명한다. 검증자(RP 서버, `CredentialVerifier`)는 반드시 이 두 값을 배포 시 고정된 CIA 키와
비교해야 한다. 비교하지 않으면 공격자가 자기 키로 자기 credential 에 서명해 통과한다. circomlib
`EdDSAPoseidonVerifier`는 `Ax/Ay`의 곡선·부분군 검사를 하지 않으므로 이 비교가 유일한 방어선이다.**

**두 검증 경로가 같은 회로, 같은 검증키를 쓴다.** 온체인이 `PPID` 기반 지갑을 쓰기로 했으므로
공개 입력 집합이 일치한다. 용도를 가르는 것은 π가 아니라 Schnorr 서명이 무엇을 덮느냐다.

```
RP 로그인   σ = Schnorr.Sign(sk_i, RP 챌린지)
온체인 실행 σ = Schnorr.Sign(sk_i, txPayload)
π는 공유
```

**π는 재사용한다.** π가 말하는 것은 "root R 기준으로 나는 유효하고 폐기되지 않았다"이므로,
R이 그대로면 다시 증명해도 같은 값이다. 매 요청마다 새로 필요한 것은 **σ뿐**이다
(재생 공격 방지). 자세한 규칙은 §8.4.

## 6. 프로토콜

### 6.1 등록 (1회)

```
1. 사용자 인증 (기존 계정 체계)
2. CIA:   (pk_u, sk_u) 생성 → 사용자에게 전달 → sk_u 폐기
3. 사용자: s_u 무작위 생성
4. 사용자 → CIA: cm_u = Poseidon(s_u, r_u)  (r_u 는 사용자가 보관하는 무작위 블라인딩)
5. CIA:   (uid, pk_u, cm_u, disabled=false) 저장
```

`cm_u`는 **Sybil 방지**를 위해 필요하다. `s_u`를 사용자가 자유롭게 고르면 한 RP에서
여러 개의 `PPID`를 만들어 낼 수 있다. `cm_u`에 고정해 두고 발급 때마다 동일성을 증명한다.

### 6.2 발급 (세션마다)

```
1. 사용자: (pk_i, sk_i) 생성, blind 무작위
           C = Commit(uid, arid, s_u, blind, pk_i)

2. 사용자 → CIA:
     C
     π_issue : ZK 증명 { 공개 입력 (uid, cm_u, C),  witness (arid, s_u, blind, pk_i, r_u) :
                 C    = Poseidon(uid, arid, s_u, blind, pk_i)     ← uid 는 공개 입력 (CIA 가 안다)
               ∧ cm_u = Poseidon(s_u, r_u) }                     ← 등록 시 커밋과 같은 s_u
     Sign(sk_u, C)

3. CIA: 등록된 pk_u 로 서명 검증 (사용자 인증)
        π_issue 검증      ← arid·pk_i·blind 는 여전히 모른다
        disabled == false 확인

4. CIA: max_height = 현재높이 + 300
        σ_CIA = EdDSA-Poseidon.Sign(sk_CIA, H(C ‖ max_height))
        (uid, H(C), max_height) 기록

5. CIA → 사용자: (max_height, σ_CIA)
```

`uid`와 `cm_u`를 공개 입력으로 두면 CIA 는 `arid`·`pk_i`·`blind`를 모른 채로 `C` 가 자기
사용자의 것이고 `s_u` 가 등록된 값임을 확인한다. `π_issue` 는 별도 회로이며 제약 수는
미측정이다(§11). `sk_i` 소지 증명은 넣지 않는다 — `pk_i` 가 secp256k1 주소라 회로 안에서
증명하려면 secp256k1 스칼라곱과 keccak 이 필요해 비용이 수백만 제약이고, 막는 공격(남의
`pk_i` 를 자기 credential 에 넣기)은 `(C, σ_CIA)` 를 그 키 주인에게 건네주어야 성립한다 — 즉
**양도자가 자기 `PPID` 를 남에게 내주는 자해적 위임**이며 제3자 피해가 없다. §2.2 의
"자발적 양도" 항목으로 범위 밖에 둔다.

### 6.3 RP 로그인 (오프체인 검증)

```
1. RP → 지갑:  challenge
2. 지갑:       revRoot 가 최신이 아니면 π 재생성
               σ = Schnorr.Sign(sk_i, challenge)
3. 지갑 → RP:  (π, 공개입력, σ)
4. RP:
     a. L1 헤드를 최근 10분 안에 읽었는가?   아니면 거부      ← fail-closed
     b. π.revRoot == 방금 읽은 root ?        아니면 거부
     c. Groth16 검증
     d. Schnorr 검증 (pk_i, challenge, σ)
     e. PPID 로 사용자 식별
```

### 6.4 온체인 실행

```
PPIDWallet.execute(π, publicInputs, σ, txPayload):
     a. require(revRoot == mirror.currentRoot())     ← 가장 싸고 가장 자주 실패. 먼저
     b. require(block.number <= max_height)
     c. require(PPID == 이 지갑의 PPID)
     d. Groth16 검증                                  ← 가장 비쌈. 마지막
     e. Schnorr 검증 (pk_i, txPayload, σ)
     f. 실행
```

검사 순서가 중요하다. 경합에 지면 Groth16에 들어가기 전에 revert되어 날리는 가스가
약 25만이 아니라 약 3만이 된다.

### 6.5 폐기

```
세션 하나:   트리에 H(C) 삽입
계정 전체:   그 uid 의 미만료 H(C) 전부 삽입 + disabled = true
```

두 장치가 각각 다른 것을 막는다. **트리는 이미 발급되어 회수할 수 없는 credential을 죽이고,
`disabled` 플래그는 새로 태어나는 것을 막는다.** 하나만으로는 안 된다 — 트리만 있으면 공격자가
곧장 재발급받아 부활하고, 플래그만 있으면 이미 나간 세션이 만료까지 살아 있다.

게시:

```
publishRoot(bytes32 newRoot, uint64 epoch, bytes32[] calldata newLeaves, bytes sig)
    require(epoch > lastEpoch)                              ← 재생 방지
    require(recover(H(DOMAIN, newRoot, epoch), sig) == CIA_KEY)
    emit Revoked(epoch, newLeaves)                          ← calldata. 저장하지 않는다
    root = newRoot;  lastEpoch = epoch
```

서명 메시지에 **chainid를 넣지 않는다.** 넣으면 CIA가 체인 수만큼 서명해야 한다. 안 넣으면
한 번 서명한 것을 모든 체인에 뿌릴 수 있고, 같은 root를 다른 체인에 재생하는 것은 공격이 아니라
원하는 동작이다. 도메인 분리는 `DOMAIN` 태그 하나로 충분하다.

**제출자는 아무나여도 된다.** 권한이 서명에 실려 있으므로 릴레이어를 신뢰할 필요가 없고,
검열 저항이 따라온다.

### 6.6 복구

| 사고 | 조치 | 지갑·자산 |
|---|---|---|
| 세션키 `sk_i` 유출 | 그 `H(C)` 폐기 → 즉시 새 credential 발급 | **유지** |
| 계정 침해 | 전체 폐기 + `disabled` → 대역외 확인 후 해제 + 새 `pk_u` | **유지** |
| `s_u`까지 유출 | 새 `s_u` 필요 → `PPID` 변경 → **지갑 변경**. 자산 이전 필요 | **소실** |

`PPID = H(uid, arid, s_u)`이고 폐기·복구에서 바뀌는 것은 `C`, `pk_i`, 필요시 `pk_u`뿐이므로
앞의 두 경우는 **지갑 주소가 그대로 유지되고 잔고가 보존된다.**

세션키 도난 시 죽는 것과 사는 것이 정확히 갈린다:

```
공격자가 sk_i 를 훔침 (π는 체인에 공개되어 있으므로 공격자도 가진다)
  → CIA가 그 C 의 H(C) 만 폐기
  → root 전파 후 공격자의 π 는 비멤버십에 걸려 죽는다
  → 사용자는 새 세션키로 새 C', 새 π' 를 받아 즉시 복귀
  → 공격자는 C' 에 대해 아무것도 없다
```

## 7. 폐기 자료구조와 체인

### 7.1 트리

- **단일 인덱스드 머클 트리.** 샤딩 없음, 층 없음, 태그 없음.
- 리프 = `H(C)`. **폐기가 일어날 때만 생긴다** (발급 때가 아니다).
- **append-only.** 제거를 지원하지 않는다.
- 깊이 32, Poseidon.

**append-only인 이유는 기술적 제약이 아니다.** IMT에서 삭제는 가능하다(선행 리프를 후속으로
다시 잇고 슬롯을 비우면 된다). 만들지 않는 이유는 **쓸 일이 없어서**다:

- 복구는 리프 제거로 표현할 수 없다. 제거하면 사용자와 함께 **공격자도 되살아난다.**
  복구는 새 credential 발급이지 리프 조작이 아니다.
- 계정 폐기는 만료되지 않으므로 뺄 이유가 없다.
- 만료된 credential의 리프는 아무도 조회하지 않으므로 남아도 무해하다.

### 7.2 폐기 체인

**이더리움 L1** (데모는 로컬 hardhat). 이 체인의 존재 이유는 성능이 아니라 **투명성**이다 —
CIA가 목록을 소급해 고치거나 상대마다 다른 것을 보여주지 못하게 한다. 그 성질은 검증자 집합이
크고 독립적일수록 강해지므로, **빠른 앱체인은 오히려 나쁘다** (CIA가 사실상 장악할 수 있어
체인을 둔 의미가 사라진다).

처리량 요구는 하루 몇 건이라 빠른 체인이 줄 것이 없다.

게시 방식은 **CIA 서명 root + 리프 calldata**다. 네 가지 안 중에서:

| | 폐기 1건당 가스 | 무결성 | 데이터 가용성 |
|---|---:|---|---|
| root만 (BAAR 방식) | ~30k | CIA 신뢰 | **CIA에 의존** |
| **root + 리프 calldata** | **~30k** | CIA 신뢰 (사후 감사 가능) | **체인에서 재구성** |
| 온체인 삽입 검증 | ~71k | 체인이 강제 | 체인에서 재구성 |
| ZK 배치 증명 | ~250k+ | 체인이 강제 | 체인에서 재구성 |

리프 하나는 32바이트라 calldata 비용이 512 gas다. root만 올리는 것과 사실상 같은 값에
**누구든 이벤트를 재생해 트리를 재구성**할 수 있게 된다. root만 올리면 사용자가 비멤버십
witness를 만들 데이터를 CIA에서 받아야 하고, **CIA가 죽는 순간 아무도 증명을 만들 수 없다.**

온체인 삽입 검증이나 ZK 배치 증명은 CIA를 못 믿을 때 필요한 것이고, 그 전제가 없으므로
가스를 두 배·여덟 배 쓸 이유가 없다. 배치가 커지면(약 5건 이상) ZK 배치가 유리해지는 지점이
오지만, 지금은 배치당 1건 수준이라 멀다.

### 7.3 root 전달

컨트랙트는 다른 체인을 읽을 수 없다(외부 I/O가 없는 결정적 상태 기계다). 체인 간 데이터는
항상 **밀어 넣는** 방식이다.

**CIA가 각 소비 체인에 배포**한 컨트랙트가 CIA 서명을 검증해 root를 받는다. CIA가 직접
배포하므로 신뢰 앵커(CIA 공개키)가 배포 시점에 코드에 박히고, 설정으로 바뀌는 경로가 없다.

```
CIA가 각 체인에 배포:
  RevocationMirror     submitRoot(root, epoch, sig) / currentRoot()
  CredentialVerifier   verify(π, publicInputs) → (PPID, pk_i)
RP·지갑 컨트랙트는 CredentialVerifier 만 호출한다
```

이렇게 두면 회로를 고칠 때 RP 쪽 코드를 건드리지 않는다. 파라미터도 전부 이 둘 안에만 있다.

**라이트 클라이언트나 zk 라이트 클라이언트를 쓰지 않는다.** CIA는 폐기 목록의 유일한 권위라
CIA보다 강한 브리지를 붙여도 얻는 것이 없다 — CIA가 root를 위조해 누군가를 되살릴 수 있다
해도 애초에 폐기를 안 하면 그만이고, 없는 사람을 폐기하는 것도 진짜 체인에서 똑같이 할 수 있다.
**CIA의 equivocation은 CIA가 이미 할 수 있는 것 이상을 주지 않는다.**

**예외:** 폐기 체인이 L1이고 소비 체인이 그 위의 롤업이면, 롤업은 L1 상태를 프로토콜 차원에서
검증된 형태로 읽을 수 있으므로 **CIA 서명 없이 root가 건너간다.** 그 배치에서는 서명 경로를
생략할 수 있다.

## 8. 파라미터

```
TTL         = 300 블록 (1시간)          이더리움 12초/슬롯 → 3600/12
max_height  = 발급높이 + 300            양자화 없음
N           = 1                        최신 root만 받는다. 경합 여유 0
P           = 배칭 창 ≈ 2.5분           = 실효 폐기 지연
폐기 체인    = 이더리움 L1
fail 정책    = fail-closed
                오프체인: L1 헤드 신선도 10분
                온체인:   max_height 가 상한 (하트비트 없음)
V           = 없음                     root 일치 규칙이 대신한다
```

### 8.1 `P` — 왜 2.5분인가

`P`는 **게시 사이의 최소 간격 = 배칭 창**이다. 고정 주기가 아니다 — root는 폐기가 실제로
일어났을 때만 바뀌므로, 조용한 구간에서는 게시도 비용도 0이다.

**하한은 폐기 체인의 확정성이 정한다.** 폐기가 들어간 블록이 확정되기 전에 그 root를 소비
체인에 뿌렸는데 재구성(reorg)으로 그 트랜잭션이 빠지면, 미러들은 존재하지 않는 트리 상태의
root를 들고 있게 된다. 그런데 미러의 epoch가 단조 증가라 **되돌릴 수 없고**, 더 높은 epoch로
덮어쓰는 사이에 정상 사용자들이 막힌다.

| 폐기 체인 | `P` 하한 |
|---|---|
| 이더리움 L1, 완전 확정 (2 에폭) | 약 13분 |
| **이더리움 L1, 확률적 확정 12블록** | **약 2.5분** |
| 빠른 확정 체인 | 수 초 |

**오프체인 경로만 보면 이 제약이 없다** — RP는 현재 상태를 읽을 뿐이라 reorg가 나면 다음에
읽을 때 바로잡히고, 되돌릴 수 없는 상태가 어디에도 남지 않는다. 확정성이 걸리는 것은
온체인 미러 때문이다.

`P = 2.5분`은 L1 확률적 확정(12블록)을 택한 값이다. 이때 포화 시 실패 확률 상한이 20%인데
(§8.3), 그 수준에 닿으려면 하루 폐기가 576건을 넘어야 하고 이는 사용자 500만 명 규모다.
그 구간에 가면 `P`를 5~10분으로 올려 상한을 10~5%로 묶는다. **`P`는 컨트랙트 상수가 아니라
릴레이어의 운영 설정이므로 재배포 없이 조정할 수 있다.**

### 8.2 `N = 1` — 최신 root만

경합 여유는 `(N−1)·P`이므로 `N=1`이면 **정의상 0**이다. 여유를 준다는 것은 최신이 아닌 root를
받는다는 뜻이고, 그만큼 폐기된 사용자가 더 산다. 트랜잭션 단위로 정확히 0이다 — root 갱신
트랜잭션과 사용자 트랜잭션이 같은 블록에 들어가면 순서가 앞선 쪽이 이긴다.

**대신 실패를 싸게 만든다.** §6.4의 검사 순서로 조기 revert시켜 약 3만 가스로 줄이고,
지갑은 root를 최대한 늦게 읽고 실패 시 자동 재시도한다.

오프체인 경로에서는 날릴 가스 자체가 없다 — RP가 거절하면 0.5초 재증명해서 다시 내면 된다.

### 8.3 실패 확률

인플라이트 창 `T` = root를 읽은 시각부터 트랜잭션이 포함되는 시각 ≈ 30초
(증명 0.5초 + 전파·포함 12~36초).

**저부하(폐기가 드문 구간).** root 변경을 하루 `R`회의 포아송으로 보면

```
P_실패 = 1 − exp(−R·T/86400)
```

| 사용자 수 | 하루 폐기 `R` (0.01%/일) | 트랜잭션당 실패 확률 |
|---:|---:|---:|
| 1만 | 1 | 0.03% |
| 10만 | 10 | 0.35% |
| 100만 | 100 | 3.4% |
| 300만 | 300 | 9.9% |

**포화(폐기가 잦아 배칭이 걸리는 구간).** 게시가 `P` 간격으로 강제되어 등간격에 가까워지므로
사용자의 창 `T`가 그 일정에 균등하게 놓인다고 보면

```
P_실패 ≤ min(1, T/P)
```

| `P` | 폐기 지연 상한 | 실패 확률 상한 (`T=30s`) |
|---|---:|---:|
| 1분 | 1분 | 50% |
| 2.5분 | 2.5분 | 20% |
| 5분 | 5분 | 10% |
| 10분 | 10분 | 5% |

설계 규칙: **`P ≥ T / 목표 실패율`.** 목표 실패율을 1% 아래로 가져가려면 `P`가 아니라
`T`를 줄여야 한다(제출 직전 root 재확인, 빠른 포함).

`T`는 주어진 값이 아니라 **지갑이 지키기로 하는 규율**이다. 세션 초반에 만든 π를 몇 분 뒤에
그대로 내면 `T`가 그만큼 부풀어 실패 확률이 비례해 오른다. **"제출 직전 root 재확인"을
지갑 요구사항으로 명시한다.**

### 8.4 재증명 규칙 — 별도 주기를 두지 않는다

> **π의 `revRoot`는 검증자가 지금 인정하는 root와 같아야 한다.**

`N=1`이라 온체인은 이미 이것을 강제한다. RP도 같은 규칙을 쓴다. 그러면 **재검증 주기라는
파라미터가 필요 없다.**

```
매 요청마다      새 Schnorr 서명 σ      ← 재생 공격 방지. 비용 무시 가능
root가 바뀔 때만  새 π                   ← 폐기 신선도
```

σ가 "이 요청을 지금 내가 승인한다"를 말하고, π가 "나는 유효하다"를 말한다. 앞의 것은 매번
새로워야 하고 뒤의 것은 root가 바뀔 때만 새로우면 된다.

root는 폐기가 있을 때만, 그것도 `P`마다 최대 한 번 바뀐다:

| 하루 폐기 배치 | 세션(1시간)당 재증명 횟수 |
|---:|---:|
| 10 | 0.4회 |
| 100 | 4회 |
| 576 (`P=2.5분` 포화) | 24회 — 천장 |

### 8.5 fail-closed

| | fail-open | fail-closed (채택) |
|---|---|---|
| root를 못 읽거나 오래됐을 때 | 마지막 root로 진행 | 거부 |
| 폐기된 사용자 | **통과함** | 막힘 |
| 실패의 성격 | 조용함 — 아무도 모름 | 시끄러움 — 즉시 드러남 |

인증 시스템에서 "폐기된 사람이 조용히 들어오고 있다"는 "로그인이 안 된다"보다 나쁘다.
후자는 곧 고쳐지고 전자는 오래 간다.

**오프체인은 공짜다.** RP가 체인을 직접 읽으므로 **블록 헤드**를 본다. root가 안 바뀌어도
체인이 살아 있다는 것을 헤드 높이로 알 수 있어 하트비트가 필요 없다. 임계값 10분은
일상적인 RPC 지연을 흡수할 만큼 여유 있게 잡되, **그 값이 곧 "폐기가 무력화될 수 있는
최대 시간"**임을 유의한다.

**온체인은 이미 절반이 fail-closed다.** 소비 체인의 컨트랙트는 폐기 체인의 헤드를 볼 수
없어 오프체인의 방법을 쓸 수 없지만, `max_height`가 그 역할을 한다. 릴레이가 끊겨도
폐기된 사용자의 credential은 발급 시점에 박힌 마감선에서 죽고, CIA가 새 credential을
안 내주니 갱신도 못 한다.

```
withholding 공격의 최대 노출 = TTL = 1시간
```

**어떤 방해로도 credential을 TTL 너머로 늘릴 수 없다.** 만료가 credential 안에 들어 있어
외부 전달에 의존하지 않기 때문이다.

더 조이려면 하트비트(`H`마다 같은 root 재게시 + `2H` staleness 검사)가 필요한데,
`H=10분`이면 노출이 20분으로 줄지만 소비 체인당 하루 144 트랜잭션이 붙는다.
**소비 체인이 L2면 넣고, L1이면 넣지 않는다.** 초기 구현에서는 넣지 않는다.

## 9. 기각한 대안과 이유

### 9.1 유효성 근거 — 누적기 멤버십(BAAR) vs CIA 서명

**CIA 서명을 택했다.** 갱신율이 10,000배 갈린다.

| | 내 샤드/트리 갱신 빈도 | 캐시된 증명 수명 |
|---|--:|--:|
| 비멤버십 (폐기 0.01%/일) | 드묾 | 시간 단위 |
| 멤버십 (발급마다 root 변경) | 블록당 여러 번 | 1블록 미만 |

멤버십은 트랜잭션마다 재증명 + CIA 왕복을 받아들일 때만 성립하고, 그러면 **CIA가 모든
트랜잭션의 가용성 의존**이 된다. BAAR은 이 부담을 "users coordinate with the CIA to refresh
their Merkle witnesses" 한 줄로 넘긴다.

BAAR에는 CIA 서명이 없다(유효성 = 누적기 멤버십, `σ`는 사용자의 임시키 Schnorr 서명이다).
따라서 **CIA 서명 도입은 BAAR로부터의 의도적 변경**이며 논문에 그렇게 적어야 한다.

### 9.2 폐기 단위

계정 단위 → credential 단위(`H(C)`)로 정착했다. 계정 단위에서 시작했으나, 리프를 `H(C)`로
두면 CIA가 `arid`를 모른 채로도 정확히 그 credential만 죽일 수 있고, 계정 전체 폐기는
그 uid의 미만료 `H(C)`를 전부 삽입하는 것으로 처리된다. 폐기는 드물고 N은 보통 한 자릿수인
반면 **회로의 머클 경로는 모든 사용자가 매 세션 지불**하므로, 드문 쪽을 비싸게 하고 잦은 쪽을
싸게 하는 것이 맞다.

계층 구조(세션층 + 계정층)는 Mode 2가 없애려던 복잡도를 그대로 되살리므로 기각.

### 9.3 `rid` — 두 번 도입했다가 둘 다 폐기

`rid_cred`(= `H(uid, arid, salt)`)와 `rid_acct`(계정당 무작위)를 만들었으나 `H(C)`가 둘 다
대체했다. `H(C)`는 CIA가 이미 알고 회로가 직접 계산하므로, 발급 ZKP도 리프 종류 태그도
사용자가 장기 보관할 값도 필요 없다. **`rid`라는 이름의 값은 최종 설계에 없다.**

### 9.4 샤딩

불필요. 리프가 폐기 시에만 생기므로 트리가 작다. 샤딩하면 샤드 인덱스가 공개되어
**CIA에 대한 누출**이 된다(CIA는 `H(C)`를 알므로 인덱스를 계산할 수 있고, 트랜잭션마다
후보를 좁힌다). Mode 2의 복잡도 대부분이 여기서 나왔다.

### 9.5 `max_height` 양자화 (`Q`)

**도입하지 않는다.** `Q`는 `max_height`가 준식별자가 되는 것을 막기 위한 것이었으나,
§2.4의 "동시 로그인 없음" 가정 아래에서는 신호가 성립하지 않는다(로그인이 몇 분만 떨어져도
값이 달라 일치하지 않는다). 빼면 **수명이 정확히 300블록으로 고정**되는 이득도 따라온다
(`Q`가 있으면 1~2시간으로 흔들린다).

남는 노출: 거의 동시에 시작된 두 세션 사이에 우도비 약 300의 상관 신호. 후보를 1/300로
좁히는 효과이며 식별을 성립시키지는 않는다. 온체인 검증 경로에서만 제3자에게 보인다.

### 9.6 `N ≥ 2` (수용 창)

기각. 체인마다 root가 다른 것은 문제가 되지 않는다 — 트랜잭션은 한 체인을 대상으로 하고
지갑이 그 체인의 현재 root에 맞춰 증명하면 된다. `N=1`의 비용은 경합뿐이고 §8.3에서
정량화된 수준이다.

### 9.7 `H(C)`를 RP에 공개

기각. 공개하면 RP가 트리를 직접 확인해 재증명이 0이 되지만, §8.4의 root 일치 규칙으로도
지연은 같고 재증명은 폐기가 있을 때만이라 **얻는 것이 없다.** 회로가 어차피 `H(C)`를 내부에서
계산하므로 숨기는 비용이 0이다. 공짜인 쪽을 버리고 정보를 내줄 이유가 없다.

### 9.8 `arid`를 CIA에 공개

기각. `C`가 단순 해시가 되어 회로가 가벼워지지만, CIA가 `(uid, arid)`를 갖게 되면
사용자의 RP 접속 이력 전체를 알게 되고, `s_u`가 없다면 `PPID`까지 계산해 온체인 활동을
실명으로 추적할 수 있다. honest-but-curious 모형에서 **준 정보는 곧 학습된 정보다.**

### 9.9 RP가 CIA에 매번 조회

기각. ① CIA가 죽으면 모든 RP의 모든 요청이 멈춘다. ② 매번 CIA에게 물으면 CIA의 말이 곧
진실이 되어 **폐기 체인이 장식이 된다.** ③ CIA가 모든 사용자의 활동을 실시간으로 본다.
**신뢰 여부와 무관하게 조회는 체인에서 한다.**

### 9.10 `arid` 공개 노출 (감수)

`arid`는 π의 공개 입력이라 온체인 경로에서는 관찰자가 지갑이 어느 RP 소속인지 본다. Mode 2는
`rid`를 비공개로 두고 `arid_i`만 공개했다. Mode 3는 지갑이 RP마다 별개(`PPID` 기반)라 소속
자체가 주소 구조에서 드러나므로 추가 손실이 없다고 보고 감수한다.

## 10. 설계 대화 중 정정한 것

구현할 때 잘못된 근거를 되살리지 않도록 남긴다.

1. **"하트비트를 넣으면 폐기 발생 타이밍 누출이 사라진다"** — 틀렸다. 하트비트는 같은 root를,
   폐기는 새 root를 올리므로 관찰자가 그냥 구별한다. 하트비트가 해결하는 것은 withholding
   탐지(fail-closed)뿐이다. **"폐기가 언제 일어났는지는 공개된다. 누구인지는 숨는다"**가
   감수 사항이다.
2. **`P_실패 ≤ 1−exp(−(1440/P)·T/86400)`** — 틀렸다. 포화 상태의 게시는 등간격에 가까워
   포아송보다 나쁘다. 올바른 상한은 `min(1, T/P)`이며, 이전 값은 과소평가였다.
3. **"`max_height` 상관이 `arid` 은닉을 무력화한다"** — 과장이었다. 우도비 약 300의
   상관 신호이지 식별이 아니다.
4. **"체인 간 공통 root가 없으면 곤란하다"** — 과장이었다. 하나의 π를 여러 체인에 재사용하는
   전제에 기댄 논거였고, 그 전제가 필요한 상황이 드물다.
5. **"두 검증 경로는 서로 다른 회로가 필요하다"** — 온체인이 `PPID` 기반 지갑을 쓰기로 하면
   공개 입력 집합이 일치하므로 **회로 하나로 통합된다.**
6. **`PPID = H(uid, arid)`** — CIA가 `uid`를 알고 `arid`는 공개 RP 식별자이므로 **CIA가
   모든 RP에 대해 열거할 수 있었다.** 발급 시 `arid`를 가려도 소용이 없다(사건은 가려지지만
   대응 관계는 계산된다). `s_u`를 넣어 고쳤다. **이 결함은 대화 중 제안했던 중간 설계에만 있었고, Mode 2의
`pi_ppid.circom`은 처음부터 `Poseidon(uid, rid, salt)`로 사용자 비밀을 포함하고 있다.**
7. **"append-only라서 재기준화가 필요하다"** — 인과가 반대다. 리프를 뺄 수 있어도 복구는
   새 credential 발급이어야 한다. 제거는 공격자까지 되살리기 때문이다.

## 12. 구현 단계

**(c) → (a) → (b) 순서.** 회로가 이 설계의 심장이고, 제약 수와 증명 시간이 나와야
나머지 판단(재증명 빈도가 감당 가능한지, 온체인 가스가 얼마인지)이 근거를 갖는다.

### (c) 회로

- `circuits/mode3/pi_cred.circom` — §5의 ①~④
- 제약 수, 증명 시간, 검증키 크기 측정
- 회로 컴파일·셋업은 **별도 승인 후** 실행 (오래 걸리고 기존 산출물에 영향)

### (a) 오프체인 전 구간

- circuits/pi_issue.circom — §6.2 의 발급 증명. C 개봉 + cm_u 동일성. **제약 수를 (a) 의 첫 태스크로 잰다.** 두 번째 zkey·검증키·(필요 시 더 큰 ptau)·CIA 측 Groth16 검증 경로가 함께 붙는다
- `cia.js` — 등록, 발급, 폐기, 트리 관리, root 게시 (Mode 2의 `custom_idp.js`는 손대지 않는다)
- 폐기 체인 컨트랙트 (`RevocationLog`) + 로컬 hardhat 배포
- RP 로그인 검증 (오프체인 Groth16 + 신선도 + Schnorr)
- 지갑 측: 트리 전체 동기화, 위트니스 로컬 생성, π 캐시와 root 일치 확인

### (b) 온체인 실행

- `RevocationMirror`, `CredentialVerifier` (CIA가 배포)
- `PPIDWallet` 연동, §6.4의 검사 순서
- 가스 실측

### 제약

- **Mode 2 데모를 건드리지 않는다.** 별도 포트, 별도 상태 파일. 실행 중인 `custom_idp.js`(:4000)와
  `idp_state.json`은 손대지 않는다.
- 회로 재생성(`zk:compile`, `zk:key`)은 사용자 승인 후에만.
- 새 테스트는 `scripts/run_tests.sh`의 해당 그룹에 등록한다.
