# Mode 3 — CIA 기반 credential 발급과 폐기 설계

**상태: 설계 확정. 구현 전.**
작성 2026-09-09. 2026-09-09 설계 대화에서 정해진 내용을 옮긴다.

**개정 2026-09-10 — 두 가지 독립적인 변경이 있었다.**

**(1) 온체인 검증 경로를 기각했다(§9.11).** Mode 3는 오프체인(RP 로그인) 검증만 한다.
그에 따라 §3·§5·§6.4·§6.6·§7.3·§8.1~8.5·§9.5·§9.10·§11·§12가 바뀌었고, 계정 폐기의
묶음 노출(§9.12)이 미결 항목으로 추가되었다.

**(2) 커밋 스킴을 교과서 Pedersen 으로, 발급 PoK 를 시그마 프로토콜로 바꿨다.** 스칼라
상한 2²⁵⁰(§4.1)이 도입되었고, §4.1/§6.1/§6.2/§11/§12가 그에 따라 바뀌었다.

두 변경은 서로 다른 이유에서 나왔고 독립적으로 되돌릴 수 있다.

**개정 2026-09-14 — 사용자 개시 폐기를 추가했다(§6.5.1).** 계정 비밀번호로 인증하는 자기 폐기
경로다. 컨트랙트·회로·게시 경로는 바뀌지 않는다.

**개정 2026-09-14 (2) — 속성 credential 설계가 §4.1·§5·§6.2·§6.3 을 대체한다.** 커밋에 속성 슬롯 4개,
서명 메시지 `(C, exptime, chainid, nonce)`, 벽시계 만료, nonce 기반 재생 방지. 본문은
`2026-09-14-mode3-attribute-credential-design.md` 에 있고, 이 문서의 해당 절은 옛 형식의 기록으로 남긴다. 회로(`pi_cred.circom`)
자체는 어느 쪽으로도 바뀌지 않았지만(2026-09-14 속성 credential 개정에서는 회로가 바뀌었다 — 아래 개정 (2)), §11.1의
실측값은 (2)를 반영해 Pedersen 판으로 다시 쟀다(`8c3e65b`).

**개정 2026-09-15 — 세션 성명·서비스 인증서 설계(`2026-09-15-mode3-session-statement-design.md`)가 §2.2·§2.3 의 일부와
§8.4 를 대체한다.** 성명이 서비스의 `r_s` 를 임베딩하고(발표 자료 8장), CIA↔RP 조건부 추적 가능성이 명시되며, 성명 재사용은
세션 안으로 좁아진다.

Mode 2(IdP + PS/EdDSA + Groth16 SSO)와 **공존하는 새 흐름**이다. Mode 2 코드·데모·상태
파일은 건드리지 않는다. 진행 중 메모는 `2026-09-09-cia-revocation-redesign-notes.md`이고
이 문서가 그것을 대체한다.

## 1. 무엇이 달라지는가

| | Mode 2 (현행) | Mode 3 (이 문서) |
|---|---|---|
| 발급자 | IdP | **CIA** (Credential Issuing Authority) |
| 장기 키 | 사용자 생성 | **CIA가 발급**, `sk_u`를 기억하지 않음 |
| 발급 입력 | JWT / 인가 토큰 | **커밋 `C` + `π_issue`** |
| 유효성 근거 | IdP EdDSA 서명 | **CIA EdDSA 서명** (동일 방식) |
| 폐기 자료구조 | v3 이중 트리(세션층 4,096 샤드 + 계정층 4,096 샤드) | **단일 IMT, 샤딩 없음** |
| 폐기 리프 | 세션 층 / 계정 층 두 종류 | **`H(C)` 한 종류** |
| 폐기 레지스트리 | `RevocationRegistryV4` (전이 검증으로 root 유도) | **CIA 서명 root + 리프 calldata** |
| 체인 구성 | 단일 체인 | **폐기 체인 1개** (소비 체인 없음 — §9.11) |
| 검증 위치 | 온체인만 | **오프체인(RP 로그인)만** (§9.11) |

핵심 단순화는 **샤딩 제거**다. Mode 2의 복잡함(상위 트리, 컨트랙트 접기, 세션 리셋 보조정리,
전이 증명 회로 2개)은 전부 "트리가 크다"는 전제에서 나왔다. 폐기 리프가 **폐기가 일어날 때만**
생기도록 바꾸면 그 전제가 무너진다.

## 2. 위협 모형과 가정

### 2.1 CIA

**honest-but-curious.** 프로토콜을 정직하게 따르되, 본 것에서 최대한 추론한다.

- 폐기 목록을 정직하게 관리한다. 상대마다 다른 목록을 보여주지 않는다.
- 없는 사람을 폐기하거나 폐기된 사람을 숨기지 않는다.
- **그러나 알게 된 정보는 전부 학습한다.** 따라서 CIA에게 주는 정보를 최소화한다.

**신뢰와 가용성은 별개 축이다.** CIA를 신뢰하더라도 CIA가 죽지 않는다는 보장은 없다.
그래서 **조회는 항상 체인에서** 하고, CIA는 발급 경로에만 필요하다. CIA가 멈추면
새 로그인만 막히고 진행 중인 세션은 계속 동작해야 한다.

### 2.2 범위 밖

- **CIA-RP 담합** — 위협 모형에 넣지 않는다. (2026-09-16 개정: **승인된 개봉**으로 모델에 넣는다 — `2026-09-16-mode3-authorized-opening-design.md` §2. 로그인마다 지갑이 2-of-2 트레이스 태그를 증명 공개 입력에 넣고, 서비스 조각 + CIA 조각 + 운영자 승인이 있어야 세션 하나의 uid 가 열린다.)
- CIA의 능동적 부정(위조 root 게시, 목록 조작).
- 사용자 자신의 credential 자발적 양도(계정 공유). 양도자만 손해를 보고 제3자 피해가 없다.

### 2.3 CIA에게 숨기는 것

| 값 | CIA가 아는가 | 이유 |
|---|---|---|
| `uid` | ○ | 등록부의 주체 |
| `pk_u` | ○ | 등록부 |
| `C` | ○ | 서명해야 하므로 |
| `H(C)` | ○ | `C`를 아니까. **폐기하려면 필요하다** |
| `max_height` | ○ | CIA가 정하는 정책값 |
| `arid` | **✕** | 알면 사용자의 RP 접속 이력 전체를 갖게 된다 |
| `s_u` | **✕** | 알면 `PPID`를 계산해 이 사용자의 RP별 신원을 전부 열거할 수 있다 |
| `pk_i`, `blind` | ✕ | `C` 안에 은닉 |

### 2.4 명시적 가정

**동시 로그인 없음.** 사용자가 서로 다른 RP 두 곳에 **같은 블록(12초) 안에** 로그인하지
않는다고 가정한다. 이 가정 위에서 `max_height`를 양자화 없이 공개한다(§9.5).

깨지는 경우: **지갑이 여러 RP 세션을 자동으로 한꺼번에 갱신하는 구현.** 사람은 그러지 않지만
프로그램은 그럴 수 있으므로, 지갑은 세션 발급을 몰아서 하지 않아야 한다.

## 4. credential

### 4.1 구성

```
C_pt       = uid·G₁ + arid·G₂ + s_u·G₃ + pk_i·G₄ + blind·H   ← 교과서 Pedersen 벡터 커밋 (곡선 점). blind 가 은닉을 담당
C          = Poseidon(C_pt.x, C_pt.y)                        ← 점을 필드 원소로 압축 (회로의 Cf)
credential = (C, max_height, σ_CIA)
             σ_CIA = EdDSA-Poseidon.Sign(sk_CIA, Poseidon(DOMAIN_MODE3_CRED, C, max_height))
폐기 리프    = mask₂₅₂(Poseidon(TAG_MODE3_CRED, C))   TAG_MODE3_CRED = 3, 하위 252비트 마스킹 (회로 LessThan(252) 규약)
             (이 문서의 `H(C)` 는 이 리프 값의 약칭이다 — `credLeaf(C)`)
PPID       = H(uid, arid, s_u)
```

DOMAIN_MODE3_CRED = 1426111059989523219780 ("MODE3CRED" 빅엔디언). Mode 2 의
DOMAIN_IDP_TOKEN 과 갈라 두어 서명이 모드를 넘어 재사용되지 않는다. 태그 3 은 Mode 2 의
TAG_SESSION=1, TAG_ACCOUNT=2 와 갈라 둔 것이다.

**이 문서에서 `C` 는 압축된 필드 원소를 가리킨다.** 커밋 자체는 곡선 점 `C_pt` 지만, 서명
메시지와 폐기 리프는 압축값 `C` 를 쓴다. 덕분에 리프 규약과 서명 메시지 모양이 Poseidon 판과
같아서, **나중에 Poseidon 커밋으로 되돌려도 바뀌는 것은 `C_pt` → `C` 블록 하나뿐이다.**
압축 해시 한 번(약 240 제약)이 그 대가다.

커밋 스킴을 Pedersen 으로 둔 이유는 발급 PoK 를 시그마 프로토콜로 짜기 위해서다(§6.2, §11).
show 회로 비용만 보면 Poseidon 이 싸다 — 실측 비교는 §11.1.

**스칼라 상한 2²⁵⁰.** `uid, arid, s_u, pk_i, blind`(그리고 §6.1 의 `r_u`) 는 모두 `[0, 2²⁵⁰)`
이어야 한다. baby jubjub 소수 부분군 위수 `r` 은 251비트라 `2²⁵⁰ < r` 이고, 이 상한이 없으면
`e` 와 `e+r` 이 같은 점을 만들어 한 `C_pt` 를 두 `s_u` 로 열 수 있다(Sybil). 회로는
`Num2Bits(250)` 으로, `lib/mode3_credential.js` 의 `credCommit` 은 throw 로 강제한다.
**무작위 비밀(`s_u`, `blind`, `r_u`)은 반드시 `randomScalar()` 로 뽑는다** — 필드 전체 난수를
쓰면 약 92% 가 거부된다(`2²⁵⁰/p ≈ 0.083`). Mode 2 의 `valueToField()` 규약을 그대로 가져오면 안 된다.

`max_height`는 **`C` 밖에서 나란히 서명된다.** `C` 안에 숨기면 사용자가 임의로 크게 써넣어도
CIA가 확인할 수 없어 만료가 무력화된다. 반대로 `pk_i`는 `C` **안**에 있어야 한다 — 근거는
두 가지다. (1) **심층 방어**: RP 로그가 유출되면 `(arid, pk_i)` 가 밖으로 나오는데, CIA 가
`pk_i` 를 알고 있었다면 그 유출만으로 `uid ↔ RP` 가 이어진다. (2) **온체인 재도입 대비**
(§9.11) — 되돌리면 `pk_i` 는 다시 체인에 공개되고, CIA가 그것과 대조해 "이 사용자가 저
RP에 로그인했다"를 알아낼 수 있다. 두 값이 정반대 방향을 요구하므로 한 해시에 묶으면 안 된다.

**Mode 2 명명과의 대응.** 구현 시 혼동을 막기 위해 적어 둔다.

| Mode 3 | Mode 2 (`circuits/pi_ppid.circom`) | 뜻 |
|---|---|---|
| `arid` | `rid` (public) | RP 식별자 |
| `s_u` | `salt` (private) | 사용자 비밀. `PPID` 유도에 쓰인다 |
| `blind` | — (Mode 3 신규) | 커밋 블라인딩 |

**`PPID`의 구조는 Mode 2와 동일하다** — `Poseidon(uid, arid, s_u)`는 Mode 2의
`Poseidon(uid, rid, salt)`와 같은 것이다. (2026-09-15 개정으로 더 이상 동일하지 않다 — `chainid` 가
들어가 `Poseidon(uid, s_u, chainid, arid)` 가 되었다. `2026-09-14-mode3-attribute-credential-design.md` §3.) §10의 6번 정정은 대화 중 제안했던 중간 설계
(`H(uid, arid)`)에 대한 것이며, **Mode 2 구현에는 그 결함이 없다.**

### 4.2 각 항이 하는 일

| 항 | 역할 | 빼면 생기는 일 |
|---|---|---|
| `uid` | 계정 식별. `PPID` 유도 | `PPID`를 만들 수 없다 |
| `arid` | RP 스코프 바인딩 | 세션키 하나가 털리면 **모든 RP**가 뚫린다 |
| `s_u` | `PPID`에 CIA가 모르는 비밀을 넣는다 | CIA가 `H(uid, arid)`를 열거해 모든 `PPID`를 계산한다 |
| `blind` | 커밋 은닉 | RP 로그 유출 시 CIA가 새어나온 `(arid, pk_i)`와 자기가 아는 `uid`로 `C`를 재계산해 대조하는 심층 방어를 잃는다. 온체인 재도입 시(§9.11)엔 상시 관찰자에 대해서도 마찬가지다 |
| `pk_i` | 이 π가 이 서명자의 것임을 묶는다 | 남의 π를 주워 자기 키로 서명하면 **완전 사칭**이 된다 |

### 4.3 리프를 `C`로부터 **유도**하는 이유

리프가 `C` 안의 속성이면 사용자가 그 값을 고르므로, 아무 난수나 넣고 "내 건 트리에 없다"고
주장할 수 있다. 막으려면 발급 시 정합성 ZKP가 필요하다.

`H(C)`로 두면 **회로가 비공개 입력 `C`에서 직접 계산**하므로 다른 리프를 들이밀 방법이 없다.
발급 ZKP가 통째로 불필요해진다.

그리고 CIA는 서명하면서 `C`를 보므로 `H(C)`를 계산할 수 있다 — **속성을 하나도 모른 채로
정확히 그 credential만 죽일 수 있다.** `arid`를 모르는 채 폐기가 가능한 것이 이 구조의 핵심이다.

## 5. 증명 π

```
공개 입력   PPID, arid, pk_i, max_height, revRoot, pk_CIA_x, pk_CIA_y   ← 이 순서. 단계 (a)·(b)가 의존
비공개 입력 uid, s_u, blind, σ_CIA(S, R8x, R8y), 비멤버십 witness
             (C 는 입력이 아니라 회로가 계산하는 신호다 — 증명자가 C 를 고를 수 없다)

증명 내용
  ① EdDSA-Poseidon.Verify(pk_CIA, Poseidon(DOMAIN_MODE3_CRED, C, max_height), σ_CIA) = 1
  ② C_pt = Commit(uid, arid, s_u, blind, pk_i)                 ← 개봉. pk_i·arid는 공개 입력과 일치
  ③ PPID = H(uid, arid, s_u)
  ④ mask₂₅₂(Poseidon(TAG_MODE3_CRED, C)) ∉ IMT(revRoot)         ← 비멤버십
```

**검증자의 의무: `pk_CIA_x`, `pk_CIA_y`는 공개 입력이므로 회로는 '어떤 키에 대해 서명이 유효하다'만
증명한다. 검증자(RP 서버)는 반드시 이 두 값을 설정에 고정된 CIA 키와
비교해야 한다. 비교하지 않으면 공격자가 자기 키로 자기 credential 에 서명해 통과한다. circomlib
`EdDSAPoseidonVerifier`는 `Ax/Ay`의 곡선·부분군 검사를 하지 않으므로 이 비교가 유일한 방어선이다.**

**검증 경로는 하나다.** 온체인 실행은 기각되었으므로(§9.11) π를 소비하는 곳은 RP 로그인뿐이다.

```
RP 로그인   σ = Schnorr.Sign(sk_i, RP 챌린지)
π는 root가 바뀔 때까지 재사용
```

**π는 재사용한다.** π가 말하는 것은 "root R 기준으로 나는 유효하고 폐기되지 않았다"이므로,
R이 그대로면 다시 증명해도 같은 값이다. 매 요청마다 새로 필요한 것은 **σ뿐**이다
(재생 공격 방지). 자세한 규칙은 §8.4.

## 6. 프로토콜

### 6.1 등록 (1회)

```
1. 사용자 인증 (기존 계정 체계)
2. CIA:   (pk_u, sk_u) 생성 → 사용자에게 전달 → sk_u 폐기
3. 사용자: s_u 무작위 생성
4. 사용자 → CIA: cm_u = s_u·G₃ + r_u·H   (Pedersen. r_u 는 사용자가 보관하는 무작위 블라인딩)
5. CIA:   (uid, pk_u, cm_u, disabled=false) 저장       ← cm_u 는 곡선 점이므로 필드 원소 2개
```

`cm_u`는 **Sybil 방지**를 위해 필요하다. `s_u`를 사용자가 자유롭게 고르면 한 RP에서
여러 개의 `PPID`를 만들어 낼 수 있다. `cm_u`에 고정해 두고 발급 때마다 동일성을 증명한다.

**`G₃`와 `H`는 `C_pt`(§4.1)와 같은 생성원이다.** `s_u`가 두 커밋에서 같은 생성원에
실려야 발급 PoK를 시그마 프로토콜로 짤 수 있다 — 다른 생성원을 쓰면 동일성을 이을 방법이
SNARK밖에 없다(§11).

바뀐 것은 binding 의 근거다. Poseidon 커밋일 때는 해시 충돌 저항이었고, Pedersen 은
**baby jubjub 이산로그**다(부분군 위수 ≈ 2²⁵¹, 약 125비트). hiding 은 **완전(perfect)이 아니라
계산적**이다 — 교과서 Pedersen 은 `blind` 가 `Z_r` 전체에서 균일할 때 완전 hiding 인데, 우리는
`blind` 를 2²⁵⁰ 미만으로 제한하므로(`r ≈ 1.51 × 2²⁵⁰`) `blind·H` 가 부분군의 66% 만 덮는다.
통계적 거리가 상수라 완전 hiding 이 아니며, "이 점의 `H`-이산로그가 2²⁵⁰ 미만인가" 라는
구간 이산로그 문제의 어려움에 기댄다. hiding 이 지켜야 할 상대는 바로 CIA 다 — CIA 는
발급 때 `C_pt` 를, 등록 때 `cm_u` 를 평문으로 본다. 계산적 hiding 으로 충분한 이유는 CIA 가
속성을 추측하려면 2²⁵⁰ 구간 이산로그를 풀어야 하기 때문이다. `s_u`·`r_u`에는 `C_pt`와 같은
**스칼라 상한 2²⁵⁰**을 적용한다 — Sybil 을 실제로 막는 것은 두 사실의 조합이다: (i) `cm_u`
가 `s_u mod r` 을 유일하게 고정한다, (ii) show 회로가 `Num2Bits(250)` 으로 그 잉여류의
대표원을 하나로 좁힌다(`circuits/lib/mode3_commit.circom`). 시그마 프로토콜은 범위를
증명하지 않으므로 등록 시 CIA 가 `s_u < 2²⁵⁰` 를 검사할 수는 없고, 검사할 필요도 없다 —
상한 밖의 `s_u` 로는 show 회로를 통과하는 credential 을 만들 수 없다.

### 6.2 발급 (세션마다)

```
1. 사용자: (pk_i, sk_i) 생성, blind 무작위
           C_pt = Commit(uid, arid, s_u, blind, pk_i)

2. 사용자 → CIA:
     C_pt
     π_issue : 발급 PoK { 공개 입력 (uid, cm_u, C_pt),  witness (arid, s_u, blind, pk_i, r_u) :
                 C_pt = uid·G₁ + arid·G₂ + s_u·G₃ + pk_i·G₄ + blind·H   ← uid 는 공개 입력 (CIA 가 안다)
               ∧ cm_u = s_u·G₃ + r_u·H }                                  ← 등록 시 커밋과 같은 s_u
     h = 사용자가 본 현재 블록 높이
     Sign(sk_u, Poseidon(C_pt.x, C_pt.y, h))

3. CIA: C 를 사용자에게서 받지 않는다 — π_issue 의 공개 입력 C_pt 에서
             C = Poseidon(C_pt.x, C_pt.y) 를 스스로 계산한다. 사용자가 보낸 C 를
             서명하면 증명된 C_pt 와 무관한 값에 서명이 붙어 cm_u 동일성 증명이 무력화된다
        등록된 pk_u 로 서명 검증 (사용자 인증)
        h ∈ [현재높이 − 30, 현재높이 + 1] 확인   ← 요청 본문에 nonce 가 없으면 만료된 요청을
             그대로 다시 내서 새 σ_CIA(새 max_height)를 받을 수 있다(TTL 연장). 창 안의
             재제출은 아래 "같은 C 재발급 거절" 이 막는다 (2026-09-11 리뷰 반영)
        π_issue 검증      ← arid·pk_i·blind 는 여전히 모른다
        disabled == false 확인

4. CIA: max_height = 현재높이 + 300
        σ_CIA = EdDSA-Poseidon.Sign(sk_CIA, Poseidon(DOMAIN_MODE3_CRED, C, max_height))
        (uid, H(C), max_height) 기록

5. CIA → 사용자: (max_height, σ_CIA)
```

`uid`와 `cm_u`를 공개 입력으로 두면 CIA 는 `arid`·`pk_i`·`blind`를 모른 채로 `C` 가 자기
사용자의 것이고 `s_u` 가 등록된 값임을 확인한다. **이것은 §5 의 `pk_CIA` 대조와 같은 급의
검증자 의무다.**

**`π_issue` 는 SNARK 가 아니라 시그마 프로토콜이다.** `C_pt` 와 `cm_u` 가 둘 다 Pedersen 이고
`s_u` 가 같은 생성원 `G₃` 에 실리므로, 두 표현(representation)에 대한 PoK 를 `s_u` 를 공유하는
AND 합성으로 짜면 된다 — 교과서 구성이며 회로가 필요 없다. 비대화형으로 만들 때 **Fiat-Shamir
챌린지는 도메인 태그와 `(uid, C_pt, cm_u)` 를 모두 덮어야 한다.** 덮지 않으면 다른 세션의
발급 증명을 재생할 수 있다.

이 덕분에 두 번째 회로·zkey·검증키와 CIA 측 Groth16 검증 경로가 통째로 불필요해진다.
`π_cred`(§5)는 영향을 받지 않는다 — `cm_u` 는 show 회로에 등장하지 않으므로 §11.1 의
실측값은 그대로다. `sk_i` 소지 증명은 넣지 않는다 — `pk_i` 가 secp256k1 주소라 회로 안에서
증명하려면 secp256k1 스칼라곱과 keccak 이 필요해 비용이 수백만 제약이고, 막는 공격(남의
`pk_i` 를 자기 credential 에 넣기)은 `(C, σ_CIA)` 를 그 키 주인에게 건네주어야 성립한다 — 즉
**양도자가 자기 `PPID` 를 남에게 내주는 자해적 위임**이며 제3자 피해가 없다. §2.2 의
"자발적 양도" 항목으로 범위 밖에 둔다.

### 6.3 RP 로그인 (오프체인 검증)

```
1. RP → 지갑:  challenge
2. 지갑:       revRoot 가 최신이 아니면 π 재생성
               σ = Schnorr.Sign(sk_i, challenge)
3. 지갑 → RP:  (π, 공개입력, σ)
4. RP:
     a. L1 헤드를 최근 10분 안에 읽었는가?   아니면 거부      ← fail-closed
     b. π.revRoot == 방금 읽은 root ?        아니면 거부
     c. 현재 L1 헤드 높이 ≤ max_height ?  아니면 거부   ← 만료. 온체인 §6.4 의
                                                        block.number 검사가 오프체인으로 옮겨온 것
     d. Groth16 검증
     e. Schnorr 검증 (pk_i, challenge, σ)
     f. PPID 로 사용자 식별
```

### 6.4 온체인 실행 — 기각

이 경로는 설계에서 제거되었다. 제거된 내용과 근거는 **§9.11**에 있다.
절 번호는 상호 참조를 깨지 않기 위해 비워 두고 유지한다.

### 6.5 폐기

```
세션 하나:   트리에 H(C) 삽입
계정 전체:   그 uid 의 미만료 H(C) 전부 삽입 + disabled = true
```

두 장치가 각각 다른 것을 막는다. **트리는 이미 발급되어 회수할 수 없는 credential을 죽이고,
`disabled` 플래그는 새로 태어나는 것을 막는다.** 하나만으로는 안 된다 — 트리만 있으면 공격자가
곧장 재발급받아 부활하고, 플래그만 있으면 이미 나간 세션이 만료까지 살아 있다.

게시:

```
publishRoot(bytes32 newRoot, uint64 epoch, bytes32[] calldata newLeaves, bytes sig)
    require(epoch > lastEpoch)                              ← 재생 방지
    require(recover(H(DOMAIN, address(this), newRoot, epoch, keccak(newLeaves)), sig) == CIA_KEY)
    emit Revoked(epoch, newLeaves)                          ← calldata. 저장하지 않는다
    root = newRoot;  lastEpoch = epoch
```

**서명이 리프 배열까지 덮는다(2026-09-10 구현에서 보강).** 제출이 무허가이므로 릴레이어가
서명된 root 에 다른 리프를 붙여 calldata 를 오염시킬 수 있고, 그러면 지갑이 잘못된 트리를
재구성해 root 불일치로 전원이 막힌다. 리프를 서명에 넣으면 그 경로가 닫힌다.

**서명이 로그 컨트랙트 주소도 덮는다(2026-09-11 리뷰 반영).** 원래는 "CIA 키 하나당 로그
하나, 키 회전 = 재배포"를 전제로 주소를 넣지 않았는데, 운영 절차가 재배포 시 CIA 이더 키를
유지하므로 그 전제가 지켜지지 않았다. 그러면 옛 로그의 공개 calldata `(root, epoch, leaves, sig)`
하나를 새 로그에 그대로 제출해 root 를 옛 트리로 바꿀 수 있고, 결과는 위 calldata 오염과 같다
(전원 root 불일치, 로그 재배포 외 복구 불가). 주소를 덮으면 서명이 그 로그에만 유효하다.

같은 이유로 **CIA 는 기동 시 로컬 폐기 트리를 온체인 root 와 대조한다.** 게시 tx 는 성공했는데
상태 저장 전에 죽은 경우는 이미 게시된 pending 접두사를 걷어내 복구하고, 어느 접두사도 맞지
않으면(로그 재배포, 상태 파일 유실·옛 백업 복원) 기동을 거부한다 — 어긋난 채 다음 게시를 하면
전원이 막히기 때문이다.

**credential 단위 폐기는 CIA 의 발급 기록에 있는 리프만 받는다(2026-09-11 리뷰 #7 반영).** 트리가
append-only 라 잘못 넣은 리프가 영구히 남으므로 관리자가 임의의 리프를 넣는 경로를 두지 않는다.
따라서 상태 파일을 옛 백업으로 복원해 발급 기록만 잃은 경우, 그 사이에 나간 살아 있는 credential
은 개별로 폐기할 수 없다(알려진 제약, 2026-09-12 결정 — 강제 폐기 API 로 안전장치를 다시 열지
않는다). 노출은 TTL(`max_height`, 기본 300블록)로 상한이 있고, 계정 단위 폐기의 `disabled` 는
기록과 무관하게 동작하므로 재발급은 즉시 막을 수 있다. 백업 복원 시 원칙은 §7·§6.5 의 기동 대조와
같다 — 기록이 앞선 상태 파일을 쓰지 않는 것이다.

(소비 체인이 있던 설계의 논거다 — §9.11. 여지를 남기기 위해 chainid 는 여전히 넣지 않는다.)
서명 메시지에 **chainid를 넣지 않는다.** 넣으면 CIA가 체인 수만큼 서명해야 한다. 안 넣으면
한 번 서명한 것을 모든 체인에 뿌릴 수 있고, 같은 root를 다른 체인에 재생하는 것은 공격이 아니라
원하는 동작이다. 도메인 분리는 `DOMAIN` 태그와 로그 주소로 한다 — 여러 체인에 같은 서명을
쓰려면 CREATE2 로 주소를 맞추면 된다.

**제출자는 아무나여도 된다.** 권한이 서명에 실려 있으므로 릴레이어를 신뢰할 필요가 없고,
검열 저항이 따라온다.

#### 6.5.1 사용자 개시 폐기 (2026-09-14 추가)

관리자만이 아니라 **사용자 자신도 자기 계정을 폐기할 수 있다.** 목적은 편의다 — 장치를 잃거나
빼앗긴 사용자가 관리자에게 연락하지 않고도 스스로 막는 경로.

```
POST /cia/account/self_revoke  { uid, pwd }
    계정 비밀번호 대조(등록 §6.1 과 같은 계정 체계) → 등록된 uid 인지 확인
    → 계정 전체 폐기(위 §6.5 와 같은 처리: 미만료 H(C) 전부 삽입 + disabled = true)
```

**인증은 계정 비밀번호다. 지갑 키가 아니다.** 분실·탈취 상황에서 `sk_u`·`s_u`·credential 은
전부 공격자 손에 있고 사용자에게는 없다. 요청을 지갑 키로 서명하게 만들면 정작 필요한 순간에
사용자는 서명할 수 없고 공격자만 할 수 있다. 인증 수단은 잃어버린 장치 밖에 있어야 하고, 지갑
에이전트는 비밀번호를 저장하지 않으므로(등록 요청에 실어 보내고 버린다) 장치를 가진 쪽이
비밀번호까지 갖지는 않는다는 전제가 선다.

**별도 컨트랙트를 두지 않는다.** 두 가지가 CIA 밖으로 나갈 수 없다. (1) 비밀번호는 체인이
검증할 수 없다 — calldata 는 공개다. (2) 어떤 리프를 넣어야 하는지(`uid` → 미만료 `H(C)`)는
CIA 의 발급 기록에만 있다. 따라서 체인이 이 경로에서 할 수 있는 일은 지금과 같은 CIA 서명 root
게시뿐이고, 그것은 `RevocationLog` 하나로 이미 충분하다. 사용자 폐기는 "누가 폐기를 개시하느냐"
의 차이일 뿐 의미론(계정 전체 = 리프 삽입 + `disabled`)과 게시 경로는 관리자 폐기와 같다.
체인이 검증할 수 있는 무언가(등록 때 맡긴 이더리움 복구 키)를 두면 요청 접수 컨트랙트가
자연스럽게 들어오지만, 그것은 사용자에게 키 하나를 더 보관시키는 일이라 채택하지 않았다.

**게시 시점은 바꾸지 않는다.** `disabled` 는 즉시 효력을 갖고(재발급 차단), 트리 반영은 다음
게시(§8.1 의 주기 P, 데모에서는 관리자 게시 버튼) 때다. 자기 폐기가 즉시 게시를 부르게 하면
폐기 1건마다 tx 가 나가고 게시 잠금·실패 처리를 사용자 요청 경로에서도 다뤄야 한다.

**체인이 닿지 않아도 폐기가 전부 걸린다(2026-09-14 개정).** 만료 판정이 벽시계(`exptime`)가 되면서 계정 폐기가
체인 head 를 읽을 이유가 없어졌다 — 자기 폐기는 인증 직후 `disabled` 를 저장하고 그대로 미만료 리프를 넣는다.
그동안 게시는 체인이 돌아온 뒤에 한다. (그 전 판의 `treeUpdated:false` 부분 성공 응답은 이 개정으로 사라졌다.)
관리자 폐기(`/cia/revoke`)도 같다.

**복구는 §6.6 그대로 관리자만 한다.** 비밀번호로 스스로 복구하게 두면 비밀번호까지 아는
공격자가 폐기를 되돌릴 수 있다.

**요청은 멱등이다.** 이미 disabled 이거나 미만료 리프가 없어도 성공으로 답한다 — 같은 요청을
두 번 보내 새 리프가 들어가지는 않는다(트리 삽입이 중복을 거른다).

**알려진 한계.** 비밀번호 무차별 대입 제한이 없다. 등록 엔드포인트와 같은 데모 수준 제약이다.
화면은 CIA 가 직접 제공한다(`GET /account`) — 잃어버린 지갑이 아니라 어느 장치에서든 열 수
있어야 하기 때문이다.

| 사고 | 조치 | `PPID` = RP 계정 |
|---|---|---|
| 세션키 `sk_i` 유출 | 그 `H(C)` 폐기 → 즉시 새 credential 발급 | **유지** |
| 계정 침해 | 전체 폐기 + `disabled` → 대역외 확인 후 해제 + 새 `pk_u` | **유지** |
| `s_u`까지 유출 | 새 `s_u` 필요 → `PPID` 변경 → **RP 계정 연결이 끊긴다**. 재연결 필요 | **소실** |

`PPID = H(uid, arid, s_u)`이고 폐기·복구에서 바뀌는 것은 `C`, `pk_i`, 필요시 `pk_u`뿐이므로
앞의 두 경우는 **RP 쪽 계정이 그대로 유지된다.** 사용자는 재로그인만 하면 된다.
(온체인 실행을 기각하기 전에는 이 열이 "지갑·자산"이었고 잔고 보존이 논거였다 — §9.11.)

세션키 도난 시 죽는 것과 사는 것이 정확히 갈린다:

```
공격자가 sk_i 를 훔침 (온체인 경로가 없어 π 는 공개되지 않지만,
                     지갑까지 털려 π 도 넘어갔다고 보수적으로 가정한다)
  → CIA가 그 C 의 H(C) 만 폐기
  → root 게시 후 공격자의 π 는 비멤버십에 걸려 죽는다 (RP 검증에서 거절)
  → 사용자는 새 세션키로 새 C', 새 π' 를 받아 즉시 복귀
  → 공격자는 C' 에 대해 아무것도 없다
```

## 7. 폐기 자료구조와 체인

### 7.1 트리

- **단일 인덱스드 머클 트리.** 샤딩 없음, 층 없음, 리프 종류는 하나이며 태그 값 3 으로
  도메인 분리한다(§4.1).
- 리프 = `H(C)`. **폐기가 일어날 때만 생긴다** (발급 때가 아니다).
- **append-only.** 제거를 지원하지 않는다.
- 깊이 32, Poseidon.

**append-only인 이유는 기술적 제약이 아니다.** IMT에서 삭제는 가능하다(선행 리프를 후속으로
다시 잇고 슬롯을 비우면 된다). 만들지 않는 이유는 **쓸 일이 없어서**다:

- 복구는 리프 제거로 표현할 수 없다. 제거하면 사용자와 함께 **공격자도 되살아난다.**
  복구는 새 credential 발급이지 리프 조작이 아니다.
- 계정 폐기는 만료되지 않으므로 뺄 이유가 없다.
- 만료된 credential의 리프는 아무도 조회하지 않으므로 남아도 무해하다.

### 7.2 폐기 체인

**이더리움 L1** (데모는 로컬 hardhat). 이 체인의 존재 이유는 성능이 아니라 **투명성**이다 —
CIA가 목록을 소급해 고치거나 상대마다 다른 것을 보여주지 못하게 한다. 그 성질은 검증자 집합이
크고 독립적일수록 강해지므로, **빠른 앱체인은 오히려 나쁘다** (CIA가 사실상 장악할 수 있어
체인을 둔 의미가 사라진다).

처리량 요구는 하루 몇 건이라 빠른 체인이 줄 것이 없다.

게시 방식은 **CIA 서명 root + 리프 calldata**다. 네 가지 안 중에서:

| | 폐기 1건당 가스 | 무결성 | 데이터 가용성 |
|---|---:|---|---|
| root만 (BAAR 방식) | ~30k | CIA 신뢰 | **CIA에 의존** |
| **root + 리프 calldata** | **~30k** | CIA 신뢰 (사후 감사 가능) | **체인에서 재구성** |
| 온체인 삽입 검증 | ~71k | 체인이 강제 | 체인에서 재구성 |
| ZK 배치 증명 | ~250k+ | 체인이 강제 | 체인에서 재구성 |

리프 하나는 32바이트라 calldata 비용이 512 gas다. root만 올리는 것과 사실상 같은 값에
**누구든 이벤트를 재생해 트리를 재구성**할 수 있게 된다. root만 올리면 사용자가 비멤버십
witness를 만들 데이터를 CIA에서 받아야 하고, **CIA가 죽는 순간 아무도 증명을 만들 수 없다.**

온체인 삽입 검증이나 ZK 배치 증명은 CIA를 못 믿을 때 필요한 것이고, 그 전제가 없으므로
가스를 두 배·여덟 배 쓸 이유가 없다. 배치가 커지면(약 5건 이상) ZK 배치가 유리해지는 지점이
오지만, 지금은 배치당 1건 수준이라 멀다.

### 7.3 root 전달

**전달할 곳이 없다.** 소비 체인을 두지 않으므로(§9.11) 체인 간 밀어넣기, `RevocationMirror`,
`CredentialVerifier`가 모두 불필요하다. **RP가 폐기 체인(L1)을 직접 읽는다.**

```
RP → L1 노드:  RevocationLog.root()  와  블록 헤드 높이
```

신뢰 앵커는 CIA 공개키 하나이고, RP가 설정으로 고정한다. §5의 검증자 의무(`pk_CIA` 대조)가
그 앵커를 강제하는 유일한 지점이다.

이 단순화는 온체인 실행 기각의 가장 큰 부수 효과다. 체인 간 root 전달은 브리지 신뢰,
릴레이 가용성, 소비 체인별 배포·파라미터 관리를 전부 끌고 들어왔는데 그것이 통째로 사라졌다.

## 8. 파라미터

```
TTL         = 300 블록 (1시간)          이더리움 12초/슬롯 → 3600/12
max_height  = 발급높이 + 300            양자화 없음
N           = 1                        최신 root만 받는다. 경합 여유 0
P           = 배칭 창 ≈ 2.5분           = 실효 폐기 지연
폐기 체인    = 이더리움 L1
fail 정책    = fail-closed
                L1 헤드 신선도 10분 (max_height 가 두 번째 상한)
V           = 없음                     root 일치 규칙이 대신한다
```

### 8.1 `P` — 왜 2.5분인가

`P`는 **게시 사이의 최소 간격 = 배칭 창**이다. 고정 주기가 아니다 — root는 폐기가 실제로
일어났을 때만 바뀌므로, 조용한 구간에서는 게시도 비용도 0이다.

**하한은 폐기 체인의 확정성이 정한다.** 폐기가 들어간 블록이 확정되기 전에 그 root를 소비
체인에 뿌렸는데 재구성(reorg)으로 그 트랜잭션이 빠지면, 미러들은 존재하지 않는 트리 상태의
root를 들고 있게 된다. 그런데 미러의 epoch가 단조 증가라 **되돌릴 수 없고**, 더 높은 epoch로
덮어쓰는 사이에 정상 사용자들이 막힌다.

(아래 표는 온체인 미러가 있던 시절의 하한이다. §9.11 이후에는 적용되지 않는다 — 두 단락
뒤 참조.)

| 폐기 체인 | `P` 하한 |
|---|---|
| 이더리움 L1, 완전 확정 (2 에폭) | 약 13분 |
| **이더리움 L1, 확률적 확정 12블록** | **약 2.5분** |
| 빠른 확정 체인 | 수 초 |

**오프체인 경로만 보면 이 제약이 없다** — RP는 현재 상태를 읽을 뿐이라 reorg가 나면 다음에
읽을 때 바로잡히고, 되돌릴 수 없는 상태가 어디에도 남지 않는다. 확정성이 걸리는 것은
온체인 미러 때문이었다.

**§9.11로 그 미러가 사라졌으므로 확정성 하한도 함께 사라졌다.** 남은 경로가 오프체인뿐이니
`P`를 정하는 것은 이제 확정성이 아니라 배칭 효율(폐기 1건당 게시 가스)과 폐기 지연의 맞교환
뿐이다. 원리적으로는 `P`를 수십 초까지 내려 폐기 지연을 줄일 수 있다.

`P = 2.5분`은 그 제약이 있던 시절에 L1 확률적 확정(12블록)을 택한 값이며, **일단 그대로
둔다.** 이 값에서 포화 시 실패 확률 상한은 0.87%이고(§8.3 개정판), 그 수준에 닿으려면 하루
폐기가 576건을 넘어야 하며 이는 사용자 500만 명 규모다. 현재 값으로도 여유가 크므로 서둘러
조정할 이유가 없다. **`P`는 컨트랙트 상수가 아니라 릴레이어의 운영 설정이므로 재배포 없이
조정할 수 있다.**

### 8.2 `N = 1` — 최신 root만

경합 여유는 `(N−1)·P`이므로 `N=1`이면 **정의상 0**이다. 여유를 준다는 것은 최신이 아닌 root를
받는다는 뜻이고, 그만큼 폐기된 사용자가 더 산다. 요청 단위로 정확히 0이다 — RP가 방금 읽은
root가 지갑이 증명에 쓴 root보다 새로우면 그 요청은 거절된다.

**실패가 공짜라서 감당된다.** RP가 거절하면 지갑이 새 root로 0.8초 재증명해 다시 내면 그만이고,
날릴 가스가 없다. `N=1`이라는 가장 엄격한 선택이 성립하는 것은 **검증이 오프체인이기
때문이다**(§9.11). 온체인이었다면 검사 순서 최적화와 가스 예산이 함께 필요했다.

### 8.3 실패 확률

인플라이트 창 `T` = 지갑이 root를 읽어 π를 만든 시각부터 RP가 root를 읽어 대조하는 시각
**≈ 1.3초** (증명 815ms + 왕복. 증명 시간은 §11.1 Pedersen 판 실측값).

이 값은 데스크톱 실측(§11.1) 기준이다. 브라우저 지갑은 증명이 3~5배 느려 `T` ≈ 3~4.5초이며,
그때 `P=2.5분` 의 포화 상한은 2.0~3.0% 로 "1% 아래" 를 만족하지 못한다(1% 아래를 원하면
`P ≥ 100·T` = 300~450초, `T` = 3~4.5초 각각). 지갑 실행 환경을 정하면 이 절의 표를 그 `T` 로 다시 채운다.

> **2026-09-10 개정.** 이전 값은 `T ≈ 30초`였고 "트랜잭션이 블록에 포함되는 시각"을 끝점으로
> 삼은 것이었다. 온체인 실행을 기각하면서(§9.11) 끝점이 **RP의 검증 시각**으로 바뀌어 전파·포함
> 지연 12~36초가 통째로 빠졌다. 아래 두 표의 값은 그에 따라 다시 계산한 것이다.

**저부하(폐기가 드문 구간).** root 변경을 하루 `R`회의 포아송으로 보면

```
P_실패 = 1 − exp(−R·T/86400)
```

| 사용자 수 | 하루 폐기 `R` (0.01%/일) | 요청당 실패 확률 (`T=1.3s`) | (참고: `T=30s`였을 때) |
|---:|---:|---:|---:|
| 1만 | 1 | 0.0015% | 0.03% |
| 10만 | 10 | 0.015% | 0.35% |
| 100만 | 100 | 0.15% | 3.4% |
| 300만 | 300 | 0.45% | 9.9% |

**포화(폐기가 잦아 배칭이 걸리는 구간).** 게시가 `P` 간격으로 강제되어 등간격에 가까워지므로
사용자의 창 `T`가 그 일정에 균등하게 놓인다고 보면

```
P_실패 ≤ min(1, T/P)
```

| `P` | 폐기 지연 상한 | 실패 확률 상한 (`T=1.3s`) | (참고: `T=30s`였을 때) |
|---|---:|---:|---:|
| 1분 | 1분 | 2.2% | 50% |
| 2.5분 | 2.5분 | **0.87%** | 20% |
| 5분 | 5분 | 0.43% | 10% |
| 10분 | 10분 | 0.22% | 5% |

설계 규칙 **`P ≥ T / 목표 실패율`**은 그대로다. 달라진 것은 이 규칙이 이제 데스크톱 `T`
기준으로 `P=2.5분`에서 이미 1% 아래를 만족한다는 점이다(브라우저 `T` 에서는 위에서 본 대로
그렇지 않다) — 온체인일 때는 목표 1%를 맞추려면 `P`를 50분까지 늘리거나 `T`를 줄여야
했는데, **`T`가 23분의 1로 줄면서 제약이 사라졌다.**

`T`는 여전히 **지갑이 지키기로 하는 규율**이다. 세션 초반에 만든 π를 몇 분 뒤에 그대로 내면
`T`가 그만큼 부풀어 실패 확률이 비례해 오른다. **"제출 직전 root 재확인"을 지갑 요구사항으로
명시한다.** 다만 실패의 대가가 가스가 아니라 0.8초 재증명이므로, 위반의 비용은 이전보다 낮다.

### 8.4 재증명 규칙 — 별도 주기를 두지 않는다

> **π의 `revRoot`는 검증자가 지금 인정하는 root와 같아야 한다.**

`N=1`이므로 RP는 자신이 방금 읽은 root와의 일치를 요구한다. 그러면 **재검증 주기라는
파라미터가 필요 없다.**

```
매 요청마다      새 Schnorr 서명 σ      ← 재생 공격 방지. 비용 무시 가능
root가 바뀔 때만  새 π                   ← 폐기 신선도
```

σ가 "이 요청을 지금 내가 승인한다"를 말하고, π가 "나는 유효하다"를 말한다. 앞의 것은 매번
새로워야 하고 뒤의 것은 root가 바뀔 때만 새로우면 된다.

root는 폐기가 있을 때만, 그것도 `P`마다 최대 한 번 바뀐다:

| 하루 폐기 배치 | 세션(1시간)당 재증명 횟수 |
|---:|---:|
| 10 | 0.4회 |
| 100 | 4회 |
| 576 (`P=2.5분` 포화) | 24회 — 천장 |

### 8.5 fail-closed

| | fail-open | fail-closed (채택) |
|---|---|---|
| root를 못 읽거나 오래됐을 때 | 마지막 root로 진행 | 거부 |
| 폐기된 사용자 | **통과함** | 막힘 |
| 실패의 성격 | 조용함 — 아무도 모름 | 시끄러움 — 즉시 드러남 |

인증 시스템에서 "폐기된 사람이 조용히 들어오고 있다"는 "로그인이 안 된다"보다 나쁘다.
후자는 곧 고쳐지고 전자는 오래 간다.

**오프체인은 공짜다.** RP가 체인을 직접 읽으므로 **블록 헤드**를 본다. root가 안 바뀌어도
체인이 살아 있다는 것을 헤드 높이로 알 수 있어 하트비트가 필요 없다. 임계값 10분은
일상적인 RPC 지연을 흡수할 만큼 여유 있게 잡되, **그 값이 곧 "폐기가 무력화될 수 있는
최대 시간"**임을 유의한다.

**노출 창이 하나로 통일된다.** 온체인 실행을 기각하면서(§9.11) "절반만 fail-closed"였던
두 번째 경로가 사라졌고, 그것을 조이기 위한 하트비트(`H`마다 같은 root 재게시 + `2H`
staleness 검사, 소비 체인당 하루 144 트랜잭션)도 함께 불필요해졌다.

```
withholding 공격의 최대 노출 = 헤드 신선도 임계 = 10분
```

`max_height`(TTL 1시간)는 **두 번째 방어선**으로 남는다. RP가 체인을 아예 못 읽는 상황이
길어져도 credential 자체가 발급 시점에 박힌 마감선에서 죽고, CIA가 새 credential을 안
내주니 갱신도 못 한다. **어떤 방해로도 credential을 TTL 너머로 늘릴 수 없다** — 만료가
credential 안에 들어 있어 외부 전달에 의존하지 않기 때문이다. 다만 정상 운영에서 실효
상한은 10분이며, 1시간은 체인 접근이 완전히 끊겼을 때의 최악값이다.

## 9. 기각한 대안과 이유

### 9.1 유효성 근거 — 누적기 멤버십(BAAR) vs CIA 서명

**CIA 서명을 택했다.** 갱신율이 10,000배 갈린다.

| | 내 샤드/트리 갱신 빈도 | 캐시된 증명 수명 |
|---|--:|--:|
| 비멤버십 (폐기 0.01%/일) | 드묾 | 시간 단위 |
| 멤버십 (발급마다 root 변경) | 블록당 여러 번 | 1블록 미만 |

멤버십은 요청마다 재증명 + CIA 왕복을 받아들일 때만 성립하고, 그러면 **CIA가 모든
트랜잭션의 가용성 의존**이 된다. BAAR은 이 부담을 "users coordinate with the CIA to refresh
their Merkle witnesses" 한 줄로 넘긴다.

BAAR에는 CIA 서명이 없다(유효성 = 누적기 멤버십, `σ`는 사용자의 임시키 Schnorr 서명이다).
따라서 **CIA 서명 도입은 BAAR로부터의 의도적 변경**이며 논문에 그렇게 적어야 한다.

### 9.2 폐기 단위

계정 단위 → credential 단위(`H(C)`)로 정착했다. 계정 단위에서 시작했으나, 리프를 `H(C)`로
두면 CIA가 `arid`를 모른 채로도 정확히 그 credential만 죽일 수 있고, 계정 전체 폐기는
그 uid의 미만료 `H(C)`를 전부 삽입하는 것으로 처리된다. 폐기는 드물고 N은 보통 한 자릿수인
반면 **회로의 머클 경로는 모든 사용자가 매 세션 지불**하므로, 드문 쪽을 비싸게 하고 잦은 쪽을
싸게 하는 것이 맞다.

계층 구조(세션층 + 계정층)는 Mode 2가 없애려던 복잡도를 그대로 되살리므로 기각.

### 9.3 `rid` — 두 번 도입했다가 둘 다 폐기

`rid_cred`(= `H(uid, arid, salt)`)와 `rid_acct`(계정당 무작위)를 만들었으나 `H(C)`가 둘 다
대체했다. `H(C)`는 CIA가 이미 알고 회로가 직접 계산하므로, 발급 ZKP도 사용자가 장기 보관할
값도 필요 없다. 리프 **종류를 구분하는** 태그가 필요 없다(도메인 분리 태그 3 은 있다 — §4.1).
**`rid`라는 이름의 값은 최종 설계에 없다.**

### 9.4 샤딩

불필요. 리프가 폐기 시에만 생기므로 트리가 작다. 샤딩하면 샤드 인덱스가 공개되어
**CIA에 대한 누출**이 된다(CIA는 `H(C)`를 알므로 인덱스를 계산할 수 있고, 요청마다
후보를 좁힌다). Mode 2의 복잡도 대부분이 여기서 나왔다.

### 9.5 `max_height` 양자화 (`Q`)

**도입하지 않는다.** `Q`는 `max_height`가 준식별자가 되는 것을 막기 위한 것이었으나,
§2.4의 "동시 로그인 없음" 가정 아래에서는 신호가 성립하지 않는다(로그인이 몇 분만 떨어져도
값이 달라 일치하지 않는다). 빼면 **수명이 정확히 300블록으로 고정**되는 이득도 따라온다
(`Q`가 있으면 1~2시간으로 흔들린다).

남는 노출: 거의 동시에 시작된 두 세션 사이에 우도비 약 300의 상관 신호. 후보를 1/300로
좁히는 효과이며 식별을 성립시키지는 않는다.

**§9.11로 이 노출은 소멸했다.** 온체인 경로가 없으면 `max_height`를 보는 것은 RP뿐이고,
RP는 자기 세션의 발급 시각을 어차피 안다. 제3자 관찰자가 존재하지 않는다.

### 9.6 `N ≥ 2` (수용 창)

(온체인 프레이밍의 기각 근거다. 오프체인 전용에서는 §8.2 의 "실패가 공짜" 논거만으로
충분하다.)

기각. 체인마다 root가 다른 것은 문제가 되지 않는다 — 트랜잭션은 한 체인을 대상으로 하고
지갑이 그 체인의 현재 root에 맞춰 증명하면 된다. `N=1`의 비용은 경합뿐이고 §8.3에서
정량화된 수준이다.

### 9.7 `H(C)`를 RP에 공개

기각. 공개하면 RP가 트리를 직접 확인해 재증명이 0이 되지만, §8.4의 root 일치 규칙으로도
지연은 같고 재증명은 폐기가 있을 때만이라 **얻는 것이 없다.** 회로가 어차피 `H(C)`를 내부에서
계산하므로 숨기는 비용이 0이다. 공짜인 쪽을 버리고 정보를 내줄 이유가 없다.

### 9.8 `arid`를 CIA에 공개

기각. `C`가 단순 해시가 되어 회로가 가벼워지지만, CIA가 `(uid, arid)`를 갖게 되면
사용자의 RP 접속 이력 전체를 알게 되고, `s_u`가 없다면 `PPID`까지 계산해 각 RP에서의
사용자 신원을 실명으로 연결할 수 있다. honest-but-curious 모형에서 **준 정보는 곧 학습된 정보다.**

### 9.9 RP가 CIA에 매번 조회

기각. ① CIA가 죽으면 모든 RP의 모든 요청이 멈춘다. ② 매번 CIA에게 물으면 CIA의 말이 곧
진실이 되어 **폐기 체인이 장식이 된다.** ③ CIA가 모든 사용자의 활동을 실시간으로 본다.
**신뢰 여부와 무관하게 조회는 체인에서 한다.**

### 9.10 `arid` 공개 노출 (§9.11로 소멸)

`arid`는 π의 공개 입력이라 온체인 경로에서는 관찰자가 지갑이 어느 RP 소속인지 본다. Mode 2는
`rid`를 비공개로 두고 `arid_i`만 공개했다. Mode 3는 지갑이 RP마다 별개(`PPID` 기반)라 소속
자체가 주소 구조에서 드러나므로 추가 손실이 없다고 보고 **감수하기로 했었다.**

**§9.11로 이 노출은 소멸했다.** 온체인 경로가 없으면 π는 RP에게만 전달되고, RP는 자기
`arid`를 이미 안다. 다만 **RP는 `PPID`를 공개 입력으로 직접 받으므로**(§6.3 4f) 자기 RP
스코프 안에서 사용자를 지속 식별한다 — 이것은 `PPID`의 설계 목적 그대로이며 노출이 아니다.

### 9.11 온체인 검증 경로 (기각, 2026-09-10)

**Mode 3는 오프체인 검증만 한다.** `PPIDWallet.execute`, `RevocationMirror`,
`CredentialVerifier`, 소비 체인 N개가 전부 설계에서 빠졌다.

제거된 설계를 기록으로 남긴다:

```
PPIDWallet.execute(π, publicInputs, σ, txPayload):
     a. require(revRoot == mirror.currentRoot())     ← 가장 싸고 가장 자주 실패. 먼저
     b. require(block.number <= max_height)
     c. require(PPID == 이 지갑의 PPID)
     d. Groth16 검증                                  ← 가장 비쌈. 마지막
     e. Schnorr 검증 (pk_i, txPayload, σ)
     f. 실행
```

**기각 근거.** 두 경로를 나란히 놓고 비교했을 때 온체인이 모든 축에서 나빴다.

| | 오프체인 (§6.3) | 온체인 (제거됨) |
|---|---|---|
| 폐기 체인 접근 | 직접 읽음 (헤드까지) | **불가** — 결정적 상태 기계 |
| withholding 노출 창 | **10분** | **60분** (`max_height`가 유일한 상한) |
| fail-closed | 완전 | **절반** — 오래된 root로도 진행 |
| 실패 비용 | 0 (0.8초 재증명) | 3만 가스 소각 |
| 실패 확률 | 0.15% @100만 | 3.4% @100만, 포화 시 20% |
| 검증 비용 | 21 ms CPU | ~25만 가스 |
| 관찰자 | RP 단독 (π 에 한해서. 폐기 체인 calldata 는 §9.12) | 전 세계, 영구 |

결정적인 것은 **첫 두 행의 방향이 반대라는 점**이다. 온체인은 자산 이동을 다루므로 오류를
되돌릴 수 없는데, 폐기 신선도는 오프체인보다 6배 느슨했다. 컨트랙트가 폐기 체인의 헤드를 볼 수
없어 §8.5의 "헤드 높이로 생존 확인"을 쓸 수 없기 때문이며, 구조적 한계라 파라미터로 못 고친다.
하트비트로 60분을 20분까지 줄일 수 있었으나 소비 체인당 하루 144 트랜잭션이 붙고, 그래도
오프체인의 10분에 못 미친다.

**제거로 사라진 것.**

- §7.3 체인 간 root 전달 전체 — 브리지 신뢰, 릴레이 가용성, 소비 체인별 배포·파라미터
- §9.5 `max_height` 상관(우도비 300), §9.10 `arid` 소속 노출 — **둘 다 온체인 경로 전용 노출**
- §8.2 가스 예산과 검사 순서 최적화, §8.3의 실패 확률 (`T`가 30초 → 1.3초로 23배 감소)
- §8.5 "절반 fail-closed"와 하트비트 미결 항목
- §12 구현 단계 (b)
- §4.1/§4.2 의 `pk_i`·`blind` 은닉 근거 — "체인에 공개된 값과 대조" 에서 "RP 로그 유출 시
  심층 방어 + 재도입 대비" 로 낮아졌다

**대가.** PPID 지갑과 자산 기능을 포기한다. **Mode 3는 SSO 전용 설계다.** §6.6 복구표의
"세션키가 털려도 잔고가 보존된다"는 논거가 근거를 잃었고, 그 열은 "RP 계정 유지"로 바뀌었다.

**되돌리려면** 이 절이 출발점이다. 최소 조건은 하트비트 도입(노출 20분)이며, 그래도 오프체인과
동등해지지 않는다는 점을 먼저 받아들여야 한다.

### 9.12 계정 폐기의 묶음 노출 (확정: 감수, 2026-09-10)

§6.5의 `emit Revoked(epoch, newLeaves)`는 리프 배열을 calldata로 공개한다. 계정 전체
폐기는 그 uid의 미만료 `H(C)`를 **한 epoch에 한꺼번에** 삽입하므로 관찰자가 읽는 것이 있다.

| 드러나는 것 | 여전히 숨는 것 |
|---|---|
| 그 배열의 리프들이 **같은 사람의 것**이라는 관계 | 그게 누구인지 — `H(C)`는 π의 공개 입력이 아니다 |
| 그 사람이 최근 TTL(1시간) 안에 연 세션 수 `N` | 어느 RP였는지 — `arid`는 `C` 안에 은닉 |
| 계정 폐기(세션 폐기가 아니라)가 일어났다는 사실 | |

§10의 1번 감수 사항("폐기가 언제 일어났는지는 공개된다. 누구인지는 숨는다")에서 한 단계 더
나간다. **누구인지는 여전히 숨지만, 묶음 관계와 그 크기 `N`이 추가로 드러난다.**

**배칭이 가려주지 않는다.** 창 `P` ≈ 2.5분이 폐기들을 섞어주는 것은 폐기가 잦을 때뿐이다.
§7.2의 전제대로 처리량이 하루 몇 건이면, 한 창에 리프가 2개 이상 실린 것 자체가 거의 확실히
계정 폐기 한 건이다. 익명성 집합이 트래픽에 비례하는 전형적 문제이며, 여기서는 트래픽이 낮은
것이 설계 조건이므로 저절로 해소되지 않는다.

**규모.** §2.4의 "동시 로그인 없음" 가정 아래 `N`은 TTL 1시간 안에 접속한 서로 다른 RP
수이므로 보통 한 자릿수 초반이다. 실측한 값이 아니라 가정에서 유도한 추정이다.

| 안 | 방법 | 비용 |
|---|---|---|
| 감수 | 그대로 둔다 | `N`과 묶음 관계가 노출된다. `H(C)`가 다른 어떤 공개값과도 연결되지 않으므로 실익이 낮다는 판단 |
| 패딩 | 매 epoch 고정 개수를 더미 리프로 채운다 | 트리 성장 + calldata gas. 더미는 조회되지 않으므로 정확성에는 무해 |
| 분산 | `N`개를 여러 epoch에 나눠 올린다 | 폐기 지연이 `N·P`로 늘어 §8.3의 실패 확률이 나빠진다. TTL 안에 끝나야 의미가 있다 |

**결정: 감수 (2026-09-10, 사용자 확정).** 드러나는 것은 "같은 사람의 리프 `N`개"라는 관계와
`N`뿐이고, `H(C)`는 π의 공개 입력이 아니라 다른 어떤 공개값과도 연결되지 않으므로 실익이 낮다.
패딩은 트리 성장과 calldata gas 를, 분산은 폐기 지연 `N·P`로 §8.3의 실패 확률 악화를 대가로
치르는데 둘 다 그 실익을 넘는다. 온체인 경로를 기각해도(§9.11) 이 노출은 폐기 체인 calldata에서
나오므로 **그대로 남는다** — 트래픽이 늘어 배칭이 실제로 섞어주게 되면 저절로 완화된다.

## 10. 설계 대화 중 정정한 것

구현할 때 잘못된 근거를 되살리지 않도록 남긴다.

1. **"하트비트를 넣으면 폐기 발생 타이밍 누출이 사라진다"** — 틀렸다. 하트비트는 같은 root를,
   폐기는 새 root를 올리므로 관찰자가 그냥 구별한다. 하트비트가 해결하는 것은 withholding
   탐지(fail-closed)뿐이다. **"폐기가 언제 일어났는지는 공개된다. 누구인지는 숨는다"**가
   감수 사항이다.
2. **`P_실패 ≤ 1−exp(−(1440/P)·T/86400)`** — 틀렸다. 포화 상태의 게시는 등간격에 가까워
   포아송보다 나쁘다. 올바른 상한은 `min(1, T/P)`이며, 이전 값은 과소평가였다.
3. **"`max_height` 상관이 `arid` 은닉을 무력화한다"** — 과장이었다. 우도비 약 300의
   상관 신호이지 식별이 아니다.
4. **"체인 간 공통 root가 없으면 곤란하다"** — 과장이었다. 하나의 π를 여러 체인에 재사용하는
   전제에 기댄 논거였고, 그 전제가 필요한 상황이 드물다.
5. **"두 검증 경로는 서로 다른 회로가 필요하다"** — 온체인이 `PPID` 기반 지갑을 쓰기로 하면
   공개 입력 집합이 일치하므로 **회로 하나로 통합된다.** (2026-09-10: 온체인 경로 자체가
   기각되어 경로가 하나만 남았다 — §9.11. 정정은 여전히 옳지만 적용 대상이 사라졌다.)
6. **`PPID = H(uid, arid)`** — CIA가 `uid`를 알고 `arid`는 공개 RP 식별자이므로 **CIA가
   모든 RP에 대해 열거할 수 있었다.** 발급 시 `arid`를 가려도 소용이 없다(사건은 가려지지만
   대응 관계는 계산된다). `s_u`를 넣어 고쳤다. **이 결함은 대화 중 제안했던 중간 설계에만 있었고, Mode 2의
`pi_ppid.circom`은 처음부터 `Poseidon(uid, rid, salt)`로 사용자 비밀을 포함하고 있다.**
7. **"append-only라서 재기준화가 필요하다"** — 인과가 반대다. 리프를 뺄 수 있어도 복구는
   새 credential 발급이어야 한다. 제거는 공격자까지 되살리기 때문이다.

## 12. 구현 단계

**(c) → (a) 순서.** 회로가 이 설계의 심장이고, 제약 수와 증명 시간이 나와야
나머지 판단(재증명 빈도가 감당 가능한지)이 근거를 갖는다.
온체인 실행 단계 (b)는 기각과 함께 삭제되었다(§9.11).

### (c) 회로

- `circuits/pi_cred.circom` (+ `circuits/lib/mode3_commit.circom`) — §5의 ①~④
- 제약 수, 증명 시간, 검증키 크기 측정
- 회로 컴파일·셋업은 **별도 승인 후** 실행 (오래 걸리고 기존 산출물에 영향)

### (a) 오프체인 전 구간

- ✅ 발급 PoK — §6.2 의 시그마 프로토콜(`C_pt` 표현 PoK ∧ `cm_u` 표현 PoK, `s_u` 공유). **회로가 아니므로 두 번째 zkey·검증키·더 큰 ptau·CIA 측 Groth16 검증 경로가 전부 불필요하다.** 구현은 순수 JS(baby jubjub 스칼라곱)이고, Fiat-Shamir 트랜스크립트가 도메인 태그와 `(uid, C_pt, cm_u)` 를 덮는지 테스트로 고정한다 — `lib/mode3_issuance.js`
- ✅ `cia.js` — 등록, 발급, 폐기, 트리 관리, root 게시 (Mode 2의 `custom_idp.js`는 손대지 않는다) — `cia.js`, `lib/mode3_state.js`
- ✅ 폐기 체인 컨트랙트 (`RevocationLog`) + 로컬 hardhat 배포 — `contracts/RevocationLog.sol`
- ✅ RP 로그인 검증 (오프체인 Groth16 + 신선도 + Schnorr) — `lib/mode3_rp.js`
- ✅ 지갑 측: 트리 전체 동기화, 위트니스 로컬 생성, π 캐시와 root 일치 확인 — `lib/mode3_wallet.js`
- ✅ RP 검증기의 `pk_CIA` 고정 대조 (§5) — 설정에 박힌 CIA 키와 `publicSignals[5..6]` 비교.
  **공격자가 자기 키로 서명한 credential 이 거부되는 음성 테스트**로 고정한다 —
  `lib/mode3_rp.js` d단계 + `tests/test_mode3_rp.mjs`
- ✅ §9.12 계정 폐기 묶음 노출 — 감수로 확정 (2026-09-10, 사용자)

### Poseidon 전환 (보류)

`pi_cred` 의 `C` 계산 블록을 `CommitPoseidon` 으로 되돌리고(`Cf` 자리에 Poseidon 출력),
`credCommit` 을 `credCommitPoseidon` 으로 바꾸고, 발급 PoK 를 시그마에서 SNARK `π_issue` 로
옮긴다(회로·zkey·CIA 검증 경로 신설). 공개 입력 순서와 리프 규약은 유지된다. 전환 기준선
수치는 §11.1 의 Poseidon 열이다.

### 제약

- **Mode 2 데모를 건드리지 않는다.** 별도 포트, 별도 상태 파일. 실행 중인 `custom_idp.js`(:4000)와
  `idp_state.json`은 손대지 않는다.
- 회로 재생성(`zk:compile`, `zk:key`)은 사용자 승인 후에만.
- 새 테스트는 `scripts/run_tests.sh`의 해당 그룹에 등록한다.
