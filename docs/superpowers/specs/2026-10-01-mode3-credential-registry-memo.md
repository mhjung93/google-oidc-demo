> 1. valid credential list가 왜 필요한지 이유도 따로 만들고
> 2. 애초에 RCL은 두 개 종류로 나누는 게 당연해 보인다
> 3. latest active cred도 왜 필요한지 생각해 봐라 — 의도적으로 바로 revoke해 RCL에 올려 내가 등록한 C가 C′으로 바뀌지 않았는지 체크하고 싶을 수 있다

## 0. 요약

세 줄은 하나의 요구로 읽힌다 — **사용자가 IdP(AA)의 발급 장부를 스스로 확인할 수 있어야 한다(IdP 책임성).** 지금 설계는 AA를
honest-but-curious로 두어(가정 A10) 그 요구를 다루지 않는다. 다루려면 "쓸 수 있는 사용자 자격증명"이 공개 구조에 있어야 하고,
그 구조는 집합(set)이 아니라 **사용자별 슬롯**이어야 탐지가 된다. 슬롯을 들이면 폐기 구조는 저절로 두 종류가 된다:
사용자 레벨 = 슬롯 등록부(멤버십, 갱신형), 세션 레벨 = 폐기 트리(비멤버십, append-only). 권고안은 §4의 O2이고, 비용은
회로 +2천 제약 안팎·공개 입력 +1·온체인 쓰기는 자격증명 발급 때만(세션은 그대로 0)이다. 결정 요청은 §6.

## 1. 세 줄을 하나로 — 무엇이 빠져 있나

**지금 모델.** AA는 사용자를 비밀번호로 인증하고 사용자 키 sk_u까지 **AA가 만들어 준다**(`cia.js:380-384`). 사용자 자격증명 발급은
sk_u 서명 + π_u(C_u가 uid·등록 cm_u·AA 기록 속성으로 열림)를 AA가 검사한 뒤 서명한다. 서명은 비공개(지갑과 증명 안에만)다.
사용자가 자기 자격증명 상태를 알 길은 `/account` 페이지뿐인데 이것은 **AA의 자기 보고**다.

**AA가 부정하면.** sk_u·비밀번호·검사 절차를 모두 AA가 쥐므로 AA는 임의의 uid에 대해 자기 salt′로 C′을 만들어 서명할 수 있다.
그 C′으로는 사용자의 기존 주소를 쓸 수 없고(salt를 모름) **같은 uid의 두 번째 신원**이 생긴다. 해는 둘이다.
- Sybil: uid당 계정이 여럿 — "실명 1인 1계정"을 전제하는 서비스에서 AA가 계정을 찍어낼 수 있다.
- 모함: 그 세션의 Trace Tag를 열면 피해자 uid가 나온다.

**막을 수 없는 것과 잡을 수 있는 것.** AA는 사용자 DB의 주인이라 가짜 uid를 만드는 것은 어떤 공개 구조로도 못 막는다. 잡을 수
있는 것은 **내 uid로 발급된 것이 내가 만든 것뿐인가**의 탐지이고, 교수님의 세 줄은 모두 이 탐지를 가리킨다.

**교수님 예시의 뜻.** "일부러 폐기해 RCL에 올려 확인"은 현 구조에서 사용자가 쓸 수 있는 유일한 공개 확인 수단이다. 그런데 그
방법으로 확인되는 것은 "AA가 내 H(C_u)를 알고 있다"까지이고, 병행 C′의 존재는 보이지 않는다. 그래서 "latest active"가 필요하다는
것이 세 번째 줄이다.

## 2. 질문 1 — VCL이 왜 필요한가, 왜 뺐는가

| | 내용 |
|---|---|
| 뺀 이유(9/23 논증, 유효) | 유효성 = AA 서명 + 만료. 발급 때 온체인 쓰기 0, 증명은 비멤버십만, 발급 기록이 공개되지 않아 AA↔RP를 잇는 손잡이가 없다 |
| 필요한 이유(교수님) | **책임성.** 서명은 비공개라 사용자·감사자가 발급을 볼 수 없다. 쓸 수 있는 모든 사용자 자격증명이 공개 구조에 있고 검증자가 그 구조를 증명 안에서 요구해야, AA가 공개하지 않은 C′은 어디서도 쓸 수 없고 공개한 C′은 사용자가 본다 |
| 형태 | 집합 VCL은 탐지에 무력하다 — 항목이 해시라 어느 것이 내 uid 것인지 모른다. **사용자별 슬롯**이어야 "내 자리에 내 값이 있는가"를 볼 수 있다 |
| 범위 | **사용자 자격증명만.** 세션 증명 π_RP는 C_u를 열어야 하므로(salt) AA가 사용자의 C_u 위에 세션을 위조할 수 없다. 세션은 서명 + 폐기 트리로 충분하고 VCL에 넣으면 로그인마다 온체인 쓰기가 생긴다 |

## 3. 질문 2 — RCL 두 종류

지금은 트리 하나에 태그로 두 종류(사용자 리프 H(4, H(C_u)), 세션 리프 H(5, H(C_s)))다. 논리적으로는 이미 둘이지만 교수님
말씀대로 **역할이 달라서** 구조도 다른 것이 자연스럽다.

| | 사용자 자격증명 | 세션 자격증명 |
|---|---|---|
| 수명 | 사용자당 하나, 속성 바뀔 때만 교체 | 로그인마다 새로, 300~400블록 뒤 만료 |
| 필요한 질문 | "지금 활성인 것이 이것인가" (멤버십) | "만료 전에 폐기됐는가" (비멤버십) |
| 구조 | **슬롯 등록부** — 갱신형, 키당 값 하나 | **폐기 트리** — append-only, 현행 그대로 |
| 폐기 | 슬롯을 비우거나 새 값으로 교체 → 옛 C_u는 멤버십 실패 | 리프 추가(현행) |

슬롯을 들이면 폐기 트리의 사용자 리프 종류는 없어진다(사용자 자격증명 폐기 = 슬롯 교체). 그래서 "두 종류"는 "트리 둘"이 아니라
**"등록부 하나 + 폐기 트리 하나"**가 된다. 슬롯 없이 트리만 둘로 쪼개는 안은 §5 표의 열 B다 — 책임성은 얻지 못하고 root만 둘이 된다.

## 4. 질문 3 — latest active 설계안

| 안 | 구조 | 내 C→C′ 교체 탐지 | 비용 | 판단 |
|---|---|---|---|---|
| O0 현재 | 공개 구조 없음(폐기 리프만) | 불가 — 폐기해도 병행 C′은 안 보임 | 0 | 책임성 없음 |
| O1 집합 VCL | 활성 H(C_u) 집합, π_RP가 멤버십 | 불가 — 어느 항목이 내 것인지 모름 | 발급마다 쓰기, 멤버십 1건 | 비용만 들고 탐지 못 함 |
| **O2 슬롯(키 = cm_u)** | 등록 커밋먼트 cm_u → 활성 H(C_u) 한 칸. π_RP가 ① 슬롯(cm_u) = H(C_u) 멤버십, ② C_u의 salt = cm_u의 salt(Pedersen 등식)를 증명 | **됨** — 내 cm_u 칸에 내 H(C_u)가 있는지 지갑이 확인; AA가 C′을 쓰려면 내 칸을 바꿔야 하고 그러면 내 자격증명이 죽어 바로 드러남 | 자격증명 발급 때만 쓰기, 멤버십 1건 + Pedersen 2항 | **권고** |
| O2′ 슬롯(키 = VRF_AA(uid)) | uid당 키 하나를 VRF로 강제 | O2 + "내 uid의 두 번째 등록"까지 | 키↔uid 결속을 회로 안에서 해야 해 비쌈(VRF 검증 or AA 서명 1건 추가), 구현량 큼 | 과제로 남김 |
| O3 서명 영수증 | AA가 발급 기록에 서명해 지갑이 보관 | 불가 — 제3자에게 발급한 것은 내가 못 봄 | 거의 0 | 부정의 **증거 보관**에는 쓸모 있으나 탐지 수단은 아님 |

**O2가 잡는 것과 못 잡는 것.** 잡는 것: 내 등록(cm_u)의 활성 자격증명이 바뀌었는지, 활성이 정확히 하나인지(구조상 칸이 하나),
발급이 공개됐는지. 못 잡는 것: AA가 내 uid로 **등록을 하나 더**(cm_u′) 만드는 것 — 키가 uid와 무관해서다. 이것을 잡으려면
키가 uid의 결정적 함수여야 하는데, 공개 pepper면 uid 사전 공격(uid는 작은 수), 비밀 pepper면 AA가 둘을 쓸 수 있어 VRF가
필요하고 그 결속을 회로 안에 넣어야 한다(O2′). 1차로는 O2를 들이고 두 번째 등록은 한계로 적는 것을 권한다 — 교수님 예시
("내 C가 C′으로 바뀌지 않았는지")는 O2가 그대로 답한다.

**O2의 프라이버시.** 슬롯 키 cm_u는 Pedersen 커밋먼트라 은닉이고 RP는 본 적이 없다(π_RP의 비공개 증인). 관찰자가 새로 아는 것은
등록 수와 슬롯 갱신 시각이다. 갱신 시각과 첫 로그인의 상관은 지금 폐기 리프 시각과 같은 부류의 누설이다(형식 문서 §8 (c)).
AA는 cm_u↔uid를 이미 안다. 즉 RP 쪽 연결성은 늘지 않고, 체인 쪽에 "사용자 수"가 새로 보인다.

**사용자 확인 절차(O2).** 지갑이 등록부 root와 자기 cm_u의 경로를 읽어 칸의 값 = 자기 H(C_u)인지 본다. 폐기도 요청도 필요 없다.
다르면 "AA가 내 요청 없이 바꿨다"이고, 바뀐 요청에는 내 sk_u 서명이 있어야 하므로(`userCredRequestMessage`) AA가 그 서명을 못
내면 부정의 증거가 된다 — 단 sk_u를 AA가 만들어 주는 현 등록 방식에서는 이 증거력이 약하다. **등록 때 키를 지갑이 만들어
pk_u만 내는 것**이 O2와 같이 가야 할 작은 변경이다(스펙에서 결정).

## 6. 결정 요청

1. **O2 채택** — 사용자 자격증명 등록부(키 cm_u, 값 H(C_u))를 두고 π_RP가 멤버십 + salt 등식을 증명. 세션은 현행 폐기 트리.
2. **등록 키를 지갑이 생성**(pk_u만 AA에 제출) — O2의 증거력을 위한 동반 변경.
3. **두 번째 등록 한계 수용** — O2′(VRF 키)는 논문의 한계·향후 과제로 적는다.
4. **논문 반영 범위** — §V 구조(등록부 + 폐기 트리), 새 목표 G12 "발급 책임성(사용자가 자기 등록의 활성 자격증명을 공개 구조로 확인)", 형식 문서 가정 (A10) 완화 범위.

승인되면 다음 단계는 설계 스펙(brainstorming) → 회로 V9 → 벤치 재측정 순서다.

## 7. 슬라이드용 한 줄들 (B 단계에서 2장에 넣을 것)

- VCL이 필요한 이유: 서명은 비공개라 사용자가 AA의 발급을 볼 수 없다 → 책임성. 뺐던 이유: 검증에는 서명 + 만료로 충분(발급 때 쓰기 0).
- 형태: 집합이 아니라 사용자별 슬롯(키 = 등록 커밋먼트). 세션은 제외.
- 두 종류: 등록부(멤버십, 갱신) + 폐기 트리(비멤버십, append-only). 사용자 리프 종류는 등록부로 흡수.
- latest active = 슬롯 자체. 폐기해서 확인할 필요가 없다. 못 잡는 것: 내 uid의 두 번째 등록(VRF 키 과제).
- 비용: 제약 +2천 안팎, 공개 입력 +1, 쓰기는 자격증명 발급 때만.
